# PandaWiki 系统功能文档（基于代码梳理）

## 1. 文档目的

本文档面向毕业论文补充、项目答辩说明和后续维护交接三个场景，对 PandaWiki 当前代码中已经实现的功能进行系统化梳理。与偏产品宣传性质的简介不同，本文档强调“功能模块 - 页面入口 - 接口入口 - 用例层实现 - 数据流”的对应关系，尽量回答以下几个问题：

1. 系统到底已经实现了哪些能力。
2. 每项能力主要由哪些页面、接口和后端模块承载。
3. 这些能力如何围绕知识接入、RAG 问答、知识图谱和公开站点形成闭环。
4. 哪些能力已经落地，哪些属于预留扩展位。

本文档主要依据以下代码范围整理：

- 管理后台前端：`web/admin/src/pages/*`
- 公开站点前端：`web/app/src/*`
- 后端接口层：`backend/handler/v1/*`、`backend/handler/share/*`
- 后端业务层：`backend/usecase/*`
- 向量检索与图数据库实现：`backend/store/rag/*`、`backend/store/neo4j/*`
- 异步任务与消费者：`backend/handler/mq/rag.go`

## 2. 系统角色与使用场景

### 2.1 系统管理员

系统管理员主要使用管理后台，承担知识库创建、文档组织、页面配置、机器人接入、权限治理、图谱维护、版本发布、反馈审核和统计分析等职责。对应页面入口主要包括：

- 文档管理：`web/admin/src/pages/document/index.tsx`
- 设置中心：`web/admin/src/pages/setting/index.tsx`
- 版本发布：`web/admin/src/pages/release/index.tsx`
- 数据统计：`web/admin/src/pages/stat/*`
- 对话记录：`web/admin/src/pages/conversation/index.tsx`
- 图谱管理：`web/admin/src/pages/graph/index.tsx`
- 反馈与评论：`web/admin/src/pages/feedback/index.tsx`
- 用户贡献审核：`web/admin/src/pages/contribution/index.tsx`

### 2.2 公开站点访客

访客使用公开 wiki 站点或嵌入式机器人，主要完成文档浏览、目录导航、AI 问答、仅搜索文档、发表评论、提交反馈、提交文档贡献等操作。主要入口包括：

- 门户首页与动态落地页：`web/app/src/views/home/index.tsx`
- 文档阅读页：`web/app/src/views/node/*`
- 问答弹窗：`web/app/src/components/QaModal/*`
- H5/Widget 问答页：`web/app/src/views/h5Chat/*`、`web/app/src/views/widget/*`

### 2.3 外部渠道与系统集成方

系统还支持以开放接口或机器人方式接入外部渠道，包括：

- OpenAI 兼容接口机器人
- Widget 嵌入机器人
- 钉钉、飞书、Lark、Discord 机器人
- 微信公众号、微信客服、企微机器人、企微 AI Bot
- MCP Server 文档检索能力

这些能力主要由设置页配置，并通过 `backend/handler/share/*` 提供公开访问入口。

## 3. 系统总体功能概览

从代码结构看，PandaWiki 不是单一的“聊天问答页面”，而是由六类能力共同组成的知识服务平台：

1. 知识库与文档管理能力
2. 多源知识接入与内容导入能力
3. RAG 检索增强问答能力
4. 公开 wiki 站点与多渠道机器人能力
5. 知识图谱建模、查询、可视化与故障恢复能力
6. 权限、安全、反馈、统计和发布治理能力

后端接口从职责上分为两类：

- 管理接口：`backend/handler/v1/provider.go` 统一挂载 `User`、`KnowledgeBase`、`Node`、`App`、`File`、`Model`、`Conversation`、`Crawler`、`Stat`、`Comment`、`Graph` 等后台模块。
- 公开接口：`backend/handler/share/provider.go` 统一挂载 `ShareNode`、`ShareApp`、`ShareChat`、`ShareComment`、`ShareConversation`、`ShareStat`、`ShareWechat`、`ShareCaptcha`、`OpenapiV1` 等外部访问入口。

这意味着系统在架构上已经天然区分了“管理面”和“服务面”，便于论文中解释不同角色的业务边界。

## 4. 后台管理端功能

### 4.1 知识库生命周期管理

知识库管理由 `backend/handler/v1/knowledge_base.go` 与 `backend/usecase/knowledge_base.go` 实现，覆盖从创建到发布的完整生命周期。

#### 4.1.1 知识库创建

知识库创建并不是只写一条数据库记录，而是包含两步初始化动作：

1. 先调用向量服务创建数据集，获得 `dataset_id`。
2. 再在 PostgreSQL 中创建知识库记录，并保存访问域名、端口、公私钥等接入配置。

随后系统会异步触发图谱同步，在 Neo4j 中创建 `KnowledgeBase` 节点。这一逻辑位于 `KnowledgeBaseUsecase.CreateKnowledgeBase` 中，说明知识库一经创建，就同时成为：

- 业务主库中的管理对象
- 向量检索范围的逻辑边界
- 图数据库中的知识组织根节点

#### 4.1.2 知识库成员与管理员

知识库支持成员邀请、权限调整和管理员维护，相关逻辑集中在：

- 后端：`GetKBUserList`、`KBUserInvite`、`UpdateUserKB`
- 前端：`web/admin/src/pages/setting/component/CardKB.tsx`

当前代码中可以看到知识库后台角色至少覆盖：

- 完全控制
- 文档管理
- 数据操作

这使系统不仅支持单人使用，也支持小团队协作。

#### 4.1.3 版本发布与回溯

版本管理页位于 `web/admin/src/pages/release/index.tsx`。从实现逻辑看，版本发布不仅是“打标签”，而是：

1. 根据待发布节点列表创建 `NodeRelease` 快照。
2. 为每个快照异步投递向量更新任务。
3. 再创建知识库版本记录 `KBRelease`，保存版本号、备注、发布者和发布时间。

因此，“发布”在系统中承担了内容冻结、问答数据切换和公开站点可见版本维护三重职责。

### 4.2 文档树与知识组织管理

文档管理页是后台最复杂、最核心的页面之一，对应 `web/admin/src/pages/document/index.tsx`。

#### 4.2.1 树形目录与文档创建

管理员可以在任意目录节点下执行：

- 创建文件夹
- 创建富文本文档
- 创建 Markdown 文档
- 重命名
- 删除
- 拖拽移动

前端使用树结构组件维护目录层级，后端通过 `backend/handler/v1/node.go` 和 `backend/usecase/node.go` 完成节点创建、更新、移动和删除。

#### 4.2.2 文档发布与重新学习

代码中明确存在以下动作：

- `发布文档`
- `发布更新`
- `重新学习`
- `文档属性`
- `前台查看`

其中“重新学习”对应 `NodeRestudy`，会把节点重新投递到向量处理队列，用于修复索引失效、重新分块或重新写入摘要。“前台查看”用于快速跳转公开文档页，说明后台与公开站点使用同一套内容对象。

#### 4.2.3 批量操作

文档管理页支持批量选择后执行：

- 生成摘要
- 批量移动
- 批量删除
- 批量设置权限

这部分功能对论文很重要，因为它表明系统不是只支持单文档演示，而是具备面向真实知识库整理场景的批量治理能力。

### 4.3 多源知识接入与导入

知识接入能力由前端导入菜单、爬虫接口和文件上传接口共同完成。

#### 4.3.1 支持的导入来源

根据 `web/admin/src/pages/document/index.tsx` 与 `backend/usecase/crawler.go`，当前代码已经支持以下来源：

- 离线文件
- URL 网页
- RSS
- Sitemap
- Notion
- Epub
- Wiki.js
- 语雀
- 思源笔记
- MinDoc
- 飞书文档
- 钉钉文档
- Confluence

这说明系统的“知识接入”不是单纯文件上传，而是面向第三方知识系统迁移的导入平台。

#### 4.3.2 文件上传与内容保存

文件相关接口位于 `backend/handler/v1/file.go`，主要包括：

- `/api/v1/file/upload`
- `/api/v1/file/upload/url`
- `/api/v1/file/upload/anydoc`

后端 `backend/usecase/file.go` 提供从文件流、字节数组、URL 和通用文档通道上传内容的能力。上传后内容会进入对象存储，文档元数据保存到 PostgreSQL，随后再进入发布、向量化和图谱同步流程。

#### 4.3.3 导入处理的统一中间表示

无论内容来自网页、第三方文档平台还是本地文件，最终都会被整理成统一的节点对象 `Node`。这意味着后续模块只需要围绕统一文档对象工作，而无需为每个来源单独实现问答或图谱逻辑。

### 4.4 文档权限治理

权限管理是 PandaWiki 相比普通 demo 更完整的一部分。

#### 4.4.1 三层权限模型

根据 `backend/domain/node.go` 与 `DocPropertiesModal.tsx`，文档存在三组权限维度：

- `answerable`：可被问答
- `visitable`：可被访问
- `visible`：导航内可见

每组权限都支持三种状态：

- 完全开放
- 部分开放
- 完全禁止

这三层权限分别作用于：

- AI 问答可否召回该文档
- 文档详情页可否打开
- 导航目录中可否展示该文档

#### 4.4.2 用户组粒度控制

当权限为“部分开放”时，管理员可以为三类权限分别绑定用户组。后端在 `NodePermissionsEdit` 中除了更新数据库权限信息，还会向向量任务队列发送 `update_group_ids` 请求，把问答权限同步到向量库元数据。

这意味着系统的权限不是只停留在页面隐藏，而是深入到了检索层：

- 用户没有 `answerable` 权限时，文档不会进入召回结果
- 用户没有 `visitable` 权限时，搜索结果会被过滤
- 用户没有 `visible` 权限时，目录树中不会展示该节点

## 6. RAG 问答与知识处理能力

### 6.1 文档向量化链路

向量化链路主要由三部分组成：

1. 业务层投递任务：`KnowledgeBaseUsecase.CreateKBRelease`、`NodeRestudy`
2. MQ 消费者执行：`backend/handler/mq/rag.go`
3. 向量服务存储：`backend/store/rag/ct.go`

当文档发布后，系统会创建节点发布快照，并向消息队列发送 `upsert` 请求。消费者读取快照内容后：

- 读取知识库对应 `dataset_id`
- 获取文档回答权限对应的用户组 ID
- 调用向量服务写入文档内容
- 更新当前快照的 `doc_id`
- 删除旧版本遗留的向量记录

因此，向量层中的对象并不是直接绑定草稿节点，而是绑定“已发布版本”。

### 6.2 文档格式处理

`backend/store/rag/ct.go` 中可以看到，若内容是 HTML，系统会先自动转换成 Markdown，再上传到向量服务。这一设计的价值在于：

- 保留更多语义结构
- 降低富文本噪声
- 让不同来源内容在检索层有更统一的中间表示

### 6.3 权限感知检索

向量查询和写入都带有 `group_ids` 元数据：

- 写入时：根据节点 `answerable` 权限写入用户组 ID
- 查询时：根据当前用户所属组过滤检索结果

这使 RAG 召回本身就是权限感知的，而不是“先召回再人工过滤”。

### 6.4 对话编排

`ChatUsecase.Chat` 与 `LLMUsecase.BuildConversationMessageWithRAG` 共同构成完整的问答链路：

1. 校验应用与模型配置
2. 创建或续接会话，生成 `conversation_id` 和 `nonce`
3. 保存用户消息
4. 执行敏感词检测
5. 解析当前用户所属权限组
6. 从向量库召回证据块
7. 将证据块格式化为提示词上下文
8. 流式调用大模型
9. 实时返回证据块、答案片段和完成事件
10. 保存助手消息与 Token 用量

### 6.5 摘要生成

摘要功能同时服务于：

- 单文档摘要生成
- 批量摘要生成
- 搜索与图谱展示中的摘要字段

`LLMUsecase.SummaryNode` 会先按 token 限制切分长文，再对每块内容生成局部摘要，最后合并为总摘要。这一机制避免长文档一次性送入模型造成成本过高或上下文溢出。

## 7. 知识图谱能力

### 7.1 图谱数据建模

当前已明确落地图谱节点类型至少包括：

- `KnowledgeBase`
- `Folder`
- `Document`
- `User`

同时在数据模型中预留了 `Entity` 扩展位，用于后续实体抽取。

关系类型主要包括：

- `BELONGS_TO`
- `CONTAINS`
- `CREATED_BY`
- 文档间 `RELATED_BY_KEYWORD`

这表明系统当前阶段采取的是“先构建业务对象图，再逐步增加语义实体层”的策略。

### 7.2 文档关系自动构建

文档关系构建由 `graph_tokenizer.go` 与图查询/图存储层共同完成，其核心特点是：

- 对标题给予更高权重
- 提取英文/数字 token
- 对中文文本使用 bi-gram 切分
- 限制最大源文本长度与最大 token 数
- 根据相似度构建 `RELATED_BY_KEYWORD` 关系

在图谱同步中，文档创建和文档更新后会自动重建当前文档的相似关系，因此图谱会随着内容变化动态演进。

### 7.3 图谱同步

图谱同步由 `backend/usecase/graph_sync.go` 实现，已支持的任务类型包括：

- 文档创建、更新、删除、移动
- 文件夹创建、更新、删除、移动
- 用户创建
- 知识库创建

同步逻辑的核心原则是：业务库为主，Neo4j 为增强层。也就是说，图谱是对业务主数据的结构化投影，而不是新的主事实来源。

### 7.4 自动重试与死信恢复

图谱同步具备清晰的补偿机制：

- 最大重试次数：3 次
- 初始退避时间：500ms
- 最大退避时间：4s
- 超限后写入 `graph_sync_dead_letters`

死信记录中会保存：

- 知识库 ID
- 任务类型
- 实体 ID
- 任务载荷
- 错误信息
- 重试次数
- 状态与时间戳

后台图谱页可手动重放死信任务，因此管理员可以直接修复图谱层异常。

### 7.5 图谱查询接口

图谱查询接口位于 `backend/handler/v1/graph.go`，当前已实现：

- 获取全图
- 获取节点局部子图
- 查找路径
- 获取统计信息
- 搜索实体
- 手动构建文档关系
- 重试图谱同步死信

这说明图谱已经不仅是存储层，还被包装成了可被页面和未来问答模块直接调用的服务层。

### 7.6 图谱可视化

图谱管理页 `web/admin/src/pages/graph/index.tsx` 支持：

- 图谱统计概览
- 2D/3D 切换
- 全图加载
- 死信重放
- 图谱刷新与浏览

页面中同时使用了 `GraphCanvas` 和 `Graph3DCanvas`，说明系统已经具备较好的图谱展示能力，适合作为论文中“可解释性界面”的核心截图来源。

### 7.7 图谱初始化迁移

`backend/cmd/migrate/main.go` 提供了从 PostgreSQL 迁移知识库、用户、目录和文档到 Neo4j 的独立工具。这一点非常重要，因为它说明图谱模块考虑了老数据导入和一次性初始化，而不是只支持新文档增量写入。

## 9. 典型业务流程

### 9.1 新建知识库到可问答的闭环

1. 管理员创建知识库。
2. 系统创建向量数据集，并保存知识库主记录。
3. 系统异步在 Neo4j 中创建知识库节点。
4. 管理员导入文档并整理目录结构。
5. 管理员发布文档版本。
6. 系统创建文档发布快照，并异步写入向量库。
7. 图谱同步模块创建文档节点、目录关系和文档相似关系。
8. 前台即可浏览文档，并使用 AI 问答或仅搜索文档功能。

### 9.2 文档权限调整闭环

1. 管理员在文档属性中设置可见、可访问、可问答权限。
2. 后端更新节点权限与关联用户组。
3. 若问答权限发生变化，系统向 MQ 发送 `update_group_ids`。
4. 消费者把新的组信息回写到向量库元数据。
5. 后续用户提问时，检索结果自动受权限约束。

### 9.3 图谱故障恢复闭环

1. 文档或目录变更触发图谱同步。
2. 若 Neo4j 暂时不可用，同步任务自动重试。
3. 超过重试次数后写入死信表。
4. 管理员在图谱页面点击“重放死信”。
5. 系统重新执行失败任务，成功后清理死信状态。
