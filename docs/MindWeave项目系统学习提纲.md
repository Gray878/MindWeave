## 一、先用一句话讲清楚：MindWeave 到底是什么项目

MindWeave 可以理解为一个基于开源 `PandaWiki` 二次开发和工程化整合出来的企业知识库与知识图谱系统。它的核心目标不是单纯做文档管理，而是把“知识接入、知识沉淀、智能检索、智能问答、关系分析、图谱可视化、私有化部署”这些能力串成一个完整闭环。

从仓库结构上看，MindWeave 不是从零平地起的纯新项目，而是由 3 层组成：

- `PandaWiki/`：主代码仓，包含后端、管理后台、前台站点、SDK。
- 根目录部署层：`docker-compose.yml`、`bin/`、`.env`、各种启动和部署脚本，用来把整个系统跑起来。
- `docs/`：你为毕设、知识图谱设计、简历复盘、系统分析写的文档，是项目理解和答辩表达的重要补充材料。

如果你之后要在简历上介绍它，最稳妥的说法不是“我从 0 独立写了一个完整知识库平台”，而是：

- 基于开源知识库系统 `PandaWiki` 进行二次开发和工程化扩展。
- 重点完成知识图谱模块、图谱同步补偿、文档关系构建、图谱可视化和私有化部署整合。

这类表述更真实，也更容易在面试时站得住。

## 二、这个项目想解决什么问题

这个项目要解决的不是“有没有文档系统”，而是“企业内部知识能不能被真正组织、检索、解释和复用”。

典型痛点有 4 类：

### 1. 知识来源分散

企业知识不只存在于一个地方，可能来自：

- 本地文件：PDF、Word、Markdown、HTML
- 外部网页：URL
- 网站内容：Sitemap
- 订阅源：RSS
- 后续还可以扩展到图片、截图、聊天记录等多模态来源

如果接入能力弱，知识库就会变成“少量手工上传文档的地方”，无法覆盖真实业务场景。

### 2. 传统搜索只能找到关键词，找不到语义和关系

全文搜索可以搜到词，但很难处理下面这些需求：

- “这个技术和哪个模块最相关？”
- “这份文档和另外两份文档是什么关系？”
- “某个概念在系统里被哪些文档提到过？”
- “如果我不知道关键词，只知道问题描述，还能不能找出答案？”

这就需要语义检索、知识图谱和问答能力共同工作。

### 3. AI 问答容易“会说但不靠谱”

如果 AI 问答没有企业内部知识做约束，就会出现：

- 回答泛化
- 上下文不稳定
- 难以解释为什么这样回答
- 缺少引用来源和关联文档

MindWeave 希望让问答建立在知识库内容、向量召回、文档关系和图谱上下文之上，而不是完全靠大模型自由发挥。

### 4. 文档之间缺少结构化关系

如果知识永远只是“一堆文档”，那它只能被“浏览”和“搜索”，很难被“分析”和“解释”。

引入知识图谱后，系统可以表达：

- 文档属于哪个知识库
- 文档在哪个目录下
- 文档是谁创建或编辑的
- 文档和文档之间有哪些相似关系
- 未来还可以扩展为文档和实体、实体和实体之间的关系

这就是从“文档集合”走向“知识网络”。

## 三、先从用户视角看功能全貌

如果从“用户实际会看到什么”来理解，这个项目大致有 5 个功能层。

### 1. 管理后台

对应 `PandaWiki/web/admin`，是管理员和内容维护者使用的控制台。它负责：

- 知识库创建、编辑、删除
- 文档目录树管理
- 文档编辑、历史版本、摘要生成、AI 辅助写作
- 文件导入、URL 导入、RSS/Sitemap 抓取
- 模型配置、用户管理、权限配置
- 数据统计、对话记录、反馈管理
- 知识图谱查询与 2D/3D 可视化

从路由看，后台主要页面有：

- `/`：文档管理
- `/setting`：系统设置
- `/contribution`：贡献管理
- `/release`：版本发布
- `/stat`：数据统计
- `/conversation`：对话管理
- `/graph`：知识图谱
- `/feedback/:tab?`：反馈管理
- `/doc/editor/...`：编辑器及历史版本、空间管理

### 2. 前台 Wiki 站点

对应 `PandaWiki/web/app`，是普通访问者真正看到的知识库站点。

它主要提供：

- 知识库首页 / 欢迎页
- 文档目录与文档详情浏览
- 文档锚点导航、目录树、移动端目录
- 搜索和 AI 问答入口
- 评论、反馈、登录等交互

首页不是固定死页面，而是可以按配置动态组合组件。代码里已经支持的首页模块包括：

- banner
- basic_doc
- dir_doc
- simple_doc
- carousel
- faq
- text
- case
- metrics
- feature
- text_img
- img_text
- comment
- block_grid
- question

这说明前台不仅是“文档页”，还能被配置成一个知识门户首页。

### 3. AI 问答和嵌入式 Widget

项目不只有普通网页问答，还提供：

- `widget` 页面：可嵌入别的网站
- `h5-chat` 页面：适合移动端或轻量问答场景
- 搜索模式与问答模式两种交互
- 对话记录和反馈回流后台

这意味着项目具备“站内使用 + 外部嵌入”的双场景能力。

### 4. 公开访问与第三方接入层

后端除了后台私有接口 `api/v1`，还有一套 `share/v1` 公共接口，服务于前台、Widget 和外部集成。它包括：

- 文档详情与列表
- 公共问答 / 搜索
- 评论
- 登录认证
- 统计上报
- 应用信息
- Sitemap

另外还集成了多种外部入口：

- GitHub 登录/回调
- 微信服务号 / 小程序 / 公众号
- 企业微信 AI Bot
- 飞书 Bot

### 5. 运维与部署层

整个系统最终通过 Docker Compose 跑起来，包含：

- 网关
- 后端 API
- 异步 Consumer
- PostgreSQL
- Redis
- MinIO
- NATS
- Qdrant
- RAGLite
- Neo4j
- Crawler

也就是说，这个项目的价值不仅在“写功能”，还在“能交付、能跑、能联调”。

## 四、项目中的核心角色分别是谁

这个项目里主要有 4 类角色，每类角色关心的功能不同。

### 1. 管理员

管理员是系统配置和治理的主角色，典型动作包括：

- 创建知识库
- 配置访问地址、认证方式、发布信息
- 配置 AI 模型
- 管理用户和知识库成员
- 查看统计和问答记录
- 管理图谱、处理死信重放

### 2. 内容维护者

内容维护者关注知识内容本身，典型动作包括：

- 上传文件、导入网页
- 创建目录和文档
- 编辑文档内容
- 生成摘要
- 发布知识库内容
- 调整节点权限

### 3. 普通访客 / 终端用户

普通用户更关心知识消费体验，典型动作包括：

- 浏览首页和目录
- 查看文档详情
- 搜索内容
- 发起 AI 问答
- 提交评论或反馈

### 4. 运维 / 技术人员

运维或技术角色更关注可用性和运行状态，典型动作包括：

- 启动和维护服务
- 查看容器和数据卷
- 处理导入和索引异常
- 重放图谱同步死信
- 调整环境变量和端口映射

## 五、系统的完整业务主流程是怎样跑起来的

把这个项目读懂，最重要的不是先看某个函数，而是先把完整业务链路在脑子里连起来。

### 主流程 1：知识库初始化

1. 管理员登录后台。
2. 创建知识库。
3. 配置访问域名、端口、简单认证或企业认证。
4. 配置 AI 模型。
5. 系统为这个知识库准备前台站点和后续检索、问答能力的上下文。

### 主流程 2：知识接入

1. 管理员选择导入方式：
   - 文件上传
   - URL 导入
   - RSS 导入
   - Sitemap 导入
   - Anydoc / Crawler 解析
2. 原始文件或网页内容被上传到对象存储或交给抓取服务。
3. 文档元数据写入 PostgreSQL。
4. 文档内容进入解析、切片、向量化等 RAG 链路。

### 主流程 3：知识沉淀

1. 文档和文件夹在知识库里形成目录树。
2. 文档内容可在编辑器中查看和修改。
3. 节点可以设置摘要、内容格式、权限状态。
4. 节点可以发布、删除、移动、批量移动、重新学习。

### 主流程 4：检索与问答

1. 用户在前台或 Widget 里输入问题。
2. 系统先做检索召回。
3. 召回结果交给问答链路生成答案。
4. 结果带有对话记录、引用文档、反馈信息等上下文。
5. 问答记录沉淀到后台的会话和消息管理模块。

### 主流程 5：图谱构建与分析

1. 文档、文件夹、用户、知识库等对象被同步到 Neo4j。
2. 系统建立层级、归属、创建者、关联文档等关系。
3. 基于标题与正文 token 相似度自动生成文档关系。
4. 管理员可在 `/graph` 页面查看全图、局部图、路径、统计，并进行 2D/3D 可视化分析。

### 主流程 6：异常恢复

1. 如果图谱同步失败，系统自动重试。
2. 多次失败后，任务写入死信表。
3. 管理员可在图谱页点击“重放死信”。
4. 系统按知识库维度重新执行失败任务，恢复数据一致性。

你可以把这个项目理解为一条连续链路：

```text
知识导入 -> 文档管理 -> 检索增强 -> AI 问答 -> 图谱构建 -> 图谱分析 -> 异常补偿
```

## 六、项目整体架构总览

从系统架构角度看，MindWeave 是一个典型的“多前端 + 后端 API + 异步消费 + 多存储 + AI 服务”的组合系统。

可以用下面这张图理解：

```text
                 ┌────────────────────────────┐
                 │        管理后台 Admin       │
                 │ React + Vite + MUI         │
                 └─────────────┬──────────────┘
                               │
                               │
                 ┌─────────────▼──────────────┐
                 │         Nginx / Caddy       │
                 └─────────────┬──────────────┘
                               │
         ┌─────────────────────▼─────────────────────┐
         │             Echo API 服务                  │
         │ api/v1 + share/v1 + middleware + auth     │
         └───────┬──────────┬──────────┬────────────┘
                 │          │          │
                 │          │          │
      ┌──────────▼───┐  ┌───▼──────┐  ┌──────────────▼─────────────┐
      │ PostgreSQL   │  │ Redis    │  │ MinIO / 文件对象存储        │
      │ 主业务数据    │  │ 会话缓存  │  │ 上传文件/中间资源           │
      └──────────────┘  └──────────┘  └────────────────────────────┘
                 │
                 │
      ┌──────────▼─────────┐
      │ NATS / Consumer    │
      │ 异步解耦与消费任务   │
      └──────────┬─────────┘
                 │
      ┌──────────▼─────────┐
      │ RAGLite + Qdrant   │
      │ 切片、向量化、语义召回│
      └────────────────────┘

      ┌────────────────────┐
      │ Neo4j              │
      │ 图谱节点、关系、路径 │
      └────────────────────┘

      ┌────────────────────┐
      │ Crawler / Anydoc   │
      │ URL / RSS / Sitemap│
      └────────────────────┘

                 ┌────────────────────────────┐
                 │ 前台 Wiki / Widget / H5 Chat │
                 │ Next.js + share/v1 接口       │
                 └────────────────────────────┘
```

这个架构说明了 3 件事：

### 1. 前后端完全分离

- 管理后台是 `React + Vite`
- 前台站点是 `Next.js`
- API 服务是 `Go + Echo`

### 2. AI 能力不是单点功能，而是系统级能力

AI 问答依赖的不只是大模型，还依赖：

- 文档内容
- 向量召回
- 对话记录
- 模型配置
- 反馈闭环
- 图谱扩展能力

### 3. 图谱不是单独的实验功能，而是嵌入在主业务链路里

图谱数据不是手工导入，而是跟随知识库、文档、文件夹、用户生命周期自动同步。

## 七、技术栈与基础设施组成

这一节不要只记技术名，要记住“每个技术在系统里做什么”。

### 1. 后端技术栈

- `Go`：后端主语言，负责业务逻辑、接口、数据协同。
- `Echo`：HTTP 框架，负责路由、中间件和请求处理。
- `GORM`：面向 PostgreSQL 的数据访问。
- `Viper`：配置管理。
- `JWT` / 会话中间件：鉴权与登录态。
- `Google Wire`：依赖注入，见 `backend/cmd/api/wire.go`、`backend/cmd/consumer/wire.go`。

### 2. 前端技术栈

管理后台：

- `React 18`
- `TypeScript`
- `Vite`
- `MUI`
- `Redux Toolkit`

前台站点：

- `Next.js 15`
- `React 19`
- `Material UI`
- `Tiptap / Markdown 渲染`

### 3. 图谱与可视化技术

- `Neo4j`：图数据库
- `Graphology`：图数据结构封装
- `Sigma.js`：2D 图谱渲染
- `ForceAtlas2` + `noverlap`：2D 图布局优化
- `react-force-graph-3d`：3D 图谱渲染
- `Three.js`：3D 场景、粒子、球形视图、相机控制

### 4. 数据与中间件

- `PostgreSQL`：主业务数据库
- `Redis`：缓存、会话
- `MinIO`：对象存储
- `NATS`：异步消息总线
- `Qdrant`：向量数据库
- `RAGLite`：RAG 相关处理服务
- `Neo4j`：图数据库
- `Crawler/Anydoc`：网页/文档抓取与解析

### 5. 可观测性与运维

- `Docker Compose`：多服务编排
- `Nginx` / `Caddy`：网关和流量入口
- `Sentry`：错误上报
- `OpenTelemetry`：APM / tracing

### 6. 启动入口

系统运行时有两个主要 Go 入口：

- `backend/cmd/api/main.go`：启动 HTTP API 服务
- `backend/cmd/consumer/main.go`：启动消息消费服务

HTTP 服务由 `backend/server/http/http.go` 负责初始化 `Echo`，其中包括：

- 自定义 Binder
- 请求校验器
- 请求日志
- Session 中间件
- 只读模式中间件
- Sentry
- OpenTelemetry

这说明后端并不是“只写几个 Handler”，而是有较完整的工程化基础设施。

## 八、多存储分层为什么这样设计

很多初学者看到这个项目会有一个问题：为什么要同时用这么多存储组件？

答案是：因为它们解决的是完全不同的问题。

### 1. PostgreSQL：系统的主数据事实来源

PostgreSQL 里保存的主要是业务本体，例如：

- 知识库
- 文档和文件夹节点
- 节点版本与发布记录
- 用户和成员关系
- 对话和消息
- 评论、反馈、统计
- 配置数据
- 图谱同步死信

它是“业务真相”的主要来源。

### 2. Redis：高频状态和会话层

Redis 在这个系统里不承担主数据，而是承担：

- 登录态
- 会话缓存
- 热点数据缓存

它解决的是“高频、低延迟访问”的问题。

### 3. MinIO：文件对象存储

文档系统不只是结构化数据，还有大量原始文件和中间资源，需要对象存储。MinIO 负责：

- 上传文件
- 导入原始资源
- 文档附件
- 抓取中间结果

这类数据不适合直接塞进关系数据库。

### 4. NATS：异步解耦

如果所有事情都在主请求里同步完成，会导致：

- 导入慢
- 写操作阻塞
- 系统容易脆弱

NATS 的价值在于把异步任务解耦出来，让系统可以：

- 分发任务
- 做后台消费
- 降低主链路延迟

### 5. Qdrant：语义检索

AI 问答不只是读原文档，还要把文档切片、向量化并做语义召回。Qdrant 的职责是：

- 存储 chunk 向量
- 提供相似度检索
- 为 RAG 问答返回候选内容

### 6. Neo4j：知识关系表达

Neo4j 不是为了代替 PostgreSQL，而是为了做 PostgreSQL 不擅长的事：

- 路径查询
- 多跳关系分析
- 图结构遍历
- 文档相似关系展示

### 7. RAGLite：检索增强服务

它承担的是 AI 检索链路中的“加工厂”角色，例如：

- 文档切片
- 向量化
- 与 Qdrant 协作
- 为问答提供召回结果

### 8. 这样设计的本质

这套架构的核心思想是：不同类型的数据和查询模式，应该交给不同组件处理。

如果全部都堆到 PostgreSQL 里，系统虽然“组件更少”，但会同时在这些方面吃亏：

- 文件存储不优雅
- 语义检索性能差
- 图谱查询很别扭
- 异步链路难扩展

所以，多存储不是“炫技术”，而是这个项目落地的必要条件。

### 9. 技术选型补充：这些组件到底是什么，为什么选它们

如果你刚开始学项目，看到下面这串名字很容易发懵：

- PostgreSQL
- Redis
- MinIO
- NATS
- Qdrant
- RAGLite
- Neo4j
- Crawler

你可以先把它们理解成 8 个不同岗位的人：

- PostgreSQL：管业务事实。
- Redis：管高频状态和会话。
- MinIO：管文件。
- NATS：管异步消息和任务派发。
- Qdrant：管向量检索。
- RAGLite：管 RAG 流程编排。
- Neo4j：管关系网络。
- Crawler/Anydoc：管抓取和解析外部内容。

先记住一句最重要的话：  
这些技术不是“越多越高级”，而是“每个组件都在解决一种 PostgreSQL 不适合单独解决的问题”。

下面逐个讲。

#### 1. PostgreSQL 是什么，为什么这里用它

一句话理解：  
PostgreSQL 是关系型数据库，最擅长存放系统里的“业务真相”。

在这个项目里，它主要保存：

- 知识库、文档、文件夹、发布版本
- 用户、权限、成员关系
- 对话、消息、反馈、评论
- 配置、统计、死信补偿记录

也就是说，只要某条数据属于“系统最终以它为准”的事实数据，通常就应该在 PostgreSQL 里。

为什么选它：

- 业务数据关系复杂，关系型数据库比纯 KV 或文档数据库更合适。
- 事务能力强，适合文档发布、对话记录、权限变更这类一致性要求高的场景。
- 这个项目的后端是 Go + GORM，和 PostgreSQL 的集成已经很成熟。
- `docker-compose.yml` 里直接以独立服务部署，说明它就是整套系统的主数据库。

为什么不是 MySQL：

- 不是说 MySQL 不能做，而是 PostgreSQL 更常被拿来承载结构复杂、约束较强、扩展性要求更高的业务系统。
- 这个项目里后面还挂了 RAGLite、自定义迁移、图谱同步、较多后台治理能力，PostgreSQL 作为主库会更自然。
- Compose 里甚至用了带 `zhparser` 的 PostgreSQL 镜像，说明项目对中文文本处理生态也有考虑。

为什么不把文件、向量、图谱全放进 PostgreSQL：

- 文件放数据库会让主库膨胀，备份恢复也会变重。
- 向量检索和业务查询混在一起，会让主库既做 OLTP 又做语义召回，职责很乱。
- 图谱路径查询也不是关系库最擅长的表达方式。

所以你可以把 PostgreSQL 理解成：  
“整个系统的主账本”，但不是“什么都往里塞的大仓库”。

#### 2. Redis 是什么，为什么这里用它

一句话理解：  
Redis 是一个以内存为主的高性能 KV 存储，擅长做缓存、会话和短期状态。

在这个项目里，Redis 主要负责：

- 登录态和 Session
- 高频访问缓存
- 一些短生命周期状态
- 分布式去重或幂等控制

代码里可以直接看到：

- Session 中间件用了 `redistore`
- 企业微信 Bot 场景里用到了 `SetNX` 和过期时间来做去重与会话关联

为什么选它：

- 它对“高频读写、低延迟、可过期”的数据非常合适。
- 这类数据不应该落到主库里，否则 PostgreSQL 会被大量短期状态拖累。
- `docker-compose.yml` 里开了 AOF 和快照，说明它不是纯临时缓存，而是带一定持久化能力的运行态存储。

为什么不是 Memcached 或本地内存：

- Memcached 更偏简单缓存，能力比 Redis 窄，不适合 Session、锁、过期控制这类场景。
- 本地内存缓存只适合单实例；一旦多实例部署，就很难共享登录态和去重状态。

所以 Redis 在这里不是“另一个数据库”，而是：  
“高频、短期、需要快速访问的运行时状态层”。

#### 3. MinIO 是什么，为什么这里用它

一句话理解：  
MinIO 是一个兼容 S3 协议的对象存储服务，可以把它理解成“自己部署的云存储”。

在这个项目里，它主要存：

- 用户上传文件
- 文档附件
- 抓取与解析中间产物
- 图片和静态资源

代码里很多地方都直接走了 MinIO 客户端上传文件，前台还能通过 `/static-file/...` 访问这些资源。

为什么选它：

- 文档系统天然会有很多二进制文件、附件、图片，这些数据不适合存在 PostgreSQL。
- MinIO 是 S3 兼容的，自建部署方便，不会被某一家云厂商绑定。
- 对本地开发、Docker Compose 一体化部署非常友好。

为什么不是“把文件直接存在服务器目录里”：

- 本地目录方式在单机 demo 时简单，但一旦要迁移、备份、横向扩展、统一访问控制，就会变得很麻烦。
- 对象存储更适合通过统一 API 管理文件。

为什么不是直接用阿里云 OSS、腾讯云 COS：

- 如果这是面向学校、实验室、私有化交付或离线部署的项目，自建 MinIO 更灵活。
- 同时又保留了 S3 协议兼容性，后续要切云厂商也更容易。

所以 MinIO 在这里承担的是：  
“文件仓库”的角色，而不是普通数据库表。

#### 4. NATS 是什么，为什么这里用它，而不是 RabbitMQ 或 Kafka

一句话理解：  
NATS 是轻量级消息总线，用来做异步通信、任务派发和事件通知。

在这个项目里，它不是摆设，代码里真的在用：

- `backend/mq/nats/producer.go` 会创建 stream
- `backend/mq/nats/consumer.go` 会注册消费者
- `domain/mq.go` 里定义了实际主题，如向量任务、Anydoc 导出事件、RAG 文档更新事件

而且这里不是只用了一种模式：

- 对 `anydoc.persistence.doc.task.export` 用的是 Core NATS 订阅
- 对内部任务主题则用了 JetStream，带持久化、显式 ACK、Durable Consumer

这说明项目对 NATS 的使用是“够用且有针对性”的，不是只拿它当普通发布订阅。

为什么选 NATS：

- 这个项目的异步任务类型很多，但吞吐规模看起来还没有大到必须上 Kafka 的程度。
- 项目更需要“部署轻、接入简单、延迟低、和现有服务配合自然”的消息系统。
- RAGLite 和 Crawler 在 Compose 里也都直接依赖 NATS，说明整条链路已经围绕它打通。
- JetStream 已经能提供当前项目需要的持久化、ACK、Durable Consumer 等能力。

为什么不是 RabbitMQ：

- RabbitMQ 很强，尤其擅长复杂路由、Exchange/Queue 绑定、死信队列等传统企业消息场景。
- 但这个项目当前更像“任务事件驱动 + 服务间通知”，而不是复杂的消息路由编排。
- 如果只是为了向量任务、抓取完成通知、RAG 更新事件，引入 RabbitMQ 的交换机模型不一定更划算。

为什么不是 Kafka：

- Kafka 更适合超大吞吐、日志流、事件回放、数据管道、实时分析这类场景。
- 但 Kafka 的部署、运维、心智成本都比 NATS 重。
- 对当前这个以知识库、导入、问答、图谱为主的应用来说，Kafka 的很多能力用不上，反而会增加系统复杂度。

所以这里选 NATS 的核心原因不是“它绝对最好”，而是：  
“它在当前项目规模下足够可靠，接入成本低，和现有 RAG/Crawler 链路贴合度高，比 RabbitMQ 和 Kafka 更轻、更顺手。”

#### 5. Qdrant 是什么，为什么这里用它

一句话理解：  
Qdrant 是向量数据库，专门用来存 embedding 并做相似度召回。

在这个项目里，它的职责很纯粹：

- 保存文档 chunk 的向量
- 按问题做语义相似检索
- 给 RAG 问答返回候选文档片段

所以当用户提问“图谱同步失败怎么办”时，系统不是只靠关键词搜“失败”这两个字，而是可以在语义空间里找相关文档片段。

为什么选它：

- 这是一个很典型的 RAG 场景，向量检索是第一公民。
- Qdrant 是专用向量数据库，元数据过滤、相似度搜索这些能力都很直接。
- Compose 部署也比较轻，适合知识库类项目做私有化一体交付。

为什么不是 `pgvector`：

- `pgvector` 的优点是少一个组件，直接复用 PostgreSQL。
- 但这会让主库同时承担业务 OLTP 和向量检索职责，边界会变差。
- 当文档量、chunk 数、检索频率上来以后，专用向量库会更清晰。

为什么不是 Elasticsearch：

- Elasticsearch 更强在倒排索引、全文检索、聚合分析。
- 它也能做向量检索，但如果项目主诉求是 RAG 语义召回，Qdrant 这种专用向量库会更直接。

为什么不是更重的 Milvus / Weaviate：

- 它们也很能打，但通常部署和理解成本更高。
- 对这种 Docker Compose 就能跑起来的知识库项目来说，Qdrant 更符合“够用、清晰、好部署”的风格。

所以 Qdrant 是：  
“专门给 RAG 服务的语义召回引擎”，不是通用业务数据库。

#### 6. RAGLite 是什么，为什么这里单独放一个服务

一句话理解：  
RAGLite 不是数据库，而是一个“RAG 流程服务层”。

从 `docker-compose.yml` 和 `backend/store/rag/ct.go` 能看出来，它承担了这些事：

- 创建数据集
- 上传文档
- 文档切片
- 向量化
- 检索召回
- 模型配置同步
- 通过 NATS 回传文档状态更新

也就是说，它并不是简单帮你“查一下 Qdrant”，而是把 RAG 链路里很多重复劳动封装掉了。

为什么选它：

- 如果后端自己直接对接 Qdrant，那么文档切片、embedding、模型配置、文档状态、上传和删除生命周期，都得自己维护。
- RAGLite 把这些通用能力抽成了一个独立服务，后端只需要按数据集、文档、检索请求去调用。
- 这让主业务代码能更聚焦在知识库和问答逻辑，而不是深陷 RAG 基础设施细节。

为什么不是“自己手搓一套 RAG 管线”：

- 可以做，但代码量和运维复杂度都会明显上升。
- 你不仅要管理 Qdrant，还要管理切片规则、模型配置、重建索引、文档状态回调等一堆细节。

为什么不是只用 LangChain / LlamaIndex 这类框架：

- 这些更像应用开发框架或编排库，本质上还是要你自己组织存储和服务边界。
- 当前项目明显更偏“可部署的产品系统”，所以单独放一个 RAG 服务层更适合。

所以 RAGLite 在这里的作用可以理解成：  
“把 RAG 基础设施从主业务代码里剥离出去，让主系统通过接口来使用它。”

#### 7. Neo4j 是什么，为什么这里用它

一句话理解：  
Neo4j 是图数据库，专门用来表达“点和边”的关系网络。

在这个项目里，Neo4j 主要承载：

- 文档节点
- 文件夹节点
- 知识库节点
- 用户节点
- 节点之间的层级、归属、创建、相似等关系

因此它适合做：

- 全图展示
- 单节点关系图
- 多跳关系查询
- 最短路径或路径搜索
- 文档相似关系可视化

为什么选它：

- 这个项目不是只想做“文档能搜”，还想把文档之间的关系组织成图。
- 图数据库对路径查询、多跳遍历、关系可视化更自然。
- 代码里已经有完整的 `graph_sync.go`、`graph_query.go` 和 `store/neo4j/*`，说明它不是边角料，而是明确的架构组成部分。

为什么不是继续用 PostgreSQL：

- PostgreSQL 可以存关系，但写多跳遍历、路径查询、图统计会越来越别扭。
- 你当然能用递归 SQL 硬做，但可读性、维护性和前端图查询接口的表达都会变差。

为什么不是更重的图数据库方案：

- 当前项目规模和部署方式更偏单体产品 + 多辅助服务，不像超大规模图计算平台。
- Neo4j 社区版已经足够承担当前项目的知识关系表达需求。

所以 Neo4j 的价值不是“代替主库”，而是：  
“把关系结构从表关系里解放出来，变成可以查询、可视化、可分析的图网络。”

#### 8. Crawler / Anydoc 是什么，为什么单独做成服务

一句话理解：  
Crawler/Anydoc 是“外部内容接入和解析服务”，不只是简单爬虫。

从代码里可以看到它支持的来源不止一种：

- URL
- Sitemap
- RSS
- Notion
- Confluence
- Feishu
- Yuque
- Wiki.js
- Mindoc
- 思源
- EPUB 等文档导出

所以它做的事情包括：

- 抓取网页或第三方平台内容
- 把内容导出成系统可消费的结构
- 通过消息队列回传导出结果
- 和 MinIO、NATS 协作完成导入链路

为什么要单独拆成服务：

- 外部抓取和文档解析天然不稳定，依赖多、耗时长、失败率也更高。
- 如果把这部分都塞进主 API，主服务会变重，也更容易被外部平台问题拖垮。
- 单独拆服务后，可以独立扩容、独立排障、独立重试。

为什么不是直接在后端里写几个爬虫函数：

- 这类解析逻辑通常会越来越多，而且和主业务的边界并不一致。
- 当前项目已经不是“抓一个网页就结束”，而是要适配多来源知识接入。

为什么不是直接用 Scrapy：

- Scrapy 更偏通用网页抓取框架。
- 但这个项目需要的不只是“爬 HTML 页面”，还包括知识平台导出、文档解析、和消息链路联动。
- 所以这里的 Crawler/Anydoc 更像“知识接入适配层”，范围比传统爬虫更广。

所以你可以把它理解成：  
“系统的内容入口工厂”，专门负责把外部世界的内容转成内部知识库能接收的格式。

#### 9. 怎么判断这些选型是不是合理

技术选型没有绝对标准答案，但你可以用下面 4 个问题来判断它们是否合理：

1. 这个组件是不是在解决一个明确问题，而不是为了凑技术栈？
2. 它的复杂度是不是和当前项目规模匹配？
3. 它有没有和其他组件形成清晰边界？
4. 如果换成别的技术，是真的更简单，还是只是“你更熟”？

对这个项目来说，当前答案大体是合理的：

- PostgreSQL 管业务事实
- Redis 管运行态状态
- MinIO 管文件
- NATS 管异步事件
- Qdrant + RAGLite 管语义检索
- Neo4j 管关系网络
- Crawler 管外部知识接入

这就是一套比较典型的“知识库 + RAG + 图谱 + 导入平台”型系统架构。

## 九、核心数据对象有哪些

理解项目最好的方式之一，是先把核心对象记清楚。

### 1. KnowledgeBase：知识库

对应 `backend/domain/knowledge_base.go`。

它是整个系统的顶层业务容器，主要包含：

- `id`
- `name`
- `dataset_id`
- `access_settings`

其中 `access_settings` 很重要，里面包括：

- `ports`
- `ssl_ports`
- `hosts`
- `base_url`
- `simple_auth`
- `enterprise_auth`
- `source_type`
- `is_forbidden`

这说明知识库不仅是一个逻辑容器，还携带发布访问和认证配置。

### 2. Node：节点

对应 `backend/domain/node.go`。

系统里最核心的业务对象其实不是“文档表”和“目录表”分开，而是统一抽象为 `Node`，通过 `type` 区分：

- `NodeTypeFolder = 1`
- `NodeTypeDocument = 2`

`Node` 里包含很多关键字段：

- `kb_id`
- `type`
- `status`
- `rag_info`
- `name`
- `content`
- `meta`
- `parent_id`
- `position`
- `creator_id`
- `editor_id`
- `permissions`

### 3. 节点状态和权限

节点状态：

- `NodeStatusUnreleased = 0`：未发布
- `NodeStatusDraft = 1`：修改后未重新发布
- `NodeStatusReleased = 2`：已发布

RAG 状态：

- `PENDING`
- `RUNNING`
- `FAILED`
- `SUCCEEDED`
- `REINDEX`

节点权限由 `NodePermissions` 描述，包含 3 个维度：

- `visible`：导航内可见
- `visitable`：可被访问
- `answerable`：可被问答

每个维度又可以是：

- `open`
- `partial`
- `closed`

这意味着项目不只是“能不能看文档”，而是把“显示、访问、问答”三个权限面拆开了。

### 4. NodeMeta：节点元信息

包含：

- `summary`
- `emoji`
- `content_type`

`content_type` 目前主要有：

- `md`
- `html`

这说明编辑器和前台预览同时支持 Markdown 和富文本。

### 5. NodeRelease / KBRelease：发布模型

系统不是简单地直接对外暴露草稿文档，而是有发布概念：

- `NodeRelease`：节点发布快照
- `KBRelease`：知识库发布记录

这让系统可以支持：

- 发布标签
- 发布说明
- 发布人
- 历史版本追踪

### 6. Conversation / ConversationMessage：对话模型

对应 `backend/domain/conversation.go`。

会话对象包括：

- `Conversation`
- `ConversationMessage`
- `ConversationReference`
- `FeedBackInfo`

消息对象里还保存了：

- `role`
- `content`
- `image_paths`
- `provider`
- `model`
- `prompt_tokens`
- `completion_tokens`
- `total_tokens`
- `parent_id`
- 反馈信息

这说明系统对对话链路的记录是比较完整的，不只是保存一句问题和一句回答。

### 7. 图谱模型

对应 `backend/domain/graph.go`。

主要图谱对象有：

- `GraphDocument`
- `GraphFolder`
- `GraphUser`
- `GraphKnowledgeBase`
- `GraphEntity`

关系类型包括：

- `CONTAINS`
- `MENTIONS`
- `RELATES_TO`
- `CREATED_BY`
- `EDITED_BY`
- `BELONGS_TO`
- `REFERENCES`

但这里要注意：

> 领域模型里预留了 `Entity`、`MENTIONS`、`RELATES_TO` 等类型，说明系统已经为实体层做了设计；但根据中期验收文档，实体自动抽取和图谱问答闭环目前仍处于“预留/待完善”阶段，当前落地最完整的是文档、文件夹、知识库、用户与文档相似关系这一层。

### 8. GraphSyncDeadLetter：图谱同步死信

对应 `backend/domain/graph_sync_dead_letter.go`。

它记录的是那些“重试后仍失败”的图谱同步任务，字段包括：

- `kb_id`
- `task_type`
- `entity_id`
- `payload`
- `error_message`
- `retry_count`
- `last_retry_at`
- `resolved_at`
- `status`

这个对象是后面稳定性机制的关键。

## 十、功能模块拆解：知识库与内容管理

这是整个系统最基础的一层，没有它，后面的 AI 和图谱都没有业务依托。

### 1. 知识库管理

对应后端：

- `backend/handler/v1/knowledge_base.go`
- `backend/domain/knowledge_base.go`

对应前端：

- `web/admin/src/request/KnowledgeBase.ts`
- `web/admin/src/pages/setting`

核心功能包括：

- 创建知识库
- 获取知识库列表
- 获取知识库详情
- 修改知识库信息
- 删除知识库
- 查询当前用户对知识库的权限
- 管理知识库成员

## 十一、功能模块拆解：多源文档导入

这部分决定了系统是不是“真正可用的知识库”，因为真实知识一定来自多种来源。

- 进入解析链路
- 生成节点和内容

根据现有文档，已支持的典型文件类型包括：

- PDF
- Word
- Markdown
- HTML

### 2. URL 导入

后端接口：

- `POST /api/v1/file/upload/url`

作用是把网页内容直接导入知识库。

### 3. Crawler / Sitemap / RSS 导入

后端接口：

- `POST /api/v1/crawler/parse`

- `GET /api/v1/crawler/result`
- `POST /api/v1/crawler/results`

这套接口说明导入过程不是“一次请求立刻完成”，而是一个可追踪、可批量、可查看结果的流程。

它可以处理：

- URL 页面抓取
- RSS 订阅源
- Sitemap 网站导入

### 4. 导入的真实链路

从部署和组件关系看，导入并不是简单落一条数据库记录，而是会经历：

1. 文件或网页内容进入 API。
2. 文件可能进入 MinIO。
3. Crawler / Anydoc 负责抓取或解析。

5. 文档内容进入 RAGLite / Qdrant 链路。
6. 节点被纳入知识库树。
7. 图谱同步链路在合适时机写入 Neo4j。

从节点模型和前端组件看，导入后还涉及：

- RAG 处理状态跟踪
- 失败重试
- 重新学习 / 重新索引
- 摘要生成
- 节点状态更新

这意味着“导入”不是一个瞬时动作，而是系统级加工流程的开始。

### 6. 为什么这部分重要

如果一个知识库系统只能手工创建文档，它更像 CMS。  
如果它可以把企业现有知识内容自动接进来，它才更像企业知识平台。

### 8. RAG 问答链路详解

如果你想真正把这个项目的 AI 能力讲清楚，就不能只说“用户提问之后做一次向量检索，再把结果喂给大模型”。  
这个项目里实际落地的是一条完整的 RAG 工程链路，它至少包含“入口接入、会话管理、权限过滤、历史上下文重建、检索、Prompt 组装、流式生成、结果落库、反馈闭环”这些环节。

可以按下面 9 步理解。

1. 第一步：前台入口接入和参数校验

所有公开问答入口主要都在：

- `backend/handler/share/chat.go`

这里至少有 3 类真正参与问答的入口：

- `POST /share/v1/chat/message`：普通网页问答。
- `POST /share/v1/chat/widget`：嵌入式 Widget 问答。
- `POST /share/v1/chat/completions`：兼容 OpenAI 风格的对话接口。

虽然入口不同，但最后都会汇聚到同一条核心 usecase：

- `chatUsecase.Chat(...)`

在进入 usecase 之前，Handler 层会先做一轮“问答前置治理”：

- 从请求头读取 `X-KB-ID`，确定当前是在对哪个知识库提问。
- 检查验证码、Widget 是否开启、API 密钥是否正确等访问控制条件。
- 校验上传图片路径是否合法，限制只能引用站内 `static-file` 资源。
- 解析客户端传入的 `conversation_id`、`nonce`、`app_type`、`message`、`image_paths` 等字段。

这一步的意义是：RAG 不是裸调模型，而是先把“谁能问、问哪个库、在哪个终端问、是否带图、是否有合法会话”这些上下文先收齐。

2. 第二步：建立或恢复会话

进入 `ChatUsecase.Chat` 之后，系统首先不会马上去检索，而是先处理会话。

它会做几件事：

- 根据 `KBID + AppType` 找到当前知识库对应的应用配置。
- 根据应用配置找到应该使用的聊天模型。
- 如果前端没有传 `conversation_id`，就新建一个对话，并生成新的 `nonce`。
- 如果前端传了 `conversation_id`，就会校验 `nonce`，避免别人伪造会话继续写入。
- 为本次用户消息和助手消息分别生成独立的消息 ID。

同时，后端会立刻通过 SSE 先把这些关键标识回传给前端：

- `conversation_id`
- `nonce`
- `message_id`

这一步非常重要，因为前端后续的流式消息拼接、继续追问、点赞点踩、会话恢复，都依赖这些 ID。

3. 第三步：先把“用户问题”落库，再进入 AI 链路

系统会先把用户消息写进 `ConversationMessage`，记录的信息包括：

- 消息角色是 `user`
- 文本问题内容
- 图片路径
- 客户端 IP
- 所属会话 ID

这意味着项目的设计不是“模型答完再统一保存”，而是“用户发问这一刻就形成可追踪事实”。  
这样做的好处是：

- 即使后面的检索或模型生成失败，也能知道用户问了什么。
- 可以做问答失败分析。
- 可以做真实使用行为统计。
- 可以支持多轮对话上下文回放。

4. 第四步：输入侧风控和权限信息注入

在真正检索之前，系统还会补两类非常关键的信息。

第一类是输入内容治理：

- 后端会加载屏蔽词表。
- 如果命中敏感词，直接返回预设的拦截回答，不继续进入 RAG 和模型生成。
- 被拦截后的助手回复也会正常落库，保证审计链路完整。

第二类是访问权限：

- 系统会识别当前认证用户。
- 进一步拿到这个用户所属的权限组 `group_ids`。

后面做 RAG 检索时，这些 `group_ids` 会直接作为检索过滤条件传给向量检索层。  
也就是说，这个项目不是“先搜出来再在页面上藏掉”，而是在检索阶段就尽量限制用户只能命中自己可访问的知识。

5. 第五步：重建多轮对话上下文

真正的 RAG 组装发生在：

- `backend/usecase/llm.go`
- `BuildConversationMessageWithRAG(...)`

这个函数会先把当前会话的历史消息全部取出来，再转成大模型可消费的消息结构。

这里有几个细节很值得你记住：

- 历史消息不是只取最后一轮，而是完整拉取当前会话上下文。
- 用户消息如果带图片，会先被转换成适合模型理解的 Markdown 形式。
- 系统提示词来源不是写死的，而是按优先级选择：
- 请求里显式传入的 Prompt
- 知识库自己的 Prompt 配置
- 系统默认 Prompt

默认 Prompt 的要求很明确：回答必须依据文档内容，正文中需要带引用标记，最后还要给出引用来源列表。  
这说明这个项目不是把模型当“自由发挥的聊天机器人”，而是要求它成为“有出处的知识库回答器”。

6. 第六步：执行检索，得到“改写后的问题 + 命中文档片段”

`BuildConversationMessageWithRAG` 内部会继续调用：

- `GetRankNodes(...)`

而 `GetRankNodes(...)` 又会继续下钻到：

- `rag.QueryRecords(...)`
- `CTRAG.QueryRecords(...)`

再往下，真正执行检索的是 RAGLite 的 `Search.Retrieve(...)`。

这一层会使用下面这些参数：

- `DatasetID`：来自当前知识库绑定的 RAG 数据集。
- `Query`：用户当前问题。
- `GroupIDs`：当前用户所属权限组。
- `SimilarityThreshold`：当前代码里是 `0.2`。
- `HistoryMsgs`：历史消息，用来支持多轮问答场景下的问题改写和语义补全。
- `MaxChunksPerDoc`：限制单文档返回块数。
- `TopK`：当前实现里默认取前 10 个候选块。

这一层返回的不只是“命中的 chunk”，还会返回一个 `rewrittenQuery`。  
这说明检索不是简单拿原始用户输入直接做 embedding 搜索，而是允许检索系统结合上下文对问题进行改写。

这对多轮对话很关键。  
比如用户上一轮问的是“知识图谱怎么同步”，下一轮只说“失败了怎么办”，系统就可以把第二轮问题重写成更完整、更可检索的表达，而不是机械地搜“失败了怎么办”。

7. 第七步：把检索结果重新组织成模型真正可用的知识上下文

向量检索层返回的只是分散的 chunk，业务层还需要再做一次重组。

系统会：

- 根据检索返回的 `DocID` 去数据库里查对应文档发布版本。
- 把这些 chunk 按文档分组，构造成 `RankedNodeChunks`。
- 补齐文档标题、路径、节点摘要、节点路径名等业务字段。
- 把文档内容格式化成 `<document>` 结构，统一拼进 Prompt。

格式化后的文档块里通常会包含：

- 文档 ID
- 文档标题
- 文档 URL
- 文档正文片段

如果文档片段里还有站内 `/static-file/...` 资源，系统还会结合知识库的 `BaseURL` 把它补成绝对地址，避免模型拿到无意义的相对路径。

同时，后端还会把这些命中的文档块通过 SSE 以 `chunk_result` 事件实时发给前端。  
也就是说，前端不仅能看到“最后答案”，还可以先看到“这次回答参考了哪些资料”。

这是非常典型的工程化特征：RAG 检索结果不是只在后端偷偷使用，而是被显式暴露出来，提高可解释性。

这里要特别注意一个边界：  
当前这条主问答链路真正送进模型上下文的“知识证据”，主要还是 RAG 数据集中的文档 chunk，而不是 Neo4j 图数据库即时查询出来的关系结果。  
所以现阶段最成熟、最稳定的是“文档型 RAG 问答”，而“图谱增强问答”仍属于正在持续补强的能力。

8. 第八步：组装最终 Prompt，并流式调用大模型生成答案

完成检索之后，系统会把最终发给模型的消息组织成大致这样的结构：

- 第一条是 system message：告诉模型应该如何基于文档回答、如何引用来源。
- 中间是历史对话消息：保留多轮上下文。
- 最后一条是当前用户问题模板：里面包含当前日期、改写后的问题、以及检索到的文档块。

这意味着项目采用的不是“把文档直接贴到 system prompt 里”的粗糙方式，而是把：

- 系统规则
- 历史语境
- 当前问题
- 检索证据

分层组织后再送给模型。

真正生成答案时，调用的是：

- `ChatWithAgent(...)`

模型返回是流式的，后端每拿到一个 chunk，就通过回调往前端推送 `data` 事件。  
因此用户在页面上看到的是逐字生成的回答，而不是整段等待完成后一次性返回。

另外，这一层还做了两件很工程化的小事：

- 输出内容也会经过敏感词过滤，避免模型生成违规文本。
- 如果接的是带“思维链/推理内容”输出格式的模型，代码里还兼容了对应的流式片段处理。

9. 第九步：答案落库、引用抽取、用量统计、用户反馈闭环

当模型回答完成后，系统不会只做一个 `done` 就结束，还会继续做后处理：

- 把助手回复以 `assistant` 角色写入 `ConversationMessage`。
- 记录本次使用的模型名、Provider、token 消耗。
- 建立和上一条用户消息之间的父子关系。
- 更新模型调用统计和使用量信息。
- 在会话明细层抽取引用块，便于后续展示来源。

前端后续还可以通过：

- `POST /share/v1/chat/feedback`

对这条回答进行点赞点踩或反馈。  
这样，问答链路就从“用户提问”一直闭环到了“结果评价”。

如果从前端实际接收到的 SSE 事件顺序来理解，这条链路大致会经历：

- `conversation_id`
- `nonce`
- `message_id`
- `chunk_result`
- `data`
- `done` 或 `error`

这组事件顺序非常适合你在面试里解释“为什么前端能够一边看到参考资料，一边看到答案流式生成”。

### 9. 搜索模式和问答模式有什么区别

这个项目里有两个容易混淆的概念：

- 搜索式问答
- 生成式问答

对应代码里其实是两条相关但不同的链路。

`chatUsecase.Search(...)` 只做这些事：

- 根据问题做检索。
- 返回命中的文档块。
- 再做一次文档访问权限判断，比如 `open / partial / closed`。

它不会调用大模型生成最终自然语言答案。  
所以你可以把它理解成“AI 加强版站内搜索”。

而 `chatUsecase.Chat(...)` 才是完整的 RAG 问答：

- 先检索。
- 再把检索结果组装成 Prompt。
- 最后调用模型流式生成答案。

这两个接口并存，说明系统在产品设计上并没有把“搜索”和“问答”混成一个黑盒，而是保留了两种交互模式。

### 10. 这一段链路为什么值得写进简历

因为它体现的不是“接了一个大模型 API”，而是比较完整的 AI 应用工程能力：

- 做了多入口接入：网页、Widget、兼容 OpenAI API。
- 做了会话管理：`conversation_id + nonce` 保证可恢复和可校验。
- 做了权限控制：按用户组过滤检索结果。
- 做了多轮上下文：历史消息参与问题改写和答案生成。
- 做了可解释性：检索 chunk 先返回给前端。
- 做了过程治理：输入输出两侧敏感词控制。
- 做了持久化：完整记录消息、模型、token、反馈。

如果你在面试里讲这部分，不要只说“我们做了 RAG”。  
更准确的说法应该是：

“我们实现的是一条面向知识库场景的工程化 RAG 问答链路。它支持多终端接入、多轮会话、权限过滤、检索结果显式返回、流式生成、答案落库和反馈闭环，不是一个简单的 Prompt Demo。”

## 十三、功能模块拆解：知识图谱构建

这是 MindWeave 相对原始知识库系统最有区分度的部分。

### 1. 为什么要做图谱

图谱的价值不是替代文档，而是把文档组织成网络，让系统能回答：

- 哪些文档属于同一知识域
- 哪些目录之间有上下层级
- 哪些文档由谁创建
- 哪些文档内容相似
- 未来哪些实体之间有关联

### 2. 当前图谱的核心对象

结合现有代码，当前图谱最完整的对象层是：

- `Document`
- `Folder`
- `KnowledgeBase`
- `User`

并且已经预留了：

- `Entity`

### 3. 当前图谱的核心关系

结合 `graph_sync.go`、`store/neo4j/query.go` 和设计文档，当前最明确的关系包括：

- `CONTAINS`
- `BELONGS_TO`
- `CREATED_BY`
- `EDITED_BY`
- `RELATED_BY_KEYWORD`

其中：

- `CONTAINS`：表达目录包含文档或子目录
- `BELONGS_TO`：表达节点归属于知识库
- `CREATED_BY` / `EDITED_BY`：表达文档和用户关系
- `RELATED_BY_KEYWORD`：表达文档与文档的相似关系

### 4. 实体层的现状

系统领域模型和查询接口已经为下面这些内容做了预留：

- `GraphEntity`
- `MENTIONS`
- `RELATES_TO`
- `REFERENCES`
- 实体搜索接口

但根据中期验收报告：

- 实体识别、实体消歧、实体关系抽取还没有完全闭环
- 实体搜索接口存在，但要依赖实体数据真正进入 Neo4j

所以在学习和面试表达时，要把“已实现”和“已预留”区分清楚。

### 5. 图谱数据来自哪里

图谱不是独立维护的第二套人工数据，而是从主业务对象同步出来的：

- 文档节点来自 PostgreSQL 的 `nodes`
- 文件夹节点来自 `nodes`
- 知识库节点来自 `knowledge_bases`
- 用户节点来自 `users`
- 文档相似关系来自内容 token 分析

### 6. 图谱构建的工程含义

这套图谱设计说明项目不是简单地“把 Neo4j 接进来试一试”，而是明确在做：

- 主业务对象到图模型的映射
- 增量同步
- 自动关系构建
- 图查询接口
- 图谱可视化

这已经是完整的图谱工程化链路。

## 十七、关键机制一：图谱同步链路

这部分是项目后端最值得认真理解的地方之一。

对应核心代码：

- `backend/usecase/graph_sync.go`

### 1. 为什么要做图谱同步

因为系统主业务数据存在 PostgreSQL，而图谱数据存在 Neo4j。  
如果文档、目录、知识库、用户发生变化，Neo4j 里的图谱也必须同步变化，否则图谱就会失真。

### 2. 同步覆盖哪些场景

`graph_sync.go` 中定义了这些任务类型：

- `document_create`
- `document_update`
- `document_delete`
- `document_move`
- `folder_create`
- `folder_update`
- `folder_delete`
- `folder_move`
- `user_create`
- `kb_create`

这说明同步不是只覆盖“新增文档”这一种情况，而是覆盖整个对象生命周期。

### 3. 同步时会做什么

以文档新增为例，同步链路大致是：

1. 从 PostgreSQL 加载节点。
2. 抽取文档 token。
3. 在 Neo4j 创建 `Document` 节点。
4. 创建文档与知识库、父目录、创建者之间的关系。
5. 自动重建该文档与其他文档的相似关系。

以文档更新为例：

1. 重新抽取 token。
2. 更新 Neo4j 中的文档节点。
3. 重建相似关系。

以文件夹为例：

- 创建或更新 `Folder` 节点
- 同步父子关系

### 4. 同步实现上的一个关键特点

图谱同步不是独立跑全量导数，而是“围绕业务事件做增量同步”。

这类设计的优点是：

- 延迟低
- 更适合在线系统
- 不需要频繁做全量重建
- 更接近真实生产系统的写法

### 5. 这部分对你学习项目的意义

读懂这部分，你会同时理解：

- PostgreSQL 与 Neo4j 的职责边界
- 增量同步设计
- 图模型写入逻辑
- 文档关系自动构建

它是这个项目最能体现“后端工程价值”的模块之一。

## 十八、关键机制二：重试、死信与手动重放

如果说图谱同步体现了“功能完整性”，那么重试和死信机制体现的是“系统稳定性”。

### 1. 为什么需要这套机制

任何跨系统同步都可能失败，例如：

- Neo4j 暂时不可用
- 网络异常
- 数据状态不完整
- 某次写操作超时

如果失败任务直接丢失，图谱最终就会和主业务数据不一致。

### 2. 自动重试

`graph_sync.go` 里的关键参数是：

- 最大重试次数：`3`
- 初始等待：`500ms`
- 最大等待：`4s`

它采用的是指数退避思想：

- 第一次失败，稍后再试
- 再失败，等待更久
- 直到达到上限

### 3. 死信落库

如果达到最大重试次数仍失败，任务不会被丢弃，而是写入 `graph_sync_dead_letters` 表。

记录内容包括：

- 知识库 ID
- 任务类型
- 实体 ID
- Payload
- 错误信息
- 已重试次数
- 最后重试时间
- 是否已解决

这让失败任务具备：

- 留痕
- 可追踪
- 可审计
- 可恢复

### 4. 手动重放

管理员可以通过：

- `POST /api/v1/graph/sync/retry`

按知识库维度重放死信任务。

图谱页面里也已经把这个能力做成了可点击按钮。

### 5. 重放后的结果状态

如果重放成功：

- 死信标记为 `resolved`

如果重放仍失败：

- 失败次数继续累加
- 保持为待处理或失败状态

### 6. 这部分为什么是简历亮点

因为它体现的不只是 CRUD，而是：

- 异步任务设计
- 最终一致性
- 故障补偿
- 运维恢复能力

对于后端岗位，这是明显比“写了接口”更有说服力的工程亮点。

## 十九、关键机制三：文档关系构建算法

这是图谱模块里非常值得单独讲清楚的一个点。

对应核心代码：

- `backend/usecase/graph_tokenizer.go`
- `backend/store/neo4j/query.go`

### 1. 问题背景

如果系统只把文档同步到 Neo4j，但文档之间没有关系，那么图谱会很“散”。  
所以项目需要一种低成本、可解释、可增量更新的方法，自动发现文档之间的相关性。

### 2. token 提取逻辑

`extractGraphDocumentTokens` 的思路是：

- 标题和正文都参与抽取
- 标题权重更高
- 英文和数字用正则切词
- 中文按 `bi-gram` 切分
- 最终取高频 token

具体实现细节：

- 标题会被额外加权 3 倍
- 总文本长度最多截取 6000 个 rune
- 最多保留 160 个 token
- 英文 token 至少长度为 2

### 3. 为什么中文用 bi-gram

中文不像英文天然有空格分词，所以项目采用了工程上较容易落地的方式：

- 把连续中文按双字切分

例如：

- “知识图谱” -> “知识”、“识图”、“图谱”

这种方式的优点是：

- 不依赖复杂分词器
- 实现简单
- 对中文内容比纯空格切词有效很多

缺点是：

- 语义粒度有限
- 对长实体和复杂语义不够聪明

### 4. 文档关系的评分方式

在 `store/neo4j/query.go` 中，系统会：

1. 取两篇文档的 token 集合
2. 计算共同 token
3. 计算 `commonCount`
4. 用交并比思路计算相似度分数，也就是 Jaccard 风格分数：

```text
score = commonCount / (size(tokens1) + size(tokens2) - commonCount)
```

### 5. 当前阈值

代码里当前关系构建阈值为：

- 最少共同 token：`3`
- 最低得分：`0.18`
- 关系中最多预览关键词：`20`

### 6. 生成的关系

当满足阈值后，系统会创建：

- `RELATED_BY_KEYWORD`

并在关系上写入：

- `keywords`
- `common_count`
- `score`
- `match_mode`
- `created_at`
- `updated_at`

### 7. 这个算法的价值

它的优点是：

- 成本低
- 可解释
- 支持增量更新
- 中英文都能基本覆盖
- 足够适合当前工程阶段

### 8. 它的局限

它并不是语义模型，不擅长处理：

- 隐式关系
- 多跳概念关联
- 同义改写
- 深层语义理解

所以更准确的定位是：

- 这是当前工程阶段非常合适的“文档相似关系构建方案”
- 不是终极图谱关系算法

## 二十、关键机制四：RAG 与知识图谱如何配合

这是最容易在面试里被问到的问题之一。

### 1. Qdrant 在解决什么问题

Qdrant 负责的是：

- 文档切片后的向量存储
- 语义相似内容召回

它擅长回答的问题是：

- “这个问题语义上最像哪些文档片段？”

### 2. Neo4j 在解决什么问题

Neo4j 负责的是：

- 层级关系
- 归属关系
- 路径关系
- 文档相似关系
- 实体关系扩展

它擅长回答的问题是：

- “这个文档属于哪个目录？”
- “两个节点之间有没有路径？”
- “谁创建了这份文档？”
- “哪些文档彼此相关？”

### 3. 为什么不能只用其中一个

只用 Qdrant：

- 能找语义相近内容
- 但不擅长做图结构分析和关系解释

只用 Neo4j：

- 能表达显式关系
- 但不擅长做语义相似召回

所以两者并不是竞争关系，而是互补关系。

### 4. 当前项目中的实际状态

根据现有代码和中期验收报告，当前最准确的说法是：

- 系统已经具备 RAG 问答能力
- 系统已经具备图谱查询与可视化能力
- 两者都已经落地
- 但“自然语言问题直接转图查询并融合生成答案”的完整混合问答链路，还没有完全闭环

这点在表达时一定要说清楚。

### 5. 如何理解未来的理想形态

理想状态下，系统可以按下面方式工作：

1. 用户提问
2. 先做向量召回，找相关内容
3. 再做图查询，找结构化关系
4. 最终由大模型综合两类上下文给出答案

这就是“RAG + 图谱”的真正目标。

## 二十四、部署与运行路线：项目是如何被启动起来的

这部分决定你能不能真正把项目跑起来、讲明白。

### 1. 容器服务组成

### 2. 每个服务的职责

`caddy`

- 统一网关入口
- 管理配置和运行套接字

`nginx`

- 管理后台入口

`app`

- 前台 Wiki / Web 应用

`api`

- 后端核心 API 服务
- 暴露 `8000`
- 使用根目录 `bin/api` 覆盖镜像中的默认可执行文件

`consumer`

- 异步消息消费服务

`postgres`

- 主业务数据库

`redis`

- 缓存与会话

`minio`

- 文件存储

`nats`

- 异步消息总线

`qdrant`

- 向量库

`crawler`

- 负责网页抓取、导入解析

`raglite`

- RAG 相关处理服务

`neo4j`

- 图数据库

### 3. 为什么 `api` 容器特别关键

`api` 服务的 Compose 配置里有这一点很重要：

- 它不是直接跑镜像默认程序
- 而是通过 volume 把根目录 `./bin/api` 挂载进去，并以 `/custom/api` 作为入口

这说明你的后端自定义能力是通过编译后的 `api` 二进制真正落到运行环境中的。

### 4. 数据卷布局

本地 `data/` 目录下保存了：

- PostgreSQL 数据
- Redis 数据
- MinIO 数据
- Qdrant 数据
- Neo4j 数据
- Caddy / Nginx 配置

这意味着根目录实际上兼具“代码仓 + 运行目录”的双重属性。

### 5. 环境变量与脚本

根目录还提供了：

- `.env`
- `.env.local`
- `start-docker.ps1`
- `run-api-local.ps1`
- `deploy-backend.ps1`
- `build-and-deploy.ps1`

这些文件体现了项目不仅能在 IDE 里开发，也考虑了本地联调和部署交付。

### 6. 实际运行时的数据流

你可以把部署后的系统理解成两条主链路：

业务访问链：

```text
浏览器 -> 网关 -> API / App -> PostgreSQL / Redis / MinIO / Neo4j / Qdrant
```

异步加工链：

```text
导入请求 -> API -> NATS -> Consumer / Crawler / RAGLite -> Qdrant / MinIO / PostgreSQL
```

这就是整个系统真正跑起来的方式。

## 二十六、如果面试官追问，应该重点准备哪些问题

下面这些问题几乎是高频题。

### 1. 这个项目是你从零开发的吗？

推荐回答：

不是完全从零平地起项目，而是基于开源 `PandaWiki` 做了二次开发和系统整合。我重点负责的是知识图谱模块、图谱同步补偿机制、文档关系构建、图谱查询接口、可视化页面，以及整体部署联调。

### 2. 为什么要同时用 PostgreSQL、Qdrant 和 Neo4j？

推荐回答：

- PostgreSQL 管业务主数据
- Qdrant 管语义检索
- Neo4j 管关系结构和路径分析

三者解决的问题不同，组合后才能兼顾业务一致性、语义召回和关系解释。

### 3. 为什么图谱同步不直接做成全量导入？

推荐回答：

因为这是在线系统。文档和目录会不断变化，全量重建成本高、延迟大，所以更适合围绕新增、更新、删除、移动等事件做增量同步。

### 4. 为什么要做死信表？

推荐回答：

因为跨系统同步一定会失败，失败任务不能直接丢。写入死信后，任务才具备可追踪、可审计、可重放能力。

### 5. 文档相似关系为什么不用更重的模型？

推荐回答：

当前目标是先做工程可落地的方案。token + Jaccard 成本低、可解释性强、支持增量更新，适合先构建稳定的文档关系层，再逐步升级到更重的语义关系模型。

### 6. 图谱问答现在做到什么程度了？

推荐回答：

当前已经具备 RAG 问答能力，也具备图谱查询和可视化能力。两部分都能独立工作。进一步要完善的是自然语言转图查询并融合生成答案的完整闭环。

### 7. 图谱规模变大后，瓶颈会在哪里？

推荐回答：

可能会出现在：

- Neo4j 查询复杂度
- 全图加载量
- 前端布局和渲染性能
- 3D 可视化交互成本
- 网络传输体积

### 8. 你在这个项目里最有价值的工作是什么？

推荐回答方向：

- 图谱同步与补偿
- 多存储协同
- 图谱查询与可视化
- 部署整合

因为这些点最能体现工程深度。

## 二十七、项目当前边界、缺口与可继续优化的方向

这部分一定要诚实，因为它直接关系到你后续的答辩和面试可信度。

### 1. 多模态能力还不完整

中期验收文档已经明确指出：

- 当前主要还是文本和文档类数据
- 图片 OCR、截图、聊天记录解析等多模态接入还未完成

### 2. 实体层尚未完全闭环

虽然代码中已经预留：

- `Entity` 节点
- 实体搜索接口
- `MENTIONS` / `RELATES_TO` 等关系类型

但实体抽取、消歧、关系抽取还没有完整落地。

### 3. 图谱问答链路仍在完善

当前已具备：

- RAG 问答
- 图谱查询

但“自然语言 -> Cypher -> 图结果 -> 自然语言答案”的混合链路还不是完全完成态。

### 4. 文档关系算法仍偏轻量

当前方案很适合工程阶段，但在复杂语义关系上仍有限。

未来可以优化为：

- 更强的语义建模
- 实体级关系增强
- 多跳关系推理

### 5. 性能和联调空间仍然存在

因为系统涉及：

- 多数据库
- 消息队列
- 向量库
- 图数据库
- AI 服务

所以完整压力测试、稳定性评估、资源消耗优化还有继续打磨空间。

### 6. 商业版 / 专业版边界

代码中存在：

- `backend/pro`
- `web/admin/src/request/pro`
- `web/app/src/request/pro`

这说明上游系统存在专业版扩展。  
对于你当前的 MindWeave 项目，要把“你实际用到和改到的部分”和“上游已有但你未重点实现的部分”分开。
