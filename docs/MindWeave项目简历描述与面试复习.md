# MindWeave 项目简历与面试复习

## 一、项目简历（后端开发岗）

**MindWeave｜企业知识库与知识图谱问答系统**  
**项目角色：后端开发 / AI 应用开发**  
**技术栈：** `Go`、`Echo`、`PostgreSQL`、`Redis`、`MinIO`、`NATS`、`Qdrant`、`Neo4j`、`Docker Compose`  
**项目概述：** 面向企业知识沉淀、文档检索、智能问答与知识关系可视化场景，构建覆盖知识接入、检索增强、图谱分析与私有化部署的 AI 知识管理平台。

**核心贡献：**

- **后端架构**：基于 `Go` + `Echo` 搭建知识库后端服务，完成知识库、文档、图谱查询与同步相关接口开发，支撑文档管理、AI 问答、图谱分析等核心业务。
- **存储分层**：设计 `PostgreSQL + Redis + MinIO + Qdrant + Neo4j` 多存储架构，分别承担主数据、缓存会话、对象文件、向量检索和图关系查询，兼顾数据一致性、检索效率与系统扩展性。
- **图谱建模**：抽象 `Document`、`Folder`、`KnowledgeBase`、`User`、`Entity` 等节点及 `CONTAINS`、`BELONGS_TO`、`CREATED_BY`、`RELATED_BY_KEYWORD` 等关系，支持全图查询、节点查询、路径查询、统计分析与实体搜索。
- **稳定性治理**：重构图谱同步链路，在文档/文件夹新增、更新、删除、移动及用户、知识库创建场景下引入异步同步、指数退避重试、死信落库与手动重放机制，提升图谱数据最终一致性与故障恢复能力。
- **关系构建**：优化文档关联算法，基于标题加权、正文 token 提取、中文 `bi-gram` 与英文词项切分，结合 `Jaccard` 相似度增量生成文档关系，增强知识关联发现能力与图谱质量。
- **部署交付**：基于 `Docker Compose` 编排 `Caddy`、`Nginx`、`API`、`Consumer`、`PostgreSQL`、`Redis`、`MinIO`、`NATS`、`Qdrant`、`RAGLite`、`Neo4j` 等服务，支持本地联调与私有化部署。

## 二、项目简历（AI 全栈开发岗）

**MindWeave｜AI 知识库与知识图谱管理平台**  
**项目角色：AI 全栈开发 / 后端主导**  
**技术栈：** `Go`、`Echo`、`React`、`TypeScript`、`PostgreSQL`、`Redis`、`MinIO`、`Qdrant`、`Neo4j`、`Graphology`、`Sigma.js`、`Three.js`、`Docker Compose`  
**项目概述：** 构建企业级 AI 知识管理平台，支持多源文档导入、知识库管理、智能问答、图谱构建与 2D/3D 可视化，形成“知识导入—检索增强—图谱分析—问答反馈”的业务闭环。

**核心贡献：**

- **全栈搭建**：基于 `Go` + `Echo` + `React` + `TypeScript` 搭建 AI 知识库平台，贯通管理后台、图谱分析页、问答链路与部署环境，覆盖知识沉淀、智能检索和图谱可视化等核心能力。
- **知识接入**：设计多源导入链路，支持离线文件、URL、RSS、Sitemap 等接入方式，降低知识入库门槛，提升非结构化内容接入效率。
- **AI 检索增强**：在后端集成 `Qdrant` 向量检索与 `Neo4j` 图关系查询，形成“语义检索 + 关系分析”双引擎能力，增强 AI 问答的召回效果、上下文质量与结果解释性。
- **数据一致性**：实现图谱同步与补偿机制，覆盖文档、文件夹、用户、知识库等对象的增量同步，并通过重试与死信重放降低异步任务失败导致的数据不一致问题。
- **图谱可视化**：参与图谱页面研发，基于 `Graphology`、`Sigma.js`、`react-force-graph-3d`、`Three.js` 实现 2D/3D 图谱展示，支持节点高亮、邻居聚焦、相机定位、文档预览等交互。
- **环境交付**：负责容器化部署与运行环境编排，整合网关、API、存储、消息队列、向量库、图数据库与 RAG 服务，支撑 AI 知识库应用的完整交付。

## 三、项目业务详解

### 1. 项目解决的问题

MindWeave 解决的是企业内部知识分散、检索效率低、文档关系弱、问答结果不可解释的问题。

典型痛点：

- 文档来源分散，可能来自本地文件、网页、订阅源、站点地图，知识接入成本高。
- 传统全文搜索只能搜“关键词”，无法很好理解语义，也无法表达文档之间的关联。
- AI 问答虽然能回答问题，但如果缺少知识约束和关系支撑，容易出现回答泛化、不稳定、不可追溯的问题。
- 企业知识一旦只停留在文档层面，就很难做知识脉络分析、关系发现和后续复用。

### 2. 项目业务目标

- 统一接入多来源知识内容。
- 建立知识库管理能力，支持文档沉淀、编辑、发布和权限控制。
- 构建基于知识库内容的 AI 搜索与智能问答能力。
- 用知识图谱表达文档、目录、用户、知识库、实体之间的关系。
- 让知识不仅“能搜到”，还能“看关系、查路径、做分析、做解释”。

### 3. 核心业务角色

- **管理员**：创建知识库、导入文档、配置模型、查看统计、处理反馈。
- **内容维护者**：整理文档目录、编辑内容、管理发布状态、维护知识质量。
- **普通用户**：浏览知识库、搜索内容、发起 AI 问答、查看相关文档。
- **运维/技术人员**：部署服务、处理同步异常、维护运行环境。

### 4. 核心业务流程

#### 流程一：知识接入

1. 管理员创建知识库。  
2. 通过离线文件、URL、RSS、Sitemap 导入内容。  
3. 文档进入解析、上传、入库流程。  
4. 文档元数据与内容进入主数据、对象存储和检索链路。

#### 流程二：知识沉淀与检索

1. 文档在知识库中按目录树组织。  
2. 用户可以浏览、搜索、查看文档。  
3. 系统基于知识库内容支持 AI 搜索与智能问答。  
4. 问答记录与反馈信息可沉淀到后台用于后续分析。

#### 流程三：图谱构建与分析

1. 文档、文件夹、用户、知识库等对象同步到 `Neo4j`。  
2. 系统为对象建立层级、归属、创建者、关联文档等关系。  
3. 基于标题与正文 token 相似度自动生成文档关联关系。  
4. 后台图谱页支持全图浏览、路径查询、实体搜索与统计分析。

#### 流程四：异常恢复

1. 文档或目录变更触发图谱同步任务。  
2. 如果同步失败，任务进入重试流程。  
3. 多次失败后写入死信表。  
4. 通过重放接口按知识库维度恢复失败任务。

- 文档与文件夹元数据
- 对话与消息记录
- 用户信息

负责高频访问数据和会话状态，包括：

- 登录态/会话

- 减少热点查询压力

#### MinIO

负责文件对象存储，包括：

- 上传文件
- 导入原始资源
- 文档附件或中间文件

#### Qdrant

负责向量检索，包括：

- 文档切片后的向量存储

- 为 AI 问答提供检索结果

#### Neo4j

负责知识图谱查询，包括：

- 文档层级关系
- 知识库归属关系
- 用户创建关系
- 文档相似关系
- 图谱统计和路径分析

#### NATS

负责异步解耦，包括：

- 导入链路异步处理
- 消费任务分发
- 降低主流程阻塞

### 3. 知识图谱建模

#### 节点类型

- `Document`：文档节点
- `Folder`：文件夹节点
- `KnowledgeBase`：知识库节点
- `User`：用户节点
- `Entity`：实体节点

#### 关系类型

- `CONTAINS`：文件夹包含文档/文件夹
- `BELONGS_TO`：文档/文件夹归属于知识库
- `CREATED_BY`：文档由用户创建
- `EDITED_BY`：文档由用户编辑
- `RELATED_BY_KEYWORD`：文档间相似关系
- 以及实体相关关系扩展

### 4. 图谱同步设计

图谱同步覆盖以下对象生命周期：

- 文档新增
- 文档更新
- 文档删除
- 文档移动
- 文件夹新增
- 文件夹更新
- 文件夹删除
- 文件夹移动
- 用户创建
- 知识库创建

同步策略：

- 业务主流程完成后触发图谱同步
- 同步执行失败后自动重试
- 重试采用指数退避
- 超过最大次数写入死信表
- 提供按知识库维度的死信重放接口

这部分是典型的后端高价值亮点，因为它体现了：

- 异步任务设计
- 最终一致性保障
- 故障补偿机制
- 运维可恢复性

### 5. 文档关系构建算法

核心做法：

- 对标题做更高权重处理
- 对正文抽取 token
- 中文采用 `bi-gram`
- 英文采用词项切分
- 计算共同 token 数量
- 使用 `Jaccard` 相似度筛选关系
- 将结果写入 `Neo4j` 中的 `RELATED_BY_KEYWORD` 关系

这样做的价值：

- 比只看标题更准确
- 对中文内容更友好
- 成本低、可解释性强
- 适合工程化落地和增量更新

- 视角定位

#### 3D 图谱

基于 `react-force-graph-3d` + `Three.js` 实现：

- 自动旋转

这部分对后端岗不是主卖点，但对 AI 全栈岗是明显加分项。

## 六、面试重点复习

### 1. 业务上重点复习什么

- 为什么企业知识库需要 AI 问答
- 为什么仅有全文搜索不够

### 2. 技术上重点复习什么

- `PostgreSQL`、`Redis`、`MinIO`、`Qdrant`、`Neo4j` 各自负责什么
- 为什么图谱同步要异步化
- 为什么要做重试和死信机制
- 文档关系构建为什么选择 token + Jaccard
- 中文 bi-gram 的好处和局限
- 图谱查询接口怎么设计

### 3. 功能上重点复习什么

- 文档导入链路怎么走
- 图谱怎么构建
- 图谱统计和路径查询有什么价值
- AI 问答和图谱是什么关系
- 图谱页面支持哪些核心交互

### 4. 高频问题直接准备

#### 问题 1：这个项目解决了什么问题？

答：解决企业知识分散、难检索、难复用、问答缺少知识约束和关系解释的问题。

#### 问题 2：为什么要同时用 Qdrant 和 Neo4j？

答：`Qdrant` 负责语义相似内容检索，`Neo4j` 负责结构化关系表达和路径分析，两者解决的问题不同，组合后能同时提升召回能力和解释性。

#### 问题 3：为什么图谱同步要做成异步？

答：为了避免主业务流程阻塞，降低写操作耗时，并且给失败重试、补偿恢复留出空间。

#### 问题 4：为什么要做死信表？

答：因为异步任务不可能保证每次都成功，失败任务不能直接丢失，必须留痕、可追踪、可重放。

#### 问题 5：为什么关系构建不用更重的模型？

答：当前方案更偏工程化落地，token + Jaccard 成本低、可解释性强、易于增量更新，适合先快速构建有效关系，再逐步升级到更重的语义模型。

#### 问题 6：如果图谱规模变大，瓶颈会在哪里？

答：可能出现在 Neo4j 查询复杂度、图谱全量加载耗时、前端布局和渲染性能、网络传输体积等方面。
