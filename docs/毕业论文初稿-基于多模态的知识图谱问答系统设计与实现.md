## 中文摘要

随着大语言模型、知识图谱与检索增强生成技术的快速发展，面向个人知识管理、学习辅助与垂直领域资料整理的智能问答系统逐渐成为研究与应用热点。然而，传统问答系统普遍存在知识来源分散、语义结构弱、推理路径不可解释以及多源文档难以统一组织等问题。针对上述问题，本文设计并实现了一套基于多模态知识接入的知识图谱问答系统。该系统为从 0 开始设计与开发的 Mindweave 平台，围绕毕业设计需求完成了文档接入、图谱构建、向量检索、图谱同步、图谱查询与可视化等核心模块的实现与集成。

本文围绕“多源知识接入、知识图谱构建、RAG 问答增强与图谱可视化”四条主线展开。系统后端采用 Go 实现核心业务逻辑，前端采用 React 与 TypeScript 实现交互界面，底层使用 PostgreSQL、Redis、MinIO、Qdrant、Neo4j 与 NATS 构建混合存储与异步处理架构。针对图谱数据维护的一致性问题，设计了“自动重试 + 指数退避 + 死信落库 + 手动重放”的图谱同步补偿机制；针对文档关系自动构建问题，提出了基于标题加权、双语分词与 Jaccard 相似度的轻量化关联算法；针对图谱使用体验问题，构建了支持统计概览、节点关系查询、路径查询、2D/3D 展示切换的图谱可视化页面。

从阶段性实现结果看，系统已具备文档上传、知识库管理、向量检索问答、图谱节点关系建模、图谱统计与交互浏览等能力，能够为后续实体抽取闭环、多跳推理问答及多模态 OCR 接入提供可扩展基础。本文最后对系统的不足进行了分析，并给出了后续在实体抽取、图谱问答联动、实验量化评估和真正多模态输入接入等方面的改进方向。

**关键词：** 知识图谱；检索增强生成；多模态知识管理；Neo4j；问答系统；图谱可视化

## Abstract

With the rapid development of large language models, knowledge graphs, and retrieval-augmented generation, intelligent question answering systems for personal knowledge management, learning assistance, and domain-oriented information services have become an important research topic. However, conventional QA systems usually suffer from fragmented knowledge sources, weak semantic structure, limited explainability, and poor support for unified organization of heterogeneous documents. To address these issues, this thesis designs and implements a multimodal knowledge graph question answering system.

The proposed system is implemented as Mindweave, a platform designed and developed from scratch for this graduation project. It integrates document ingestion, graph construction, vector retrieval, graph synchronization, graph querying, and graph visualization into a unified architecture. The backend is implemented in Go, the frontend is built with React and TypeScript, and the storage layer combines PostgreSQL, Redis, MinIO, Qdrant, Neo4j, and NATS. To improve graph consistency, a compensation mechanism including automatic retry, exponential backoff, dead-letter persistence, and manual replay is introduced. To construct document relations efficiently, a lightweight method based on title weighting, bilingual token extraction, and Jaccard similarity is designed. In addition, an interactive graph page supporting graph statistics, node relation exploration, path query, and 2D/3D visualization is implemented.

The current implementation has already supported document upload, knowledge base management, vector-based retrieval, graph modeling, graph statistics, and interactive browsing. It provides an extensible foundation for future improvements such as entity extraction, graph-enhanced question answering, OCR-based multimodal input, and quantitative evaluation. Finally, the thesis discusses the limitations of the current stage and outlines future work directions.

**Keywords:** knowledge graph; retrieval-augmented generation; multimodal knowledge management; Neo4j; question answering system; graph visualization

## 第1章 绪论

### 1.1 研究背景

进入大模型应用时代后，知识管理系统的核心矛盾已经从“能否存储文档”转向“能否理解异构知识、组织关系网络并生成可信答案”。围绕垂直领域问答、企业知识服务和多模态知识组织的现有研究可见，当知识仅以分散文档或静态条目形式存在时，系统往往难以兼顾检索效率、关系表达和结果可追溯性；一旦引入知识图谱、向量检索和结构化证据组织机制，系统对复杂问题、跨文档问题和解释型问题的支撑能力会明显增强[1-5]。

围绕这一问题，知识图谱与检索增强生成技术逐渐成为智能问答系统的重要基础。吕志锦、高宇德和陈文丽等研究都指出，RAG 可以通过外部知识检索缓解大语言模型知识滞后和幻觉风险，而蔡浩君、卓梁雨等进一步证明，多路召回、证据融合和索引分层是提升垂直领域问答稳定性的关键工程手段[1][2][7-9]。与此同时，李至颖、李永春等关于图数据库、向量数据库和图谱管理联动的研究说明，面向真实场景的知识问答系统不能只强调“能回答”，还需要在答案背后保留结构化关系、证据来源和知识边界[3][6]。

对于毕业设计项目而言，仅实现一个对话入口并不足以体现系统设计与工程实现能力。更具研究和展示价值的方案，应同时回答以下几个问题：如何把多源文档接入系统并保持统一管理；如何把文档、知识库、目录和用户等业务对象映射为图结构；如何让图谱与语义检索链路形成互补；如何在多存储协同条件下保持数据一致性；以及如何通过可视化方式把后台图谱能力转化为前台可感知功能。基于上述问题，本文围绕“基于多模态的知识图谱问答系统设计与实现”这一目标，从 0 开始设计并实现 Mindweave 平台，构建一套面向真实知识管理场景、支持后续扩展的系统原型。

### 1.2 研究目的与意义

#### 1.2.1 研究目的

本文的研究目的可概括为以下三个方面。

第一，构建面向多源知识管理场景的统一系统架构。通过整合文档上传、网页导入、RSS 采集、知识库存储、向量检索、图谱建模与前端可视化能力，形成一套适合个人或小型团队场景的知识处理平台。

第二，探索知识图谱与检索增强生成协同工作的实现方式。对于事实性强、关系明确的问题，图谱查询能够提供更高的可解释性；对于开放式、描述性问题，RAG 能够提供更自然的文本生成能力。二者结合有望改善单一问答方式的局限。

第三，在工程实现层面验证图谱同步补偿、轻量化文档关系构建和图谱可视化等关键设计的可行性，为后续完善实体抽取、多跳推理和真正多模态输入接入提供基础。

#### 1.2.2 理论意义

本文将知识图谱、RAG、图数据库与知识管理系统集成于同一工程框架中，对“图谱增强型知识问答系统”的落地路径进行实证式探索。在大模型快速发展的背景下，该研究有助于理解结构化知识与生成式模型之间的协同边界，并为轻量级、多模块、易部署的图谱问答系统研究提供案例参考。

#### 1.2.3 实践意义

从实践层面看，本文设计的系统可以服务于个人知识库整理、课程学习辅助、项目文档管理、研发资料归档等场景。通过图谱建模，用户能够从“文档列表视角”切换到“关系网络视角”，提升知识组织能力；通过问答接口，用户能够更快速地定位目标知识；通过图谱可视化，系统能够增强知识演化与内容结构的可观测性。

### 1.3 国内外研究现状

#### 1.3.1 知识图谱研究现状

知识图谱研究正在从单纯的知识组织工具转向面向业务推理、知识服务和智能问答的基础设施。李至颖等在海事检查场景中通过多模态知识图谱支撑智能问答，说明图谱已经能够承载文本片段、实体关系和问答证据之间的协同组织[3]。杨波等从企业舆情危机预警场景出发，指出领域知识图谱正在从单模态建模扩展为多模态、多源异构信号协同建模，图谱的价值也从“静态表示”延伸到“动态分析与决策支持”[5]。周爱华等进一步展示了利用大语言模型完成实体、属性和关系抽取并构建领域知识图谱的路径，表明大模型已经成为知识图谱构建的重要推动力量[10]。

从研究趋势看，当前知识图谱建设越来越强调与具体业务场景结合，尤其关注知识更新、来源记录、结构约束和系统联动能力。一方面，多源数据和多模态数据不断涌入，使图谱必须具备更强的融合与扩展能力；另一方面，知识服务系统又要求图谱能够支撑问答、浏览、推理和解释等复合任务[3][5][10]。这意味着，对于本文所研究的多模态知识图谱问答系统而言，图谱不只是后台数据结构，更是连接知识组织、检索增强和答案解释的中间枢纽。

#### 1.3.2 知识图谱问答研究现状

知识图谱问答是知识图谱应用的重要落地方向。吕志锦的研究表明，在垂直领域问答系统中，知识图谱能够提供结构化约束，使系统在处理实体关系明确、规则边界清晰的问题时具有更好的稳定性和可解释性[2]。李永春进一步把知识图谱管理模块与多模态问答模块联动，实现了“问题输入 - 图谱检索 - 结果返回 - 图结构展示”的闭环过程，说明图谱问答系统正在从后台推理工具转向前台可交互的综合服务模块[6]。李至颖等在海事检查场景中的实践也证明，知识图谱与问答系统联动后，能够更好地支持专业知识查询、关系浏览和知识定位[3]。

随着大语言模型的加入，知识图谱问答的研究路线正在从传统模板匹配和规则查询，逐步转向“图谱约束 + 生成式回答”的混合模式。相较于仅依赖语言模型直接生成答案的方式，这种模式更强调证据边界、答案依据和结构一致性[2][6]。因此，当前 KGQA 的关键问题已经不只是“能否查到答案”，而是“能否在自然语言交互条件下保持回答可信、可追踪且便于管理”。

#### 1.3.3 RAG 与图谱增强问答研究现状

检索增强生成是当前垂直知识问答系统的主流技术路线之一。吕志锦指出，RAG 的核心在于把向量检索与生成模型结合起来，使系统能够从外部知识库中检索相关内容并作为上下文参与答案生成[2]。高宇德的研究进一步说明，在领域知识库场景中，文档预处理、分块策略、向量化表示和检索结果组织会直接影响最终问答质量[1]。陈文丽等围绕 LangChain 知识库问答系统的实现也给出了较完整的技术链条，说明 RAG 在工程上已经形成“文档加载 - 文本切分 - 向量存储 - 语义检索 - Prompt 拼装 - 大模型生成”的稳定范式[7]。

在此基础上，国内研究正把 RAG 从单一路径召回推进到混合检索与证据治理阶段。蔡浩君等在行业知识库场景中把数据清洗、分块、向量索引和倒排索引统一纳入知识构建流程，表明高质量问答必须建立在高质量知识索引基础之上[8]。卓梁雨等进一步提出“内容标签匹配召回 + 结构化关键词召回 + 向量召回”的多路并行机制，通过去重、加权与重排扩大复杂问题与长尾问题的覆盖范围[9]。陈雪松等则通过多 Agent 协作方式，将检索、评估、重写和生成组织为可编排的自适应流程，说明 RAG 正从静态链路转向更灵活的智能调度链路[11]。

另一方面，图谱增强问答逐渐成为 RAG 的重要延伸方向。李至颖等通过向量数据库与图数据库协同存储的方式，把精简检索索引与完整图谱事实分层保存，从而兼顾召回效率与关系表达能力[3]。这说明，GraphRAG 或 HybridRAG 的价值不在于简单增加一个图数据库，而在于让结构化事实、文本证据和生成结果之间形成更稳定的衔接机制。

#### 1.3.4 多模态知识图谱研究现状

多模态知识图谱是近年知识组织研究的重要拓展方向。常彬彬指出，不同模态的数据在表示空间和语义结构上存在明显差异，如果缺少有效的跨模态对齐机制，即使文本、图像和其他信号共同描述同一对象，也难以形成统一知识表示[4]。杨波等进一步指出，多模态大模型的发展推动知识图谱构建从单模态信息抽取转向多源异构信息协同建模，研究重点逐步转向跨模态对齐、多源融合和复杂语义关系重建[5]。这意味着，多模态知识图谱并不是简单地把图片附着在文本旁边，而是要把不同模态中的互补信息共同组织为可检索、可分析、可推理的知识对象。

从工程实现角度看，多模态知识接入的关键在于把复杂输入转化为稳定的中间表示。高宇德提出的处理流程显示，版面解析、OCR 提取、公式转写、表格结构识别和统一文本化输出，是文档类多模态知识进入问答系统的重要前置步骤[1]。周爱华等基于大语言模型完成实体、属性和关系抽取的研究说明，多模态预处理的最终目标仍然是服务于知识抽取与图谱构建[10]。李永春在多模态问答研究中则把图片输入、文本提问和图谱检索结合起来，说明多模态能力只有与知识组织和问答链路打通，才能真正转化为系统能力[6]。

因此，本文理解的多模态并不仅是前端支持更多上传格式，而是系统在后台具备把版面、图片、表格、文本等多源内容逐步转化为可被向量检索和图谱调用的统一知识表示的能力。

#### 1.3.5 现有研究的不足

综合国内外研究可见，现有方法虽然在单点技术上已较成熟，但在面向毕业设计和中小规模工程项目时仍存在以下不足：

1. 很多研究关注算法指标和数据集效果，对完整系统集成、服务编排和实际部署考虑不足。
2. 多模态能力虽然越来越受到重视，但不少工作停留在抽取或建模层面，缺少与知识接入、统一存储和统一检索的工程闭环[4][5]。
3. 图谱问答、RAG 与证据治理往往分散在不同模块中实现，较少有研究从系统层面对权限控制、答案边界和可追溯性进行统一设计[11][13]。
4. 较少有工作系统讨论图谱同步失败、增量更新补偿、证据可追溯和可视化交互等工程细节。

因此，设计一套可运行、可扩展、能够服务于真实知识管理场景的图谱问答系统，仍具有较强的研究价值与实践意义。

### 1.4 研究内容

本文的主要研究内容包括以下几个方面：

1. 从 0 开始设计并实现 Mindweave 平台，形成面向多源文档接入的系统基础能力。
2. 设计基于 Neo4j 的知识图谱数据模型，实现文档、文件夹、用户、知识库等对象的图结构表达。
3. 实现 PostgreSQL 到 Neo4j 的同步机制，并通过自动重试、死信落库与重放机制保证图谱数据一致性。
4. 设计轻量化文档关系自动构建算法，为后续实体图谱与图谱问答奠定结构基础。
5. 实现图谱查询 API、图谱统计接口以及支持 2D/3D 展示的可视化管理页面。
6. 对系统功能、架构和阶段性效果进行分析，并提出后续改进方向。

### 1.5 主要贡献

围绕上述研究内容，本文的主要工作和贡献如下：

1. 提出了一种适用于中小规模知识管理场景的“关系型数据库 + 对象存储 + 向量库 + 图数据库 + 消息队列”混合架构，实现了结构化数据、非结构化文档和图谱数据的协同管理。
2. 设计并实现了图谱同步补偿机制，将自动重试、指数退避、死信持久化和人工重放纳入统一流程，提高了图谱同步链路的鲁棒性。
3. 设计了一种基于标题加权、双语 token 抽取和 Jaccard 相似度的轻量化文档关联构建方法，兼顾实现复杂度与可解释性。
4. 设计并实现了一条面向知识库场景的工程化 RAG 链路，在 `dataset_id` 管理、`group_ids` 权限过滤、多轮会话 `conversation_id + nonce` 校验、证据块回显和 SSE 流式输出之间形成统一流程。
5. 完成了图谱查询、路径查询、图谱统计、实体搜索和 2D/3D 图谱可视化功能，实现了从“知识入库”到“关系展示”的闭环原型。

## 第2章 相关技术与理论基础

### 2.1 知识图谱与图数据库

知识图谱本质上是一种围绕实体、关系和属性组织知识的结构化表示方式。杨波等指出，知识图谱能够通过图结构呈现对象之间的语义关联，因而在风险预警、情报分析和智能决策等任务中具有较高的应用价值[5]。周爱华等在能源数字网络知识图谱构建中也表明，基于大语言模型的抽取结果能够进一步丰富实体、属性和关系三类知识单元，使图谱从静态表示走向可更新、可扩展的知识网络[10]。对于本文系统而言，知识图谱不仅承担知识组织职责，还承担结构化证据提供与可视化展示职责。

在具体实现上，Neo4j 是本文采用的图数据库。吕志锦指出，Neo4j 基于属性图模型，以节点、关系、标签和属性为基本组织单元，并提供 Cypher 查询语言支持复杂关系查询和图数据操作[2]。这种模型非常适合表示文档、目录、知识库、用户及其归属、包含、编辑和关联关系，也便于后续把实体与关系逐步并入现有业务图结构。

除图数据库本身外，图谱系统还需要解决“什么进入图中、什么保留在检索层”的问题。李至颖等的研究表明，在问答系统中采用向量数据库与图数据库协同存储，可以把轻量检索索引与完整实体关系分层组织，从而同时支持高效召回和结构化分析[3]。因此，本文将图数据库定位为结构化知识增强层，而不是与业务主库完全平行的替代存储。

### 2.2 检索增强生成与向量检索

RAG 的核心思想是把外部知识检索结果与用户问题一起提供给大语言模型，从而提升回答的准确性和针对性。吕志锦认为，RAG 通常以向量数据库为检索基础，通过嵌入模型将问题与知识内容表示为向量，再通过相似度计算完成相关内容召回[2]。陈文丽等进一步给出了较完整的工程实现链路，说明检索增强生成本质上是一套由文档处理、向量化、相似度检索、Prompt 构建和回答生成组成的流程化技术体系[7]。

从工程流程看，RAG 往往包括文档预处理、文本切分、向量编码、向量索引、召回排序和答案生成等步骤。高宇德的研究表明，文档切分粒度、预处理质量和上下文组织方式会直接影响问答效果[1]。蔡浩君等在行业知识库场景中进一步强调，原始文档格式转换、文本清洗、分块和索引构建是知识库问答系统稳定运行的前提[8]。因此，向量数据库在本文中承担的并非简单存储向量的职责，而是连接知识库、检索逻辑和生成模型的关键基础设施。

近年来，行业知识库研究又把 RAG 从单一路径语义召回推进到多路证据融合阶段。卓梁雨等提出通过内容标签、结构化关键词和向量召回三路并行来扩大覆盖面，再经过去重、权重融合与重排形成候选证据集合[9]。这一趋势说明，现代 RAG 系统已经不再等同于单一向量搜索，而更接近融合多源信号的混合检索框架。

### 2.3 图谱问答与图谱增强生成

图谱问答强调从问题中识别实体、关系和约束条件，再借助图谱查询获取结构化答案。吕志锦的研究表明，知识图谱能够在垂直领域中为问答系统提供更清晰的关系表达和查询边界[2]。但仅依赖图谱问答也存在表达受限、开放式回答不足等问题。李永春在多模态问答系统中把图谱管理和问答模块联动，实现了答案与图结构的同步返回，说明图谱能力与生成式问答结合后能够同时提升答案解释性与交互体验[6]。

图谱增强生成的价值，就在于让结构化知识和自然语言生成能力形成互补。李至颖等提出的混合存储思路说明，向量数据库适合承载召回友好的轻量表示，而图数据库更适合保留完整实体关系与来源路径[3]。因此，对于领域问答系统来说，图谱模块与向量模块并不是替代关系，而是分别服务于事实型、关系型与开放式问题的两类能力单元。

从系统设计角度看，图谱增强问答至少需要满足三个要求：一是回答过程中能够引入结构化证据；二是最终结果保留来源依据与关系线索；三是当证据不足时具备澄清、拒答或回退机制。肖崇霞关于企业知识问答系统的研究正说明了这一点，即真实系统不仅要生成答案，还要处理权限、版本、来源和风险控制等约束[13]。

### 2.4 多模态文档理解技术

虽然本系统当前已实现的核心能力仍以文本和文档类输入为主，但课题目标本质上面向多模态知识接入场景。常彬彬指出，不同模态数据在特征表示和语义结构上存在明显差异，跨模态语义鸿沟是多模态知识图谱构建的关键难点[4]。杨波等进一步表明，多模态大模型能够协同处理文本、图像等异构信息，为复杂场景中的知识抽取和图谱构建提供新的技术基础[5]。这意味着，多模态系统设计不能只关注支持上传图片，还必须关注如何把图像、表格、版面和文本转换为统一知识表示。

从工程实现角度看，多模态接入并不止于输入扩展，更关键的是中间表示构建。高宇德提出的文档处理流程具有较强参考价值：先进行版面解析和文本提取，再处理公式、表格和图注等内容，最后统一整理为适合后续检索和抽取的结构化文本[1]。这种处理方式能够把原本难以直接利用的 PDF、PPT 或扫描类文档转化为可被机器检索和分析的知识对象。

此外，周爱华等的研究表明，大语言模型可以在多源文本基础上承担实体、属性和关系抽取任务，为图谱构建提供结构化输出[10]。李永春则把图片上传、文本提问和图谱检索结合在一起，说明多模态输入只有真正接入知识组织和问答链路后，才能转化为系统层面的有效能力[6]。因此，本文在系统设计中预留多模态解析和结构化中间表示接口，是一种兼顾当前可行性与后续扩展性的方案。

### 2.5 图谱可视化与交互布局

图谱可视化是知识图谱系统的重要组成部分。对用户而言，图谱的价值不仅在于后台存储，更在于能否通过可视化方式理解节点分布、关系结构、知识密度和局部子图。本文系统在前端采用基于 Graphology 的图数据结构转换与图形布局策略，并结合 2D 与 3D 展示方式完成图谱页面原型。通过图谱统计、节点聚焦、缩放、路径观察和局部浏览等交互能力，用户可直观地理解知识结构。

### 2.6 图谱增强大模型问答方法谱系

在大语言模型快速发展的背景下，图谱增强问答已经不再局限于传统的“语义解析到结构化查询”单一路径，而是逐步形成了多种工程范式。结合现有系统研究，可以将其概括为以下三类。

第一类是**检索编排增强范式**。陈雪松等通过多 Agent 协作方式，把检索、评估、重写和生成组织为可循环的自适应流程，使系统能够根据证据质量动态调整回答路径[11]。这类方法的重点不在于单次召回，而在于围绕回答质量建立持续校正机制。

第二类是**分层架构协同范式**。包晓明和肖崇霞等的研究都采用“数据层 - 检索增强层 - 生成层 - 应用层”或相近的模块化结构，把知识构建、意图理解、检索增强、答案生成和可视化展示组织为闭环路径[12][13]。这一路线强调系统是多模块协作的结果，更适合处理权限、可追溯、知识更新和异常恢复等真实工程问题。

第三类是**图谱管理联动范式**。李永春的研究把知识图谱访问、图谱管理和多模态问答设计为联动模块，使用户在获得答案的同时能够查看相关图结构与知识对象[6]。这种设计对本文具有直接启发：图谱增强问答模块不应只是隐藏在后台的辅助逻辑，而应通过查询接口、子图展示和关系可视化体现其价值。

综合来看，图谱增强大模型问答的演进方向正在从“把三元组塞进提示词”转向“把图谱能力嵌入系统流程”。对于本文系统而言，现阶段最合适的路线不是一步到位追求复杂代理式图推理，而是在现有向量问答、图谱接口和图数据库基础上，逐步实现“问题分类 + 实体定位 + 图查询 + 证据融合 + 答案生成”的分阶段闭环。

### 2.7 文档级关系抽取与实体关系构建研究

本文课题虽然以知识图谱问答系统为目标，但从实现路径上看，实体抽取与关系抽取能力的成熟度会直接决定图谱是否真正具备“语义层”。因此，有必要对文档级关系抽取研究现状进行补充说明。

现有研究已经表明，领域知识图谱构建正在从基于局部文本的抽取方式，逐步转向结合跨段文本、多源异构信息和大模型语义理解的综合抽取方式。杨波等在多模态弱信号知识图谱构建研究中强调，复杂知识抽取往往需要结合多模态线索和跨源语义融合才能获得较完整结果[5]。周爱华等则通过主体、关系、客体三元组抽取和模式链接实践，展示了大语言模型在复杂语境下进行结构化抽取的可行性[10]。

不过，这类方法在真实系统中仍受到实体规范化、抽取稳定性、人工校验成本和推理资源开销等因素制约。因此，对于本文系统而言，更现实的路线是采用渐进式建设策略：先形成文档级关联图谱骨架，再逐步引入实体层、三元组层和来源记录层。李永春关于知识图谱管理与问答联动的研究也说明，图谱系统的工程价值不只体现在抽取得多深，还体现在能否把已有结构有效接入查询和管理流程[6]。

基于这一认识，本文当前阶段优先实现了基于 token 相似度的文档关系构建，以尽快形成可浏览、可统计、可扩展的图谱骨架，并为后续实体抽取与关系补全预留接口。这种做法更符合毕业设计项目在时间、算力和实现复杂度上的约束条件。

### 2.8 多模态文档理解技术比较与启示

多模态知识图谱系统的难点并不仅仅在于“支持上传图片”，而在于如何把图像、版面、文字和结构关系共同转化为可计算、可检索、可推理的知识对象。从近年来的研究来看，面向文档和图像理解的方法大致可以分为三条路线。

第一条路线是**版面解析与 OCR 转写路线**。高宇德给出的文档预处理流程表明，通过版面分析、OCR、公式转写和表格线性化，可以先把复杂文档转换为稳定的文本中间表示，再接入后续检索与图谱构建链路[1]。这种路线的优势在于工程实现较稳健，适合毕业设计当前阶段快速接入 PDF、扫描件和截图类知识。

第二条路线是**混合存储与图谱联动路线**。李至颖和李永春等研究说明，多模态问答系统若要真正发挥图谱价值，需要把向量库中的轻量检索表示与图数据库中的完整关系结构协同管理，并让图谱管理模块与问答模块保持联动[3][6]。这种路线更强调知识对象进入系统后的组织方式，适合支持证据回溯、关系浏览和可解释问答。

第三条路线是**大模型驱动抽取路线**。常彬彬、杨波和周爱华等研究都表明，多模态场景中的关键挑战在于语义对齐、异构融合和结构化抽取，而大模型正逐步成为完成实体、属性和关系抽取的重要工具[4][5][10]。这种路线更强调从多源内容中提炼统一知识表示，为后续构建更深层次的实体关系图谱提供支撑。

将上述路线映射到本文课题，可以形成较清晰的扩展方案：短期内优先采用“版面解析/OCR + 文本清洗 + 向量检索 + 图谱骨架”的稳妥路线；中期逐步引入图谱管理与问答联动能力；长期再探索更深层的大模型驱动多模态抽取与语义融合。由于本文属于毕业设计项目，当前阶段以文本和文档类输入为主、同时预留多模态扩展接口，是更符合实现规律的取舍。

### 2.9 本文技术路线的合理性分析

综合前述研究可以看出，若试图在毕业设计周期内一次性完成“完整的多模态知识图谱问答系统”的全部能力，将同时面临多源接入、实体抽取、关系抽取、图数据库建模、图谱问答、前端可视化、系统部署和量化评估等多重任务，工作量远超一般本科毕业设计的可控范围。因此，本文采取了分阶段、分层次推进的技术路线。

首先，在知识获取层面，优先完成文档、网页和外部订阅内容等文本型知识源的统一接入，使系统具备稳定的数据来源，并为后续多模态扩展保留预处理接口[1]。其次，在问答能力层面，优先构建可运行的基础 RAG 链路，同时为后续引入多路召回、证据重排和自适应生成保留扩展空间[7-9][11]。再次，在图谱层面，优先完成文档、目录、知识库和用户等业务对象的图结构表达，再利用轻量化关系构建策略形成图谱骨架，随后逐步向实体抽取、三元组构建和图谱增强问答演进[6][10]。最后，在交互层面，通过图谱统计、局部子图、关系浏览和死信重放等页面能力，把后端图谱设计真正转化为用户可以感知和管理的系统功能[13]。

这种技术路线的优点在于：一是避免在前期陷入高成本、高不确定性的实体抽取和复杂推理实现；二是保证每个阶段都有可展示的中间成果；三是让系统可以逐步从知识管理平台过渡到图谱增强型问答平台。对于毕业设计而言，这种“先构建骨架、再补齐语义层、最后强化问答层”的策略更加符合项目推进规律。

## 第3章 系统分析

### 3.1 功能性需求分析

#### 3.1.1 面向管理员的功能需求

结合当前系统代码实现情况，管理员端的需求已经明显超出了“上传文档并发起问答”的初级场景，而是形成了一套较完整的知识管理与发布后台。首先，系统需要支持**知识库生命周期管理**。管理员不仅要能够创建知识库，还要完成成员邀请、管理员分配、访问域名设置、版本发布和历史版本查看。也就是说，知识库在系统中不是单纯的逻辑分类标签，而是问答边界、图谱归属边界和公开站点服务边界的统一载体。

其次，系统需要支持**面向真实资料整理场景的文档树管理**。从当前实现看，管理员需要在树形目录中完成文件夹创建、富文本与 Markdown 文档创建、重命名、拖拽移动、删除、发布、发布更新、前台预览和重新学习等操作，还需要支持批量生成摘要、批量移动、批量删除和批量设置权限。这说明系统面对的并非少量样例数据，而是面向持续维护型知识库的运营需求。

再次，系统需要支持**多源知识接入**。在毕业设计场景中，如果系统只能接收手工录入文本，其工程价值会非常有限。因此，本文系统必须支持 PDF、Word、Markdown、HTML 等文档上传，并进一步支持 URL、RSS、Sitemap、Notion、Confluence、Wiki.js、语雀、思源笔记、飞书文档和钉钉文档等外部知识源导入。这样设计的原因在于，真实知识往往散落在不同平台中，系统只有具备“统一接入、统一清洗、统一入库”的能力，才能形成可持续增长的知识基础。

最后，管理员端还需要承担**门户配置、机器人接入、反馈治理和运营分析**等职责。系统不仅要能维护知识内容，还要能够配置公开门户首页、问答提示词、摘要提示词、水印、复制限制、敏感词、评论开关、贡献开关、API Token、MCP Server 与外部机器人渠道。这些功能共同决定了系统是否能够从内部知识整理工具进一步演化为可公开服务、可治理、可运营的平台。

#### 3.1.2 面向访客与外部渠道的功能需求

除了后台管理者外，系统还需要面向公开站点访客与外部渠道调用方提供服务。首先，访客需要具备**公开文档浏览能力**，包括首页导航、目录阅读、文档详情查看、评论互动和无权限提示。对于公开 wiki 站点来说，如果只有问答入口而没有稳定的文档阅读链路，知识展示将缺乏可追溯性，因此文档阅读本身就是系统的重要能力单元。

其次，访客需要具备**两类知识获取模式**。第一类是智能问答模式，系统需要支持基于知识库范围的语义检索、流式回答、历史会话回放、反馈提交和证据片段展示；第二类是仅搜索文档模式，系统需要在不调用生成模型的情况下直接返回相关文档、路径和摘要。这种双模式设计可以同时满足“快速获得自然语言答案”和“优先查看原始证据”两类不同使用偏好。

再次，系统还需要支持**图片辅助提问和移动端/嵌入式接入**。虽然当前阶段的多模态能力尚未完全展开，但系统前端已经存在图片上传、粘贴图片、H5 聊天页和 Widget 聊天页等入口，这表明需求层已经考虑到非纯文本交互与多终端接入场景。对于毕业设计而言，这种“核心文本链路已闭环，扩展交互能力已预留”的做法比空泛描述多模态目标更具说服力。

此外，系统还需要支持**面向外部平台的机器人与 API 服务**。从需求角度看，知识问答能力如果只能在自带网页中调用，其应用半径会明显受限。因此，系统必须具备 OpenAI 兼容接口、Widget 接口，以及面向微信、企微、钉钉、飞书、Lark、Discord 等渠道的对接能力，使知识库能够以机器人方式嵌入不同协作环境中。

#### 3.1.3 核心业务流程需求

为了让功能需求更接近真实系统运行过程，本文进一步把需求梳理为若干必须打通的核心业务流程。

第一，系统必须打通**知识库创建到可问答的闭环流程**。一个知识库从创建开始，需要先建立主数据记录和向量数据集，再接入文档、整理目录、发布版本、构建向量索引，最后对外提供问答与文档浏览服务。如果这一链路中任何一步缺失，系统都只能停留在局部功能演示层面。

第二，系统必须具备**文档变更到增强数据更新的闭环流程**。文档的新增、编辑、移动、删除和权限变更不应只体现在业务数据库中，还需要同步影响向量检索结果与图谱结构。也就是说，系统需要围绕文档变更自动触发向量重建、图谱同步和权限元数据更新，使业务对象、检索索引和图数据库表示保持一致。

第三，系统必须具备**异常恢复流程**。由于本文系统采用 PostgreSQL、对象存储、向量数据库、Neo4j 和消息队列等多组件协同架构，故障不可能完全避免。因而需求分析中必须明确：当图谱同步失败时，系统应能自动重试；当自动重试仍失败时，应能把任务写入死信表；当管理员确认环境恢复后，应能手动重放失败任务。这一流程对于保证图谱层长期可用至关重要。

第四，系统必须具备**内容治理流程**。在公开知识服务场景中，用户不仅会提问，还会提交反馈、发表评论、发起文档贡献。因此，系统需要围绕 AI 问答评价、评论审核、贡献采纳与拒绝、敏感词过滤等环节设计治理能力，使系统不至于退化为只负责“生成答案”的黑盒工具。

#### 3.1.4 典型问题类型与系统响应目标

为了使需求分析更加贴近真实使用场景，本文进一步从用户提问类型角度对系统能力进行拆解。结合当前实现，用户问题大致可以分为五类。

第一类是**事实查询型问题**。这类问题通常关注明确对象与属性，例如“某文档属于哪个知识库”“某个目录下有哪些文件”“某篇资料由谁创建”。该类问题对应的系统目标是返回稳定、可验证、来源清晰的结构化答案，因此更适合通过业务对象关系和图谱查询完成。

第二类是**关联发现型问题**。这类问题关注对象之间的关系网络，例如“与某篇文档最相关的资料有哪些”“两个节点之间是否存在路径”“某个主题在知识库中覆盖了哪些资料”。该类问题要求系统不仅给出答案，还应展示关系依据、路径线索或局部子图，因此对图谱建模、关系构建和可视化能力提出更高要求。

第三类是**开放概括型问题**。这类问题通常没有单一标准答案，例如“请总结某主题的核心内容”“请比较两份资料的异同”“请概括某知识库的关键结论”。这类问题更依赖检索增强生成能力，需要系统先在知识库范围内召回相关证据，再把证据与问题一起交给大语言模型生成自然语言回答。

第四类是**证据优先型问题**。在真实系统中，并非所有用户都希望直接得到生成式答案，一部分用户更希望先查看原文依据。因此，系统需要提供仅搜索文档模式，直接返回标题、路径、摘要和相关片段，用于支持“先找资料、再读原文、最后决定是否追问”的使用方式。

第五类是**多模态扩展型问题**。这类问题关注截图、扫描件、图表或图片辅助提问等非纯文本输入如何被系统利用。虽然本文当前阶段尚未完全实现 OCR 与复杂多模态解析闭环，但需求分析中必须提前考虑其对上传入口、结构化中间表示、检索链路和图谱扩展的影响。正因为存在这类问题，系统在当前实现中保留了图片上传、图片问答入口和多模态扩展接口。

### 3.2 非功能性需求分析

除功能需求外，系统还需要满足一组直接影响系统可落地性的非功能需求。根据企业知识问答系统和自适应 RAG 系统的研究，现代知识问答平台除了“能回答”之外，还必须兼顾可追溯、可治理、可扩展和可恢复等要求[11][13]。结合本文项目特点，主要非功能需求可概括为以下几个方面：

1. **可扩展性。** 后续需要接入实体抽取、关系抽取、OCR、多路召回和图谱问答能力，因此系统设计必须保留模块扩展空间。
2. **可维护性。** 由于系统由多个存储组件和服务构成，各模块边界需要清晰，便于后续调试、替换和局部升级。
3. **可部署性。** 作为毕业设计项目，系统应能通过 Docker Compose 在单机环境中快速部署，并支持答辩场景下的环境复现。
4. **一致性与容错性。** 业务数据和图谱数据之间需要保持较高一致性，图谱同步失败时应具备自动重试、死信落库与人工重放能力。
5. **可观测性。** 系统需要能够通过统计页面、日志、任务状态和图谱浏览方式反映当前运行状态与数据结构。
6. **可追溯性与权限控制。** 回答结果应尽可能关联到具体知识来源、知识库范围和版本上下文，并在查询链路中执行权限校验[13]。
7. **性能与成本平衡。** 系统既要保证检索和问答体验，又要兼顾单机部署条件下的资源消耗，避免过度依赖高算力组件[11]。

上述非功能需求决定了本文系统不能被设计成单一问答脚本，而必须是一个具备分层治理能力的知识服务平台。

#### 3.2.1 非功能需求之间的约束关系

在系统设计中，各项非功能需求并不是彼此孤立的，而是相互制约、相互影响。例如，可扩展性要求系统采用分层和解耦架构，但分层越清晰，组件数量往往越多，一致性与可观测性的设计压力也会随之上升。再如，可追溯性要求系统保留更多证据和上下文信息，而这又可能带来额外的存储开销与响应延迟，因此必须在性能和成本之间做平衡。

对于本文系统而言，最关键的一组约束关系体现在“智能性、解释性与工程性”的三方平衡上。如果过分强调智能生成效果，系统可能很快做出回答，但难以说明回答依据；如果过分强调结构化解释，系统可能在开放式问题上显得僵硬；如果只强调工程可用性，则系统又可能退化为普通的文档管理平台。因此，本文在系统设计中选择把向量问答、图谱管理和证据治理并行纳入架构，而不是只保留其中某一项能力。

此外，毕业设计项目还面临时间和资源边界，这使得一些非功能需求必须以“阶段性达成”的方式实现。例如，本文通过死信重放和重试补偿保障故障恢复，但尚未建立完整的链路监控与自动告警；通过统一知识库范围控制回答边界，但尚未实现更细粒度的字段级或属性级权限约束；通过保留 OCR 与实体抽取扩展位满足可扩展性，但尚未形成完整多模态闭环。明确这些约束关系，有助于后续在论文中更客观地说明系统边界与改进方向。

### 3.3 系统可行性分析

#### 3.3.1 技术可行性

本项目围绕自主设计与实现的 Mindweave 平台展开，系统从 0 开始完成总体架构规划与核心模块落地。后端采用 Go，前端采用 React 与 TypeScript，图数据层采用 Neo4j，向量检索链路采用 Qdrant 与 Raglite，多组件之间通过 Docker Compose 进行统一编排。这些技术均拥有成熟的社区生态和明确的工程实践路径，能够支撑毕业设计原型系统的实现。

从系统目标看，本文并未将目标设定为一次性完成完整的多模态实体抽取与复杂图推理，而是优先完成“知识接入、向量问答、图谱建模、图谱同步、图谱可视化”这一可验证闭环，因此技术风险处于可控范围内。现阶段尚未完全落地的实体抽取、OCR 和图谱问答能力，也已在数据模型和接口层预留扩展空间，具备逐步演进条件。

#### 3.3.2 开发可行性

从开发过程看，系统采用模块化、分阶段的方式从 0 开始搭建核心业务能力。知识接入、用户管理、文档管理、基础问答、图谱建模与可视化等模块按照统一架构逐步实现，毕业设计工作进一步聚焦于图谱增强相关能力，包括图数据库接入、图谱同步补偿、文档关系构建、图谱查询接口和图谱可视化页面等。这种“先完成系统骨架、再逐步补齐增强能力”的开发方式，既控制了实现复杂度，也更符合毕业设计的时间边界。

同时，项目文档、数据库脚本和技术方案已经较为完整，便于围绕当前成果继续迭代。当前系统已形成阶段性原型，说明整体开发路径具备现实可行性，后续工作主要集中在功能补全、实验验证和论文完善。

#### 3.3.3 应用与经济可行性

本系统主要面向个人知识管理、小型团队资料整理和课程学习辅助场景，部署方式以单机或轻量服务器为主，对硬件资源要求相对可控。系统采用的 PostgreSQL、Redis、MinIO、Qdrant、Neo4j、NATS 等组件均可在本地或普通云主机环境下部署，软件层成本较低，适合毕业设计项目实现。

从应用价值看，系统能够解决文档知识分散、关系组织能力弱、问答结果可解释性不足等问题，具备明确的使用场景和展示价值。即便在毕业设计阶段尚未完全实现真正多模态输入闭环，当前原型系统仍已具备较好的功能可演示性和后续扩展潜力，因此在应用和经济层面均具有可行性。

### 3.4 本章小结

本章从功能需求、非功能需求和系统可行性三个层面对项目进行了分析。分析结果表明，本文系统在研究目标、技术路线、开发方式和应用场景上均具备较好的可实施性。基于上述分析，下一章将进一步展开系统设计，包括总体架构、功能模块、图谱数据模型、部署方案以及一致性与容灾机制等内容。

## 第4章 系统设计

系统设计章节主要解决“系统如何被组织和构建”的问题。结合前一章的需求分析结果，本章从系统总体架构、功能模块、数据流、图谱数据模型、部署方式以及一致性设计等角度，对系统方案进行详细说明，为后续系统实现章节提供设计依据。

### 4.1 系统总体架构设计

结合上述需求，本文设计了分层、模块化的总体架构。该设计借鉴了知识问答系统中“模块化分层 + 数据流驱动”的思路，把知识接入、检索增强、图谱构建、答案生成和可视化展示组织为一个相对闭环的处理链路[12][13]。系统整体可以分为前端展示层、应用服务层、异步处理层和数据存储层四部分。

#### 4.1.1 前端展示层

前端展示层主要由 React + TypeScript 构成，负责知识库管理、文档交互、问答界面以及知识图谱可视化页面。其中，图谱管理页面支持图谱统计、节点关系探索、2D/3D 展示切换以及死信重放操作，是本文新增的重要功能模块。

#### 4.1.2 应用服务层

应用服务层以 Go 后端为核心，负责知识库、用户、文档、图谱查询、图谱同步、问答链路、证据组织和业务权限等逻辑。应用层通过统一接口对外提供服务，并通过 UseCase 模式组织核心业务逻辑。对于问答链路而言，该层不仅承担请求转发职责，还承担问题范围限定、知识库路由、检索上下文组织和结果返回格式控制等职责，使系统能够从“功能接口集合”进一步提升为“具备流程约束的问答平台”。

#### 4.1.3 异步处理层

系统通过 NATS 实现消息驱动的异步处理机制。当文档内容变化需要更新向量索引，或业务对象变化需要同步图谱时，异步机制可以降低同步链路对主业务操作的阻塞影响。对于图谱更新失败的场景，系统进一步通过死信表持久化任务信息，支持后续重放。

#### 4.1.4 数据存储层

数据存储层采用多存储协同方案：

1. PostgreSQL 负责保存结构化业务数据；
2. Redis 负责缓存与会话辅助；
3. MinIO 负责文档对象存储；
4. Qdrant 负责向量索引与语义检索；
5. Neo4j 负责图谱存储与图查询；
6. Raglite 负责向量化与 RAG 服务能力。

这种混合架构虽然比单一数据库方案更复杂，但能够在不同数据类型之间实现职能分工，更符合系统的实际业务特征。李至颖等的研究表明，向量数据库适合保存切分片段、轻量索引和快速召回所需信息，而图数据库更适合保留实体与关系的完整结构[3]；陈文丽和蔡浩君等的研究也说明，在知识库问答系统中把原始文档、结构化元数据、向量索引和关系网络分层组织，更有利于系统性能和可维护性[7][8]。因此，本文的数据存储层采用“主业务库 + 对象存储 + 向量库 + 图数据库”的协同方案，而不是试图用单一存储承担全部职责。

### 4.2 功能模块设计

#### 4.2.1 知识库与发布管理模块

知识库与发布管理模块负责维护系统的逻辑服务边界，是整个系统的根模块。该模块不仅用于保存知识库名称和访问配置，还承担向量数据集初始化、成员权限管理、版本发布和公开服务边界管理职责。具体而言，知识库创建时需要先初始化向量数据集，再建立业务主记录，并在图数据库中创建对应的 `KnowledgeBase` 节点；版本发布时则需要把草稿文档固化为发布快照，并将发布内容异步投递到向量链路。这样设计的意义在于，将“内容编辑态”和“对外服务态”区分开来，使公开问答和公开站点读取的是稳定版本而非任意草稿状态。

#### 4.2.2 知识接入与文档管理模块

知识接入与文档管理模块是系统最重要的数据入口。该模块既要支持树形目录下的文件夹与文档管理，也要负责多源内容导入、对象存储写入、元数据维护、文档属性设置与批量治理。设计上，系统把所有来源的知识统一归约为 `Node` 节点对象，使上传文件、网页导入、第三方平台迁移和手工编辑最终汇聚到同一业务模型之中。这种“统一文档对象”的设计使后续发布、向量化、图谱同步和前台展示都建立在相同的数据基础上，避免多条数据链路并存带来的复杂性。

#### 4.2.3 门户站点与多渠道服务模块

与许多只提供后台和测试页的毕业设计不同，本文系统将公开站点本身视为独立模块进行设计。该模块需要支持动态门户首页、公开文档阅读页、AI 问答弹窗、仅搜索文档模式、评论区、贡献入口、Widget 嵌入式机器人以及 OpenAI 兼容接口和多平台机器人接入。设计上，后台通过统一设置页维护站点主题、页面组件、目录展示、SEO、提示词、免责声明、机器人参数和接入地址；前台则根据配置动态渲染首页与对话入口。这样一来，系统不只是“后台可运行”，而是真正具备可对外服务的知识门户特征。

#### 4.2.4 向量检索与对话问答模块

该模块负责文档发布后的向量索引维护，以及在对话阶段完成语义召回、上下文拼装、答案生成和结果回传，是当前系统中最成熟的智能能力模块。与传统全文检索相比，该模块不仅需要完成相似内容召回，还要在知识库边界、用户权限、提示词模板、会话上下文、证据组织和流式返回格式之间做好编排。基于此，本文将其定位为“检索增强对话模块”而非单纯的向量查询模块。后续若继续扩展关键词召回、标签召回、结果重排或图谱证据融合，也仍然可以在这一模块边界内演进[7-9]。

从实现形态看，该模块至少包含三层职责。第一层是**知识库级数据集管理**：每个知识库在创建时都会向向量服务申请独立的 `dataset_id`，从而把问答范围天然限制在知识库边界内。第二层是**异步索引更新**：文档发布、重新学习和权限变更并不直接阻塞主业务请求，而是通过消息队列投递 `NodeReleaseVectorRequest`，由向量消费者异步完成写入、删除或权限元数据更新。第三层是**对话编排**：公开站点、Widget、机器人和 OpenAI 兼容接口虽然入口不同，但最终都会汇聚到统一的对话用例中，完成会话管理、证据回显和流式输出。

因此，本文系统中的 RAG 并不是“调用一次向量搜索再拼接 Prompt”那样的简单原型，而是围绕知识库生命周期、发布版本、权限控制和会话状态构建起来的一条完整工程链路。这种设计也为后续引入图谱证据、查询路由和混合问答保留了明确接口位置。

#### 4.2.5 图谱构建、同步与恢复模块

图谱模块在本文中并非单一的 Neo4j 读写封装，而是由图数据建模、增量同步、关系构建、失败补偿和人工恢复共同组成。具体来说，该模块需要把知识库、文件夹、文档和用户等业务对象映射为图节点，并根据归属、包含、创建和相似关系形成可查询图结构；同时，它还需要监听文档和目录的新增、更新、移动和删除操作，把这些变化可靠地同步到 Neo4j 中。当同步失败时，模块应执行自动重试、指数退避、死信落库与人工重放，从而保证图谱层不会长期偏离业务层。这一模块是本文最具工程特色的部分。

#### 4.2.6 图谱查询与可视化模块

该模块负责把后端图数据库能力转化为管理员可感知的功能。系统不仅提供全图读取、局部子图、路径查询、图谱统计和实体搜索接口，还提供支持 2D/3D 切换的图谱管理页面，使管理员能够直接观察节点规模、边数量、知识密度和异常任务状态。这样设计的目的在于让图谱从“后台增强存储”变为“前台可操作对象”，从而提升系统的可解释性与可维护性[6]。

#### 4.2.7 权限治理与运营分析模块

在真实知识服务场景中，系统不能只追求“能回答”，还必须解决回答边界、内容可见范围、敏感词治理、用户反馈、评论审核、贡献处理和访问统计等问题。因此，本文将权限治理与运营分析作为独立模块看待。该模块一方面通过可见、可访问、可问答三级权限以及用户组策略控制知识暴露范围，另一方面通过统计页、对话记录页、反馈页和贡献审核页支持后续运营和改进。它是保证系统从原型走向可运维平台的重要支撑模块。

### 4.3 数据流设计

系统的数据流不能简单概括为“上传文档后即可问答”，而应视为围绕统一业务主数据展开的三条并行链路：发布链路、检索链路和图谱链路。

#### 4.3.1 内容入库与发布链路

第一条链路是内容入库与发布链路。用户上传文档或导入网页内容后，系统先把原始内容写入对象存储，再在 PostgreSQL 中保存文档元数据、目录位置、创建者和权限信息。处于编辑态的文档并不会立即直接进入公开问答，而是在发布动作发生后生成发布快照。随后，系统以发布快照为粒度，把内容投递到向量索引链路。这种做法的好处在于，公开问答面向的是稳定版本，避免未完成编辑的内容直接影响外部服务。

#### 4.3.2 权限感知的检索增强链路

第二条链路是检索增强问答链路。当用户从公开站点、Widget 或机器人入口发起提问时，请求首先进入应用层，由 `ChatUsecase` 解析知识库范围、应用类型、会话上下文和当前用户组信息。系统会先根据知识库和入口类型确定当前应用实例，读取推理模型配置，并通过 `conversation_id + nonce` 机制创建或续接会话。随后，用户问题会被先行写入会话消息表，再经过敏感词检测和权限组解析，以确保后续检索与生成都建立在合法上下文之上。

在检索阶段，`LLMUsecase.BuildConversationMessageWithRAG` 会先重建历史消息，再读取知识库级提示词配置，并以 `dataset_id` 为边界调用 Raglite 检索服务。当前实现中，检索请求除了携带用户问题外，还会携带多轮历史消息、用户所属 `group_ids`、相似度阈值等信息，使检索服务能够执行带权限约束的上下文感知召回。Raglite 返回结果后，系统并不会直接把原始 chunk 送入模型，而是继续根据 `doc_id` 回查发布文档信息，补全节点名称、摘要、目录路径等业务字段，再将片段按文档聚合为可读性更强的证据集合。

在生成阶段，系统会把系统提示词、改写后的问题和整理后的证据文档统一格式化为模型消息序列，再通过流式接口调用大语言模型。前端持续接收 `conversation_id`、`nonce`、`message_id`、证据块 `chunk_result`、答案增量 `data`、错误事件与完成事件 `done`。当模型支持思维链内容时，系统还会额外回传 `<think>...</think>` 段落。最后，完整回答及其 `prompt_tokens`、`completion_tokens`、`total_tokens` 会被持久化到会话消息表中，从而形成可回放、可反馈、可统计的真实交互记录。

#### 4.3.3 图谱同步与恢复链路

第三条链路是图谱同步与恢复链路。知识库、目录、文档和用户等业务对象在新增、更新、移动、删除时，会异步触发图谱同步任务。同步成功后，系统在 Neo4j 中维护对象节点、归属关系、层级关系和文档相似关系；同步失败时，则进入自动重试流程。若达到最大重试次数仍未成功，系统会把任务写入死信表，并在图谱管理页提供人工重放入口。这样设计使图谱层能够在不阻塞主业务流程的前提下实现最终一致性。

总体而言，本文系统的数据流体现出一个鲜明特点：**PostgreSQL 负责主事实，向量库负责召回友好表示，Neo4j 负责关系友好表示，三者围绕统一业务对象协同工作**。发布链路保证对外内容稳定，检索链路保证智能问答可用，图谱链路保证知识结构可解释，三条链路共同构成了完整系统闭环。

### 4.4 图谱数据模型设计

根据当前实现，本文并没有一开始就直接构建“全文实体图谱”，而是先围绕稳定的业务对象建立属性图模型，再逐步向实体层扩展。当前已实际进入图数据库的节点类型主要包括：

1. `Document`：表示发布后的文档对象，核心属性包括 `id`、`name`、`tokens`、`token_count`、`kb_id`、`status`、`visibility`、`creator_id`、`editor_id`、`created_at` 和 `updated_at`；
2. `Folder`：表示目录对象，核心属性包括 `id`、`name`、`kb_id`、`parent_id`、`position` 和 `created_at`；
3. `KnowledgeBase`：表示知识库根节点，核心属性包括 `id`、`name` 和 `created_at`；
4. `User`：表示创建者或内容维护者，核心属性包括 `id`、`account`、`role` 和 `created_at`；
5. `Entity`：作为后续实体抽取扩展位预留，支持未来挂接 `name`、`type`、`aliases`、`description`、`confidence` 等属性。

与上述节点对应的关系类型包括：

1. `CONTAINS`：目录包含文档或目录；
2. `BELONGS_TO`：文档或目录归属于某个知识库；
3. `CREATED_BY`：文档由某用户创建；
4. `RELATED_BY_KEYWORD`：同一知识库内文档间基于 token 重叠建立的相似关系；
5. `MENTIONS` 与 `RELATES_TO`：为实体抽取与实体关系扩展预留的关系类型。

需要说明的是，当前实现中“编辑者信息”主要以 `editor_id` 文档属性形式保存，而不是额外落成一条显式 `EDITED_BY` 边。之所以采用这种设计，是因为当前阶段图谱的主要目标是先稳定承载知识库、目录、文档和用户之间的骨架结构，再在此基础上逐步补充更细粒度的语义边。

在 Neo4j 中，为支持节点唯一识别与查询性能优化，系统对 `Document`、`Folder`、`Entity`、`User`、`KnowledgeBase` 的 `id` 字段设置唯一约束，并对文档名称、文档所属知识库、实体名称、实体类型和实体所属知识库等字段建立索引。这种设计既满足当前图谱浏览、过滤和统计需求，也为后续实体抽取与查询扩展提供了性能基础。

### 4.6 系统设计原则

为了保证系统不仅能够“实现功能”，还能够在毕业设计场景下体现完整的软件工程思路，本文在总体设计中遵循了以下原则。

第一，遵循**渐进式增强原则**。系统不以一次性完成全部多模态能力、实体抽取能力和复杂图谱问答能力为目标，而是优先完成最基础、最关键、最可验证的闭环。在此基础上逐步增强知识接入深度、图谱语义层次和推理复杂度。这一原则保证了项目在时间有限的条件下仍具有阶段性成果。

第二，遵循**解耦与分层原则**。文档管理、向量检索、图谱建模、图谱同步和可视化展示分别由不同模块承担，各模块之间通过明确接口协作，避免强耦合导致后期难以维护。例如，图谱模块并不直接承担文档切分任务，向量问答模块也不直接负责图数据库写入，从而降低了模块边界混乱的风险。

第三，遵循**可解释性优先原则**。毕业设计中的智能系统往往容易过度追求“能回答问题”，却忽略了结果是否可解释。本文在系统设计中强调结构化图谱的重要性，目的是在问答之外提供可视化关系网络、节点统计和路径查询能力，让知识来源与关系结构可以被观察、分析和验证。

第四，遵循**失败可恢复原则**。在涉及多数据库和异步处理的系统中，失败并不是异常情况，而是常态之一。若系统只设计成功路径，则实际运行中极易出现状态漂移。本文通过自动重试、指数退避和死信重放机制，使图谱同步在失败时仍有恢复手段。

第五，遵循**面向扩展原则**。虽然当前阶段多模态能力尚未闭环，但系统已经为 `Entity` 节点、实体搜索接口和图谱扩展关系预留了设计空间。这意味着后续新增 OCR、关系抽取、图谱问答时，无需推翻现有架构，只需在既有骨架上继续扩展。

### 4.7 角色分析与业务用例设计

从使用对象来看，本文系统主要面向三类角色：系统管理员、普通知识库用户以及系统维护者。

系统管理员是最核心的使用角色，主要负责创建知识库、维护文档目录、导入知识来源、查看图谱统计、执行图谱关系构建和重放死信任务。普通知识库用户主要面向问答和知识浏览场景，其关注点在于知识检索效率和答案质量。系统维护者则更关注部署、服务状态、日志、同步异常和数据库运行情况。

围绕上述角色，系统设计了若干关键业务用例：

1. **知识导入用例。** 管理员将 PDF、Markdown 或网页内容导入系统，系统保存文档并触发后续向量化与图谱同步。
2. **知识问答用例。** 用户在指定知识库范围内发起问题，系统执行向量召回并返回回答。
3. **图谱浏览用例。** 管理员进入图谱页面，查看某知识库内的节点规模、边类型分布和局部关系结构。
4. **关系构建用例。** 管理员手动触发文档关系构建逻辑，使系统为文档之间建立关联边。
5. **同步恢复用例。** 当图谱同步失败后，管理员通过死信重放接口重新执行失败任务，恢复图谱一致性。

从业务角度看，这些用例共同组成了一个完整闭环：知识导入保证数据来源，问答与浏览体现知识使用价值，关系构建体现图谱增强价值，而同步恢复体现系统运行可靠性。

### 4.8 数据一致性与容灾设计

在单数据库系统中，事务一致性通常由数据库自身保障；但在本文所设计的多存储协同架构中，知识对象需要同时在 PostgreSQL、MinIO、Qdrant 和 Neo4j 等组件之间流转，因此一致性问题更加复杂。特别是图谱数据库和业务数据库之间，天然存在“主数据在业务库、增强数据在图谱库”的双写问题。

为降低双写带来的一致性风险，本文采用“业务数据库为主、图数据库为增强层”的一致性策略。也就是说，PostgreSQL 中的知识库、文档、用户和目录数据被视为主事实来源，而 Neo4j 中的数据被视为结构化增强表示。当二者不一致时，应以业务数据库为准，通过补偿逻辑修正图谱层，而不是反向覆盖业务层。

从故障场景来看，系统可能遇到以下几类问题：

1. 业务数据写入成功，但图谱同步失败；
2. 图谱写入时遇到网络中断或数据库不可达；
3. 消息消费顺序波动导致局部状态暂时不一致；
4. 某些图谱节点已删除，但后续同步任务仍尝试更新。

针对这些问题，本文在设计上采用最终一致性而非强一致性思路。也就是说，系统允许图谱层在短时间内落后于业务层，但通过重试和补偿机制保证其最终收敛到正确状态。陈雪松和包晓明等研究都说明，在多阶段问答系统和多组件检索系统中，把失败任务显式记录并支持后续重放，是提高系统韧性的有效手段[11][12]。对于毕业设计原型而言，这种设计在工程复杂度和系统鲁棒性之间实现了较好的平衡。

### 4.9 数据库与消息流设计

为了更加清晰地说明各类数据在系统中的流动方式，本文对主要存储组件的职责进行进一步分析。

PostgreSQL 负责保存系统的业务主数据，例如知识库信息、文档节点、目录层级、用户信息和死信记录等。它承担事务一致性与业务状态管理职责，是整个系统的事实基础。MinIO 负责保存文档原始内容及衍生文件，解决大文件与结构化元数据不适合共存于数据库中的问题。Qdrant 与 Raglite 负责文档切分后的语义索引，使系统具备向量检索能力。Neo4j 负责将文档对象和关系对象图结构化，使知识组织方式从树状和列表式表达进一步提升到网络式表达。NATS 则作为消息中间层，承担异步通知与解耦职责。

从消息流角度看，一次典型文档新增操作通常会触发两条后续链路：一条是向量更新链路，一条是图谱同步链路。前者面向语义问答，后者面向结构化知识组织。二者虽然服务目标不同，但都依赖文档这一共享业务对象，因此其一致性控制必须回到统一的业务主库之上。若后续扩展多路召回与多 Agent 编排能力，则消息层还可以承担检索评估、任务调度和阶段状态传递职责，使系统在不阻塞主流程的情况下完成更复杂的问答增强逻辑[9][11]。

### 4.10 本文方案的创新点与实现难点

从毕业设计视角看，本文的创新性并不主要体现在提出全新的理论模型，而体现在对现有知识管理平台的结构化增强与系统化整合上。具体而言，本文的创新点主要体现在以下几个方面。

第一，本文将传统知识库系统中的文档、目录、用户和知识库对象统一映射到图数据库中，使得知识组织不再局限于目录树和文档列表，而能够形成具备网络结构特征的知识图谱。

第二，本文设计了图谱同步补偿机制，将自动重试、指数退避、死信落库与人工重放整合到统一链路中，使图谱层具备较好的故障恢复能力。这一设计在毕业设计项目中较为少见，体现了对系统健壮性的主动考虑。

第三，本文在实体层尚未完全闭环的情况下，采用文档级关系构建作为过渡方案，并为后续多路召回、图谱增强问答和多模态预处理预留扩展接口，使图谱能够在当前阶段提前发挥作用，同时保持后续演进空间[3][9]。这种“先形成图谱骨架，再逐步补齐语义层”的实现路径具有较强的工程实践价值。

当然，本文方案也存在明显实现难点。最大的难点之一是多存储协同带来的数据一致性问题；第二个难点是如何在时间有限的条件下平衡图谱深度和系统可完成度；第三个难点是如何让图谱模块真正服务于问答和管理，而不是停留在展示层。正是围绕这些难点展开的取舍与实现，构成了本文工作的核心内容。

### 4.11 本章小结

本章在需求分析的基础上，对系统的总体架构、功能模块、数据流、图谱数据模型、部署方式以及一致性与容灾机制进行了设计说明。通过将业务数据层、向量检索层和图谱增强层进行分工协同，系统形成了较为清晰的结构边界和可扩展方案。上述设计为后续系统实现章节中的模块落地、接口实现和页面构建提供了直接依据。

## 第5章 系统实现

### 5.1 本章概述

本章在前一章系统设计的基础上，进一步说明系统各核心模块的具体落地方式。与第 4 章侧重总体架构、数据模型和设计原则不同，本章重点描述系统功能模块的实现路径、关键接口、处理流程以及工程细节，体现从设计方案到可运行原型的转换过程。

结合本文系统的实际实现情况，本章将系统划分为知识接入与文档管理模块、向量检索与问答模块、图谱存储与关系构建模块、图谱同步与故障恢复模块、图谱查询与可视化模块，以及图谱增强问答扩展模块。每个模块均从模块职责、功能设计、实现过程和模块分析等层面进行说明，最后补充典型业务流程、权限控制与异常处理，以体现系统从设计方案到工程实现的完整性。

### 5.2 知识接入与文档管理模块设计与实现

#### 5.2.1 模块职责

知识接入与文档管理模块是整个系统的数据入口，也是向量检索、公开站点和知识图谱三条后续链路的共同基础。该模块的核心职责不仅是“把文件存起来”，而是把来自不同来源的内容统一抽象为系统中的节点对象，并同时维护其目录位置、知识库归属、创建者、发布状态、权限属性和后续增强处理状态。

从业务语义上看，系统中的文档并非孤立文本，而是一个具备完整生命周期的知识对象。一个文档在创建之后，可能经历编辑、发布、重新学习、生成摘要、权限调整、移动目录、公开展示和删除等多个阶段。因此，本模块需要同时承担编辑态管理和服务态准备两方面职责：前者负责保证管理员能够高效整理知识内容，后者负责保证后续问答与图谱链路能够基于稳定、清晰、可追踪的数据运行。

#### 5.2.2 功能设计

围绕上述职责，知识接入与文档管理模块主要实现以下功能：

1. 文档上传与基础校验；
2. URL、RSS、Sitemap 与第三方平台内容导入；
3. 文件夹与文档树管理；
4. 富文本与 Markdown 两种编辑形态；
5. 文档发布、发布更新与前台预览；
6. 文档重新学习、摘要生成与批量治理；
7. 文档属性设置与权限管理；
8. 文档移动、删除与关联增强数据清理。

从具体实现看，系统将“创建文件夹”“创建富文本”“创建 Markdown”“通过离线文件导入”“通过 URL 导入”“通过 RSS 导入”“通过 Sitemap 导入”“通过 Notion/Confluence/Wiki.js/语雀/思源/飞书/钉钉等导入”统一放在文档树操作菜单中，说明前端交互层已经把多源接入视为日常知识整理操作的一部分，而不是附属工具。与此同时，文档页还提供“发布文档”“发布更新”“重新学习”“文档属性”“前台查看”以及批量生成摘要、批量移动、批量删除、批量设置权限等功能，这些能力共同构成了可维护、可治理的知识管理后台。

#### 5.2.3 实现过程

在实现层，文件与导入相关能力分别由文件接口和爬虫接口承载。前者负责处理离线文件、任意文档和 URL 上传，后者负责处理外部站点与第三方知识平台内容抓取。无论入口来自本地文件还是外部系统，最终都会被整理为统一的节点记录，并在业务库中保存名称、类型、知识库 ID、父节点 ID、创建者、编辑者、状态和权限信息。

当管理员在文档树中创建或编辑文档时，系统首先更新业务主库中的节点信息，然后异步触发图谱同步；当管理员执行发布操作时，系统会把当前文档固化为发布快照，再通过消息队列把发布内容投递给向量索引链路。这样设计的意义在于，向量问答读取的是已发布版本而不是实时草稿，从而保证公开服务稳定。若管理员对文档进行了较大修改，可通过“重新学习”操作再次投递向量更新任务；若管理员只希望补充概要信息，则可以直接触发摘要生成任务。

对于权限修改，系统采用较为完整的处理策略：当管理员调整文档的“可被问答”权限时，后端不仅更新节点权限字段和关联用户组，还会把新的 `group_ids` 元数据异步回写到向量服务中，使后续召回结果天然具备权限感知能力。对于删除操作，系统则会同步执行节点删除、旧文档索引清理以及图数据库中的节点删除，避免业务主库、向量库和图谱库之间出现长期残留数据。

从实现路径看，本文并没有把“上传”“编辑”“发布”“重建索引”“图谱同步”拆成互不相关的多个系统，而是围绕统一节点模型组织整个内容链路。这一做法大大降低了模块耦合度，也使论文后续对于发布机制、问答机制和图谱机制的描述能够建立在共同数据模型之上。

#### 5.2.4 模块特点分析

该模块的特点主要体现在三个方面。其一，它是系统中最典型的“用户可见功能与后台增强链路耦合”模块，管理员看到的是上传、导入、发布和权限操作，而系统内部实际会触发对象存储写入、发布快照创建、向量更新、图谱同步和权限元数据传播等多步处理。其二，它通过“编辑态文档 + 发布态快照”的分层设计，把后台整理过程与公开服务过程区分开来，保证了问答与公开站点读取内容的稳定性。其三，它天然为多模态扩展预留了入口。目前系统尚未完全实现 OCR、版面分析和复杂图像理解，但上传接口、图片问答入口和统一节点模型已经为后续把扫描件、截图或图表内容转化为知识对象提供了结构基础。

### 5.3 向量检索与问答模块设计与实现

#### 5.3.1 模块职责

向量检索与问答模块是当前系统最成熟、最直接体现“智能性”的模块，其职责不仅是把文档转化为可检索的向量，还包括维护知识库级数据集、生成和更新文档索引、基于权限执行召回、组织会话上下文、流式返回答案与证据，并把整个对话过程沉淀为可回放、可统计的会话记录。

从系统定位来看，该模块既承担当前阶段的主要问答能力，也承担对后续图谱增强问答的支撑职责。也就是说，本文并没有把图谱模块设计成向量问答的替代者，而是先通过该模块形成稳定、可演示、可持续迭代的基础问答能力，再为后续结构化增强留下接口空间。

#### 5.3.2 功能设计

该模块主要包括以下功能：

1. 文档切分；
2. 文本向量化；
3. 向量索引写入与更新；
4. 语义检索与召回；
5. 权限感知的结果过滤；
6. 上下文拼接与大模型问答；
7. SSE 流式输出；
8. 会话历史管理与消息持久化；
9. 仅搜索文档模式；
10. 图片辅助提问与反馈提交。

与传统全文检索不同，本文系统中的语义检索能力并不是孤立调用向量库，而是围绕知识库、用户组权限和会话历史组织起来的检索增强链路。具体而言，系统不仅要找到“语义上相关”的文档片段，还要保证这些片段满足当前用户的访问边界，并以适合大模型理解的形式拼装为上下文。与此同时，前端问答页还需要接收检索证据块、思考过程、答案流、消息 ID 与完成事件，说明该模块在设计上天然是“检索 + 对话 + 前后端交互协议”的复合模块。

#### 5.3.3 实现过程

系统在知识库创建时会先调用向量服务创建独立数据集并获得 `dataset_id`。这一标识被持久化到知识库主记录中，后续所有向量写入、检索和状态同步都围绕该 `dataset_id` 展开。与“直接对当前编辑内容做实时嵌入”的方式不同，本文系统以“发布快照”为索引单位：当管理员执行发布或重新学习操作时，后端并不会在主线程中直接写向量库，而是将 `NodeReleaseVectorRequest` 投递到 `VectorTaskTopic`。向量消费者收到消息后，再读取对应的文档发布快照、目录路径和权限信息，并调用 Raglite 执行 `upsert`、`delete`、`summary` 或 `update_group_ids` 等操作。

在向量写入阶段，系统已经体现出较强的工程化细节。其一，若原始内容为 HTML，则会先转换为 Markdown 后再上传到 Raglite，以尽量保留标题、列表、段落等结构信息，同时减少富文本噪声。其二，消费者会在写入时同步获取节点的 `answerable` 用户组，并把 `group_ids` 作为文档元数据一并写入向量服务，使后续检索天然具备权限过滤能力。其三，Raglite 成功写入后返回的 `doc_id` 会被反写到发布记录中，旧版本文档对应的旧 `doc_id` 则会被进一步清理，从而避免同一节点多次发布后在向量层残留历史脏数据。其四，Raglite 的文档状态回调还会通过事件机制更新业务库中的 `rag_info.status`、`message` 与同步时间，使索引状态对管理员可见。

在问答阶段，系统由 `ChatUsecase.Chat` 统一接管各类入口请求。该用例首先根据知识库和入口类型确定应用实例，随后读取当前对话模型配置。若是新会话，则生成新的 `conversation_id` 和 `nonce`；若是历史会话，则校验 `nonce` 是否匹配，以防止外部伪造会话继续写入。完成会话建立后，系统会把用户问题写入会话消息表，执行敏感词检测，再根据当前认证信息解析用户所属的权限组。只有经过这些准备步骤后，请求才会真正进入检索增强链路。

检索增强逻辑在 `LLMUsecase.BuildConversationMessageWithRAG` 中完成。系统会先读取当前会话的历史用户消息与助手消息，并按知识库设置读取自定义系统提示词；随后调用 `GetRankNodes`，进一步通过 `rag.QueryRecords` 向 Raglite 发起检索请求。该请求会携带 `dataset_id`、用户问题、历史消息、`group_ids`、相似度阈值和每篇文档最大返回 chunk 数等参数。当前实现中，向量服务默认返回前 10 个候选片段，并可基于历史对话对用户问题进行改写。后端收到结果后，再根据 `doc_id` 反查发布节点信息，把文档标题、摘要、目录路径和 chunk 内容整理为统一的证据文档结构，再与系统提示词、改写问题和当前日期共同组织成模型输入。

在生成阶段，系统采用 SSE 持续向前端返回多类事件：包括会话 ID、`nonce`、消息 ID、证据块 `chunk_result`、答案增量 `data`、错误信息和完成信号 `done`。如果模型支持思维链内容，系统还会把 reasoning 内容包裹为 `<think>...</think>` 段落单独流出。生成结束后，后端将完整回答、消息父子关系以及 `prompt_tokens`、`completion_tokens`、`total_tokens` 等用量指标写入会话消息表，并同步更新模型使用统计。由此，当前 RAG 模块已经形成了“数据集管理 - 异步索引更新 - 权限感知检索 - 证据回显 - 流式生成 - 会话落库”的完整工程闭环。

除标准问答外，系统还实现了仅搜索文档模式。该模式复用同一套权限感知召回逻辑，但不再调用大语言模型，而是直接返回相关文档列表、路径、摘要和片段。这样既能作为问答功能的轻量降级路径，也能服务于“先看证据再决定是否继续提问”的用户习惯。

#### 5.3.4 模块局限

该模块的优势在于开放式问题响应快、工程链路成熟、可直接服务前台用户；其局限则在于对显式关系、多跳路径和结构化推理支持有限。例如，对于“两个对象之间经过哪些关系连接”“某实体在多个文档中如何演化”这类问题，仅依赖向量召回往往只能返回相关片段，而难以给出结构清晰、解释充分的关系答案。因此，本文将其定位为基础问答模块，而不是唯一问答模块。后续引入图谱查询、实体定位和关系推理后，可在现有检索链路基础上形成更高解释性的混合问答框架。

### 5.4 图谱存储与关系构建模块设计与实现

#### 5.4.1 模块职责

图谱存储与关系构建模块的目标，是把原本只存在于业务数据库中的目录树、知识库归属、文档作者关系和文档间关联关系提升为可计算、可查询、可视化的图结构。该模块既承担“业务对象图”的构建职责，也承担“关系骨架图”的演化职责，是本文知识图谱能力的核心基础。

与很多直接从实体抽取入手的方案不同，本文在当前阶段优先把知识库、文件夹、文档和用户等真实业务对象同步到 Neo4j，再在此基础上逐步补充文档间相似关系。这样做的原因在于，毕业设计项目首先需要保证图谱层能够稳定承载现有系统的知识组织需求，而不是在实体抽取尚未成熟的前提下过早依赖高不确定性的复杂算法。

#### 5.4.2 图谱数据模型设计

在当前系统中，图谱节点主要包括 `Document`、`Folder`、`KnowledgeBase`、`User` 和预留的 `Entity`。其中，`Document` 节点不仅保存文档 ID、标题和状态，还保存基于标题与正文抽取出的 `tokens` 与 `token_count`，以支撑后续文档相似关系计算；`Folder` 节点负责维持目录树结构，并保存 `parent_id` 与 `position` 等排序信息；`KnowledgeBase` 节点用于界定知识空间根；`User` 节点用于表达内容创建来源；`Entity` 节点则作为后续实体抽取与图谱问答扩展位存在。

从当前真实实现看，已经落地的关系类型主要包括 `CONTAINS`、`BELONGS_TO`、`CREATED_BY` 和 `RELATED_BY_KEYWORD`。其中，`CONTAINS` 用于表达目录与文档、目录与子目录之间的层级结构；`BELONGS_TO` 用于表达目录或文档对知识库的归属关系；`CREATED_BY` 用于把文档与创建者关联起来；`RELATED_BY_KEYWORD` 则用于表达文档间的轻量化相似关系。需要说明的是，编辑者信息当前以文档属性 `editor_id` 保留，尚未在图中显式建成 `EDITED_BY` 边；`MENTIONS` 和 `RELATES_TO` 关系已经在模型设计中预留，但仍待实体抽取闭环完成后真正接入。

这种模型设计体现出由浅入深的构建思路：先把稳定的业务对象映射为图节点，再逐步补充实体节点和实体关系，最后实现更丰富的图谱推理能力。与一次性追求完整实体图谱相比，这种策略更适合毕业设计项目的阶段性推进，也更符合当前系统已经具备的稳定数据来源。

#### 5.4.3 图谱初始化与存储实现

系统引入 Neo4j 作为图数据库，并在初始化阶段建立唯一约束和索引。具体而言，`InitSchema` 会对 `Document`、`Folder`、`Entity`、`User` 和 `KnowledgeBase` 节点的 `id` 字段建立唯一约束，同时对 `Document.name`、`Document.kb_id`、`Entity.name`、`Entity.type` 和 `Entity.kb_id` 等字段建立索引。这样做的目的在于避免重复节点、提升查询效率，并为后续扩展实体层保留性能空间。该设计与向量数据库的职责相互配合，使系统形成“向量库保存召回友好表示，图数据库保存关系友好表示”的混合存储格局[3]。

在图谱写入层，系统并未把所有操作塞进一条复杂的大查询，而是按对象类型拆分为若干粒度明确的存储方法。例如，`CreateDocument` 负责写入 `Document` 节点本体属性，`CreateDocumentRelations` 负责补齐 `BELONGS_TO`、`CREATED_BY` 和 `CONTAINS` 关系；`CreateFolder` 与 `CreateFolderRelations` 则分别负责目录节点与目录层级关系；知识库与用户也分别通过独立方法创建。这种拆分方式使文档创建、目录移动、知识库初始化和用户同步都可以按事件类型独立执行，从而与增量同步机制自然衔接。

在图谱初始构建阶段，系统并不是手工造数，而是提供了从 PostgreSQL 向 Neo4j 迁移知识库、用户、文档和目录的独立迁移工具，使已有业务数据能够一次性完成图谱初始化。这意味着图谱层并非仅服务新数据，而是可以承接存量知识库数据，具有更强的工程实用性。

#### 5.4.4 文档关系构建功能设计

由于当前实体抽取闭环尚未完全打通，系统在现阶段优先实现文档级关系构建。该功能并非简单依赖全文检索结果，而是使用一套轻量化的 token 抽取策略：在 `graph_tokenizer.go` 中，系统会先对标题和正文统一转为小写文本，再对标题赋予更高权重；对于英文和数字内容，采用正则提取词项；对于中文内容，则采用 bi-gram 双字切分；同时通过“最大源文本长度 6000 个 rune、最大保留 160 个 token、英文最小词长 2”这些约束控制计算成本。这样既保留了标题语义，又避免长文档带来过高的关系构建开销。

在计算层面，系统并不是把“是否相似”交给一个黑盒模型判断，而是通过 Cypher 直接在图数据库中完成关系计算。具体做法是：首先删除当前知识库或当前文档已有的 `RELATED_BY_KEYWORD` 关系；随后在同一知识库范围内对文档两两配对，求取 token 交集 `commonTokens` 及其数量 `commonCount`；再按 `commonCount / (|tokens1| + |tokens2| - commonCount)` 计算 Jaccard 风格的相似度分数 `score`。当前实现要求 `commonCount >= 3` 且 `score >= 0.18` 时才建立关系，并在关系属性中保存前 20 个公共关键词、公共词数量、相似度分值和更新时间。

更重要的是，这一关系构建不是一次性离线行为，而是嵌入到了文档创建和文档更新流程之中：当文档成功同步到 Neo4j 后，系统会自动调用单文档关系重建逻辑，只重算当前文档与同库其他文档之间的相似关系，而不是每次都全量重跑整个知识库。这样一来，知识图谱会随着文档内容变化持续演进，而不是长期停留在初次导入时的静态状态。

这一设计的价值在于，可以在实体层尚未完全成熟的情况下，让图谱先具备“关系网络”的基本形态。对于管理员来说，这些关系能够直接用于知识主题聚类、相似文档发现和内容导航；对于系统后续扩展来说，这些关系也可以作为实体层构建前的过渡结构。

#### 5.4.5 模块实现特点

图谱存储与关系构建模块最大的特点是“业务对象先行、语义层逐步补齐”。换言之，本文并没有把图谱构建完全建立在复杂抽取模型之上，而是先用真实业务对象形成骨架，再用轻量化算法补齐一部分关系层。这种思路更符合中小规模系统的工程实现规律。

此外，该模块还体现出较强的工程闭环意识：一方面，图谱节点和关系来自真实业务对象与真实变更事件，而非脱离业务的独立实验数据；另一方面，图谱关系构建结果可以直接被图谱查询接口和可视化页面消费，从而形成“构建 - 查询 - 展示 - 反馈”的完整闭环。对于毕业设计论文而言，这比单纯给出一套图模型或算法描述更能体现系统落地价值。

### 5.5 图谱同步与故障恢复模块设计与实现

#### 5.5.1 模块职责

图谱同步与故障恢复模块负责把业务层中的对象变化可靠地同步到 Neo4j 中，并在同步失败时提供自动恢复和人工恢复能力。由于本文系统同时维护 PostgreSQL 主库、向量索引和图数据库三类增强表示，图谱层若不能及时跟随业务变化，就会直接影响图谱查询结果、可视化页面准确性以及后续图谱增强问答的可靠性。因此，该模块并非附属补丁，而是多存储协同架构中的关键基础设施。

#### 5.5.2 同步触发设计

当文档、目录、知识库或用户发生新增、更新、删除和移动等操作时，系统都会触发对应的图谱同步任务。当前已经覆盖的任务类型包括：`document_create`、`document_update`、`document_delete`、`document_move`、`folder_create`、`folder_update`、`folder_delete`、`folder_move`、`user_create` 和 `kb_create`。这些任务统一进入 `GraphSyncUseCase`，再由 `executeSyncTask` 根据任务类型分派到具体同步方法。同步任务在执行前会根据业务对象当前状态重新构造图谱写入载荷，而不是简单复用旧数据，从而降低因状态过期、目录位置变化或字段遗漏造成的同步错误。

以文档为例，当文档创建成功后，系统会先重新加载最新节点内容，再抽取标题与正文 token，随后在图数据库中创建 `Document` 节点、建立所属知识库关系、目录包含关系和创建者关系，并自动重建该文档的相似关系；当文档更新时，系统会同步更新标题、状态、token 集合和编辑者信息，并重新计算文档相似关系；当文档移动时，系统只更新其父目录 `CONTAINS` 关系；当文档删除时，则直接删除对应图节点。目录和知识库的同步逻辑与此类似，从而保证图数据库中的结构与业务主库保持同构。

#### 5.5.3 自动重试与死信补偿设计

为了应对 Neo4j 短时不可用、网络波动或写入冲突等异常情况，系统为同步任务设计了自动重试机制。根据当前实现，`runWithRetry` 最多重试 3 次，初始等待时间为 500ms，并按指数退避增长到上限 4s。这样既能覆盖短时抖动场景，又不会在单次失败时对主流程造成过长阻塞。若请求上下文本身已经结束，系统还会在必要时切换到后台上下文继续执行补偿写入，以避免失败信息来不及落库。

若超过最大重试次数仍未成功，则任务会被写入图谱死信表。死信记录中不仅保存任务类型和对象标识，还保存知识库 ID、序列化后的任务载荷、错误信息、重试次数以及状态与时间戳。也就是说，系统并没有让失败静默消失，而是通过 `failGraphSyncTask` 和 `persistDeadLetter` 把失败转化为结构化问题记录。对于毕业设计项目而言，这一点能够明显体现对“失败路径”而不仅是“成功路径”的工程考虑。

#### 5.5.4 人工重放设计

在图谱页面中，管理员可以手动触发死信重放。系统会读取指定知识库范围内尚未解决的死信任务，逐条反序列化载荷，并重新调用统一的任务解析器执行同步逻辑。与初次执行不同，重放流程使用 `runWithRetryNoDeadLetter` 进行有限重试，避免在重放失败时继续无限级联地产生新死信。若重放成功，则系统将对应记录标记为 `resolved`；若仍然失败，则更新失败次数和最新错误信息，供后续继续排查。

这种人工重放机制带来的价值在于：当问题并非业务数据本身错误，而只是图数据库短时不可用、网络异常或依赖服务波动时，管理员无需手动逐条补数据，只需在环境恢复后执行一次重放即可使图谱层重新收敛。这使系统在不实现复杂分布式事务的前提下，获得了较强的最终一致性保障能力。

#### 5.5.5 模块价值分析

与许多只展示成功路径的毕业设计项目不同，本文专门为图谱同步设计了恢复链路，这使系统具备了更强的工程完整性。对于涉及多存储协同的系统而言，恢复能力不是附属功能，而是核心能力之一。更重要的是，该模块让论文中的“最终一致性”不再停留在概念描述，而是具象化为“自动重试 + 指数退避 + 死信落库 + 页面重放”的完整实现路径，从而显著增强了系统设计的可信度和答辩说服力。

### 5.6 图谱查询与可视化模块设计与实现

#### 5.6.1 模块职责

图谱查询与可视化模块承担两项任务：一是通过后端接口提供图谱访问能力，二是通过前端页面把图谱数据转换为可交互的知识网络视图。前者解决“如何把 Neo4j 中的数据组织成可消费接口”的问题，后者解决“如何让管理员看得见、看得懂、用得上图谱”的问题。两者共同决定了图谱模块能否真正从后台增强存储走向前台可操作功能。

#### 5.6.2 图谱查询功能设计

系统已经实现的图谱查询能力包括：

1. 获取指定节点邻域图谱；
2. 查找节点间路径；
3. 获取图谱统计信息；
4. 搜索实体；
5. 构建文档关系；
6. 获取知识库全图数据；
7. 重放图谱同步死信。

从实现角度看，这些接口基本对应 `GraphQueryUseCase` 中的几个核心方法。`GetNodeGraph` 通过可变深度路径匹配获取某节点周围的局部子图，适合做节点邻域浏览；`FindPaths` 基于 `shortestPath` 在给定最大深度内返回两个节点之间的连接路径，适合做关系链分析；`GetGraphStats` 会分别统计节点类型数、边类型数、总节点数、总边数、文档数、目录数、实体数以及平均连接度，用于支撑图谱概览页面；`GetAllGraph` 则在知识库范围和节点上限约束下返回整个可展示子图；`BuildDocumentRelations` 用于手动触发文档相似关系重建；`SearchEntities` 则为未来实体层问答预留搜索入口。

这些接口共同构成了图谱模块的服务边界。进一步看，它们实际上覆盖了三类使用需求：第一类是结构观察需求，例如全图读取、节点邻域与图谱统计；第二类是关系分析需求，例如路径查询、实体搜索和相似关系构建；第三类是运行维护需求，例如死信重放。通过这三类接口，图谱不再只是后端存储结构，而是成为前端交互和后续图谱问答可直接调用的能力集合。

若进一步从查询实现细节分析，这些接口也体现出明显的分层特点。`GetNodeGraph` 采用可变深度路径匹配，适合在页面侧按需展开局部邻域；`FindPaths` 基于 `shortestPath` 查找节点间最短连接路径，并限制返回数量，避免复杂图下路径爆炸；`GetGraphStats` 则把节点统计、边统计和总量统计拆分为多条查询，以提升统计逻辑的可维护性。由此可见，当前图谱查询模块并非为了演示而临时拼接接口，而是在接口粒度、查询复杂度与页面消费方式之间做了工程化平衡。

#### 5.6.3 可视化页面设计

在前端实现上，系统新增了独立的图谱管理页面，支持图谱统计概览、全图浏览、2D 与 3D 展示切换以及死信重放操作。页面初始化时会先调用 `getGraphStats` 读取统计数据，再调用 `getAllGraph` 按知识库范围和 `limit=1000` 的上限拉取展示子图。页面顶部统计区用于展示总节点数、总关系数、文档数、实体数和平均连接度；中部主体区域用于呈现图谱网络；顶部控制区提供 2D/3D 视图切换与“重放死信”操作。若当前知识库尚无图谱数据，页面会显示空状态，但依然保留死信重放入口，方便管理员先执行恢复。

参考相关知识图谱管理界面设计经验，图谱页面不仅承担展示职责，还承担图谱访问、管理和验证职责，因此其交互设计直接影响系统的可解释性与可维护性[6]。从当前实现看，这个页面已经不只是“渲染一个网络图”，而是承担了图谱统计、状态判断、异常恢复和知识结构巡检的综合管理角色。

论文写作中，这一模块应被视为“功能模块”，而不仅仅是“页面展示”。因为它直接承担了图谱管理入口的角色，是管理员理解和维护图谱的重要界面。

#### 5.6.4 图谱布局与交互实现

为了提高图谱展示效果，系统对原始图数据进行了前端适配和布局优化。后端返回的节点和边数据会先被转换为 Graphology 图结构，并为不同类型节点赋予不同颜色、大小与质量参数。节点初始位置通过黄金角度螺旋生成，再根据节点规模自适应地应用 ForceAtlas2 力导向布局，并通过 noverlap 减少节点重叠；边则根据关系类型映射颜色、宽度和曲率。这样设计的好处在于，知识库规模较小时能够快速形成清晰网络，规模增大时也能保持较好的可读性。

在 2D 视图中，系统使用 Sigma 负责画布渲染，并为节点提供悬停高亮、邻居强调、单击聚焦、双击预览和跳转文档编辑页等交互。文档节点被选中后，相关邻居节点和边会被突出显示，未选中元素则降低透明度，从而帮助管理员快速理解局部结构。对于文档节点，系统还提供预览对话框，支持直接查看节点属性并跳转到对应文档。

在 3D 视图中，系统使用 `react-force-graph-3d` 和 Three.js 构建球形分布的知识网络。节点初始会被均匀投射到球面上，并配合粒子背景、自动旋转、关系箭头、关系粒子和不同边样式展示整体结构；文档节点还会附加发光球体与文字标签。`RELATED_BY_KEYWORD`、`MENTIONS`、`REFERENCES`、`CONTAINS` 等不同边类型在颜色、宽度、曲率、箭头长度和粒子速度上都有独立映射，因此管理员可以在宏观视图中快速区分关系类型。

更重要的是，系统并未把 2D 与 3D 视图做成纯粹的视觉噱头，而是分别服务于不同观察目标：2D 视图更适合管理员阅读标签、分析局部结构和排查关系；3D 视图则更适合在答辩和演示场景下展示知识网络的整体规模与层次感。通过这一处理流程，图谱不再是简单散点图，而是具备较强可读性的交互网络，管理员能够从中快速识别核心节点、关系密集区和异常结构。

#### 5.6.5 模块作用分析

图谱查询与可视化模块把图谱从“后台增强数据”转换成“前台可操作功能”。这一步对于毕业设计论文尤其重要，因为它让系统不仅有算法和存储，还真正有了用户可感知的功能输出。管理员可以通过页面直接观察知识结构、执行关系重建、查看统计指标并处理异常任务，这使图谱模块在系统中的价值不再需要依赖额外解释，而能够通过可交互功能被直接证明。

### 5.7 图谱增强问答扩展模块设计

当前系统已经具备向量问答能力，也已经具备图谱查询能力，但尚未完全打通“自然语言问题到图谱查询再到答案生成”的完整闭环。因此，从严格意义上说，现阶段系统更接近“**RAG 主链路 + 图谱辅助链路**”的形态，而非完全意义上的 GraphRAG。不过，从现有代码结构看，该模块所需的多个前置条件已经具备：一是图数据库中已有知识库、目录、文档和用户等稳定节点；二是后端已实现节点邻域、路径查询、实体搜索和全图读取接口；三是前端问答页已经支持证据块展示和流式回答；四是系统已有成熟的权限感知 RAG 链路，可作为图谱证据不足时的回退路径。

从未来的技术实现角度看，图谱增强问答的落点应当放在“问答编排层”而不是单独再造一个对话系统。更具体地说，可以先在当前 `ChatUsecase` 前面增加问题路由步骤，把问题划分为事实型、关系型和开放型三类：事实型和关系型问题优先走图谱检索，开放型问题优先走文档型 RAG，混合型问题则同时请求图谱与向量证据。图谱部分可先通过实体搜索和候选关系筛选定位节点，再由模板规则或大语言模型生成 Cypher 查询；文档部分则沿用现有 `dataset_id + group_ids + history` 的检索逻辑。最终由统一编排层把图谱返回的结构化事实、向量召回的文本证据以及自然语言答案合并为统一响应结构。

如果进一步细化到项目继续演进时的实现步骤，较合理的接入顺序可以分为四个阶段。首先是**问题理解阶段**，沿用现有对话入口完成会话校验、敏感词检测和权限组解析，同时增加问题分类与实体候选识别；其次是**证据检索阶段**，对关系型问题优先调用图谱接口定位节点、路径或邻域子图，对开放型问题继续调用 Raglite 执行语义召回，对混合型问题则并行收集两类证据；再次是**证据融合阶段**，把图谱返回的节点、边、路径结果与向量召回的文档片段统一转换为可供模型消费的中间结构；最后是**回答生成阶段**，由大语言模型基于融合上下文生成自然语言答案，并继续沿用当前 `chunk_result + data + done` 的流式协议返回前端。这样的拆分方式能够最大限度复用现有 RAG 主链路，也能让图谱增强能力以低侵入方式嵌入现有系统。

从论文写作角度看，把该模块作为“扩展模块”而非“已完成模块”进行描述，反而更符合系统类论文的客观性。一方面，可以明确指出当前最稳定的是文档型 RAG 问答，而图谱增强问答仍处于能力拼装阶段；另一方面，也能够说明本文系统并非停留在分散模块堆叠，而是已经具备清晰的演进路径和良好的代码边界，为后续从 RAG 过渡到 HybridRAG / GraphRAG 提供了真实基础。

### 5.8 典型业务流程实现

#### 5.8.1 知识库创建与初始化流程

知识库创建是整个系统生命周期的起点。管理员在后台提交知识库名称和访问配置后，系统首先在向量服务中创建数据集，获得后续检索使用的 `dataset_id`；随后在 PostgreSQL 中创建知识库主记录；最后异步把该知识库同步到 Neo4j 中，生成 `KnowledgeBase` 节点。由此，知识库在创建完成的那一刻就同时进入业务层、检索层和图谱层，为后续文档导入、版本发布、公开站点服务和图谱构建奠定统一边界。

#### 5.8.2 文档新增、发布与重新学习流程

文档新增是系统最典型的业务流程之一。管理员通过上传、导入或在线编辑方式创建文档后，系统先完成对象存储写入和业务记录创建，再异步触发图谱同步，使文档节点、目录关系和作者关系进入 Neo4j。若节点类型为文档，图谱同步还会在成功写入后立即执行单文档相似关系重建，使该文档在图谱中尽快获得可浏览的关联边。

随后，管理员可通过“发布文档”或“发布更新”把当前文档固化为发布快照。系统以发布快照而不是编辑中的工作副本作为向量索引输入，再通过消息队列将 `NodeReleaseVectorRequest` 投递给向量消费者。消费者读取发布快照内容后，调用 Raglite 完成文档上传、权限元数据写入和旧版本 `doc_id` 清理，并把新的 `doc_id` 反写回发布记录。这样设计的好处在于，问答服务总是面对稳定版本，而不会因为后台编辑中的临时状态而出现索引抖动。

若文档内容发生较大变化、索引状态异常或希望重新刷新知识内容，管理员可进一步执行“重新学习”操作。该操作的本质并不是直接重新嵌入，而是再次投递 `upsert` 类型向量任务，使已有文档重新进入“发布快照读取 - 向量写入 - 状态回写”的标准链路。此外，当节点的可问答权限组发生变化时，系统还可以单独触发 `update_group_ids` 任务，仅更新向量服务中的权限元数据而不重写正文内容，从而兼顾一致性与处理成本。

#### 5.8.3 用户提问与流式问答流程

当用户在公开站点、Widget 或机器人入口发起问题时，请求首先进入应用层，系统校验应用配置和模型配置后，创建或续接会话，并把用户消息写入会话表。若为新会话，系统会生成新的 `conversation_id` 与 `nonce`；若为历史会话，则必须通过 `nonce` 校验后方可继续写入。这样做的目的在于让公开问答场景也具备基本的会话一致性与防伪能力。

接着，系统执行敏感词检测，读取当前认证信息对应的用户组权限，并在向量库中进行带 `group_ids` 过滤的语义召回。检索结果返回后，后端不会直接把裸 chunk 交给模型，而是先把 `doc_id` 重新映射为节点名称、摘要、目录路径和片段集合，并以 `chunk_result` 事件的形式先行回传给前端。随后，系统再把整理后的证据组织成统一上下文送入大语言模型，实现“证据先到、答案后到”的交互体验。

在生成过程中，系统通过 SSE 持续向前端返回会话 ID、消息 ID、证据块、答案流和完成事件；若模型支持思维链，还会单独返回 `<think>...</think>` 内容。问答结束后，系统把完整回答、Token 用量和消息关系落库，从而形成可回放、可反馈、可统计的完整对话记录。也正因为这一流程已经稳定打通，当前系统才能作为图谱增强问答的承载底座，而不是单纯的模型调用演示页面。

从技术细节上看，当前证据回显并不是简单把 Raglite 返回的原始 chunk 原样抛给前端，而是先在服务端根据 `doc_id` 回查业务节点，再把文档标题、目录路径、摘要和片段内容重新组织为更适合阅读与调试的证据结构。这一处理让问答结果具备两个额外价值：其一，管理员可以在回答生成前先看到系统究竟召回了哪些文档，从而快速判断召回是否偏题；其二，后续若要接入图谱证据，也可以沿用同一返回协议，把图节点、关系路径与文档片段放入统一证据区。换言之，当前 SSE 协议不仅服务于“流式回答”，也为后续混合证据展示预留了接口基础。

#### 5.8.4 图谱恢复流程

当系统出现图谱同步失败时，后台并不会简单丢弃失败任务，而是先执行自动重试。若自动重试依然失败，则把该任务写入死信表。管理员在图谱页面中可手动触发“重放死信”操作，系统读取指定知识库范围内的失败任务后重新执行同步逻辑，并根据结果更新死信状态。这一流程使图谱层在异常场景下仍具备可恢复性，也体现了系统在多存储协同架构下对失败路径的显式治理能力。

### 5.9 权限控制与异常处理

权限控制方面，本文系统并未把权限理解为单一的登录校验，而是把它拆分为知识库范围控制、节点级访问控制和检索级证据过滤三层机制。首先，后台接口与公开接口都通过统一鉴权中间件控制访问边界；其次，文档节点自身带有“可见、可访问、可问答”三级权限，且可进一步绑定用户组；最后，向量库中的文档元数据会记录 `group_ids`，使问答链路在召回阶段就能够过滤无权限内容。这样设计的结果是：用户即使知道某个问题的问法，只要没有 `answerable` 权限，对应文档也不会进入召回上下文；若没有 `visitable` 权限，则搜索结果会被过滤；若没有 `visible` 权限，则目录树中不会显示该节点。

在公开站点侧，系统还通过验证码机制对问答、评论和文件上传等高风险入口进行保护，并结合敏感词检测、水印、复制限制、免责声明和反馈机制形成更完整的治理闭环。其中，敏感词检测不仅作用于用户输入，也可在流式输出阶段继续执行过滤，避免生成内容越过既定安全边界。对于知识服务系统而言，这种“输入约束 + 输出约束 + 内容保护”的组合策略比单一登录控制更接近真实部署需求。

异常处理方面，系统主要考虑了请求参数无效、模型未配置、会话 `nonce` 校验失败、节点不存在、权限不足、检索失败、图谱同步失败、死信表缺失和数据库连接异常等情况。后台在这些场景下会返回结构化错误信息，前台则根据错误类型给出提示，并在必要时保留失败上下文供管理员排查。尤其在问答链路中，系统会把会话、消息、错误事件和 Token 信息统一写入消息模型中，从而使异常不只是“前端看到报错”，而是能够回到后端记录中进行复盘。整体而言，这一设计使系统在面对不确定输入、外部依赖波动和多组件协同时仍具备较强的可追踪性和可恢复性。

#### 6.3.4 评价指标定义

为了使后续补充的实验结果具有可比较性，本文建议对不同实验使用明确指标进行量化。

对于图谱规模实验，可采用总节点数、总边数、实体覆盖率、平均连接度、最大连通子图规模等指标。总节点数和总边数用于反映图谱规模，平均连接度可用于衡量图谱稠密程度，实体覆盖率可用于衡量图谱语义层的完整程度。

对于问答效果实验，可采用准确率、精确匹配、人工评分、平均响应时间和可解释性评分等指标。其中，准确率主要用于评价回答是否与标准答案一致；平均响应时间用于评价系统交互效率；可解释性评分则可通过人工打分方式评价答案是否包含来源依据、关系路径或检索依据。若后续引入多路召回，还可以进一步统计关键词召回命中率、标签召回命中率和向量召回命中率，以分析不同路径对最终回答的贡献[9]。

对于同步鲁棒性实验，可采用首次成功率、自动恢复率、死信写入率、死信重放成功率和平均恢复时长等指标。前两项衡量系统在正常与轻度异常场景中的稳定性，后几项则衡量补偿机制的恢复能力。

#### 6.3.5 测试问题集设计

问答系统的测试不能只依赖少量示例问题，否则很难客观反映系统能力。本文建议构建覆盖三类问题的测试问题集。

第一类是**事实型问题**，例如“某文档属于哪个知识库”“某文档由谁创建”“某目录下有哪些文档”。这类问题重点考查图谱中的显式关系是否正确。

第二类是**关联型问题**，例如“与某篇文档最相关的文档有哪些”“某节点与目标节点之间是否存在路径”“某个主题在知识库中覆盖了哪些相关文档”。这类问题重点考查图谱结构组织和关系构建效果。

第三类是**开放型问题**，例如“请概括某主题相关资料”“请解释系统中图谱同步机制的作用”“知识图谱与 RAG 在本系统中如何协同工作”。这类问题重点考查向量问答链路和后续混合问答能力。

在测试问题组织上，建议每类问题不少于二十个，总样本数不少于六十个，并由人工给出标准答案或参考答案。对于开放型问题，可采用人工评分而非严格二值判断。

#### 6.3.6 证据可追溯性与覆盖率评价设计

对于图谱增强问答系统而言，评价“答得对”还不够，还需要评价“为什么这样回答”和“系统是否召回了足够证据”。因此，本文建议增加证据可追溯性与覆盖率评价。该实验可重点统计以下指标：

1. **来源标注率。** 回答中是否附带知识片段、文档来源或图谱节点来源。
2. **结构证据率。** 回答中是否包含图谱路径、实体关系或节点关联信息。
3. **检索覆盖率。** 对于有标准证据的问题，系统召回结果是否覆盖关键证据片段。
4. **证据一致性。** 回答内容与返回证据之间是否存在明显矛盾。

卓梁雨等对多路召回的研究表明，单一路径检索容易出现覆盖不足，而多路径融合更有利于支撑复杂问题和跨条线问题的回答[9]。肖崇霞也强调，企业知识问答系统应以证据片段和版本上下文保证答案的可追溯性[13]。因此，把证据可追溯性纳入评价体系，有助于使本文实验部分更加符合图谱增强问答系统的真实评价标准。

### 6.4 阶段性结果分析

结合当前代码与文档实现情况，可以得到以下结论。

第一，系统已经完成知识管理平台向图谱增强平台的转变。原有系统主要聚焦文档管理与问答，而本文新增的图谱建模、图谱同步、图谱查询和图谱可视化，使系统具备了更强的知识组织能力。尤其是知识库、目录、文档和用户被统一映射进 Neo4j 之后，系统已经不再只是“以列表组织知识”，而是开始具备“以网络组织知识”的能力。

第二，当前 RAG 链路已经达到工程可用状态，而不是停留在演示级原型。具体表现为：系统为每个知识库维护独立 `dataset_id`；文档索引更新由发布快照驱动而非直接读取编辑态数据；权限信息以 `group_ids` 形式下沉到向量服务元数据；问答过程具备 `conversation_id + nonce` 会话一致性校验；检索证据能够通过 `chunk_result` 事件显式返回；最终回答与 Token 用量可以完整落库。换言之，当前系统最成熟的并不是“模型回答本身”，而是围绕知识库场景搭建起来的整条检索增强工程链路。

第三，图谱同步补偿机制有效提升了系统的工程健壮性。传统毕业设计项目往往只展示成功路径，而本文额外考虑了失败重试和恢复过程：同步任务在失败时会自动重试，并按指数退避延迟执行；重试耗尽后进入死信表；管理员可在图谱页面统一重放。这种设计不仅提升了图谱层可靠性，也使“最终一致性”在系统中具有了可观测、可验证的具体实现[11][12]。

第四，基于文档 token 的关系构建方式虽然不具备强语义推理能力，但作为中期阶段的过渡方案，能够在成本可控的前提下快速形成可浏览的图谱结构。标题加权、双语 token 提取和 Jaccard 风格相似度计算，使系统无需等待复杂实体抽取模型成熟，就能先获得一张具有导航价值和聚类价值的文档关系网。这一策略与“先形成图谱骨架，再逐步补齐语义层”的工程路线是一致的，也有利于后续平滑接入实体抽取与混合检索能力[3][9]。

第五，系统的不足也较为明显。当前图谱的“节点语义层”仍不够丰富，文档关系多、实体关系少；图谱问答链路尚未完全接入默认对话编排，因而大多数问题仍主要由文档型 RAG 处理；真正面向图像、截图与聊天记录的多模态处理能力尚未形成。因此，本文所实现的系统更准确地说是“面向多模态目标的图谱问答系统原型”，而非全部目标已完全达成的终态版本。

从工程评价视角进一步看，本文当前阶段最有价值的成果并不是某一个单点算法，而是把知识接入、向量检索、图谱建模、补偿恢复和前端可视化组织成了统一系统。也就是说，论文中的核心贡献更接近“可持续演进的技术底座”而不是“孤立的实验模块”。这一点对于毕业设计尤为重要，因为它说明系统后续无论继续补齐 OCR、多模态解析，还是继续向 GraphRAG 演进，都不需要推翻现有架构，而可以在既有模块边界上逐步扩展。

### 6.6 典型案例分析

为了更加直观地说明系统当前阶段的实际作用，本文进一步给出三个典型案例。

#### 6.6.1 案例一：知识库图谱概览分析

在知识库内容逐步导入后，管理员进入图谱概览页面，可以首先从统计面板了解当前知识库的整体规模，包括节点数量、关系数量、文档数量和平均连接度。如果某一知识库中节点数量持续增长而平均连接度过低，则说明知识已经被导入，但关系层仍较薄弱；若关系密度显著提高，则说明文档间已经形成初步语义网络。

这一案例说明，图谱统计不仅是可视化装饰，而是可以作为知识组织质量的一个观察窗口。管理员可以据此判断当前知识库是否需要重新构建关系、补充实体抽取或清理重复内容。

#### 6.6.2 案例二：文档关联关系浏览

当管理员希望理解某篇核心文档与其他文档之间的关系时，可以通过局部子图查看与该文档直接相连的节点。如果系统已经建立了多个 `RELATED_BY_KEYWORD` 关系，则管理员可以快速识别与该文档主题最接近的一组内容，并进一步检查这些关系是否合理。

这一案例体现了本文当前阶段关系构建方法的实际价值。即使实体层尚未完全成型，文档级关系图仍然可以帮助用户完成相近文档聚类、知识主题梳理和资料导航。

#### 6.6.3 案例三：图谱同步故障恢复

当图数据库因暂时不可用而导致同步失败时，系统会把失败任务写入死信表。管理员在图谱页面点击重放后，系统重新处理这些任务，并把成功重放的任务标记为已解决。通过这一过程，管理员可以观察系统从异常状态恢复到一致状态的完整闭环。

这一案例说明，本文系统不仅能处理理想场景，也具备面对异常场景的基本恢复能力。对于一个毕业设计项目而言，这种故障恢复链路本身就具有较高的展示价值和工程含量。

#### 6.6.4 案例四：问答证据回溯分析

当用户提出“知识图谱与 RAG 在本系统中如何协同工作”一类开放式问题时，系统理想的处理方式并不只是返回一段自然语言说明，而是同时给出相关文档片段、图谱节点或关系依据。以本文当前原型为例，虽然系统尚未完全实现图谱增强问答闭环，但已经具备形成证据回溯链的若干基础条件：知识库范围可限定、文档片段可召回、图谱关系可查询、图谱页面可展示局部子图，而且问答过程中已经能够通过 `chunk_result` 事件把证据文档名称、摘要和目录路径显式回传给前端。

从答辩展示角度看，这一案例具有较强代表性。若系统仅给出一段答案而不能解释“答案来自哪些文档、哪些关系、哪些知识对象”，用户很难判断回答是否可信；而一旦系统能够返回检索片段，并进一步在图谱页面中展示相关节点关系，即使答案仍需要人工进一步解读，系统的可解释性和说服力也会明显增强。也就是说，当前系统虽然默认答案仍主要来自文档型 RAG，但其证据链已经不再是完全黑盒的。

这一案例同时说明了本文后续工作的重点方向：未来需要把“向量片段证据”“图谱关系证据”和“自然语言答案”组织为统一返回结构，使系统在开放式问题上既能答得自然，也能答得有据可依。当前项目已经具备的 `chunk_result` 证据回显、图谱查询接口和图谱页面联动能力，正是这一目标的现实起点。

### 6.7 与其他实现路径的比较讨论

从系统实现路径看，本文方案位于三种典型方案之间。

第一种是**纯文档管理方案**。这类方案通常具备良好的文档编辑、上传和分类能力，但缺少结构化关系表达，难以支撑复杂关系查询。与之相比，本文方案在保留文档管理和发布能力的基础上，通过 Neo4j 扩展出图谱层，使知识网络能够被显式观察和分析，因此系统不再只是“内容仓库”，而是开始具备知识结构化组织能力。

第二种是**纯向量问答方案**。这类方案实现成本相对较低，能够快速形成问答能力，但在可解释性、路径查询和结构化关系表达方面存在明显不足。本文方案虽然以 RAG 作为当前主问答路径，但并不是简单的“向量搜索 + Prompt”实现，而是进一步引入了 `dataset_id` 边界、`group_ids` 权限过滤、会话 `nonce` 校验、证据块回显和异步索引治理机制。因此，与普通纯向量方案相比，本文系统在工程完整性和可维护性上更进一步；与此同时，引入图谱层又为后续结构化增强预留了明确扩展空间。

第三种是**纯图谱问答方案**。这类方案在事实型问题和关系型问题上优势明显，但搭建成本较高，对实体抽取和关系抽取质量要求也更高。若在毕业设计阶段直接以“完整图谱问答”为目标，不仅需要补齐实体抽取、关系抽取、实体链接、Cypher 生成和结果自然语言化等整条链路，还需要处理图谱更新、一致性和前端交互等工程问题，整体风险较高。本文并未直接走这一条路线，而是采用“先 RAG、后图谱增强、再向混合问答过渡”的策略，从而在项目可完成度和系统深度之间取得平衡。

从当前代码落地情况看，这一技术路径是合理的。因为向量问答、图谱同步、图谱查询和图谱可视化都已经成为真实可运行模块，而不是孤立概念。换言之，本文方案的价值并不只在于最终要做成 GraphRAG，更在于已经形成了一套可逐步演进的工程骨架：当前先让 RAG 稳定承载开放式问答，再让图谱逐步补足结构化解释与关系分析能力。

本章从功能验证、量化实验设计、案例分析和效度威胁等角度，对系统当前阶段的测试与分析进行了说明。虽然最终量化实验结果仍需要在完整环境中补齐，但从系统结构、接口能力、前端页面和补偿机制等方面看，本文设计的系统已经具备较高的完整性。更重要的是，本文不是简单给出一个“能运行”的原型，而是形成了可继续扩展的实验框架，为后续补充数据和进一步优化提供了明确方向。

5. 实现基于标题加权、双语 token 提取和 Jaccard 风格相似度计算的轻量化文档关联构建方法；
6. 实现图谱查询接口和支持 2D/3D 的图谱可视化管理页面。

从当前成果来看，本文已完成从知识管理平台向图谱增强知识问答平台的阶段性升级，基本达到毕业设计中“系统分析、架构设计、关键功能实现与论文撰写”的要求。

进一步概括来看，本文工作的价值主要体现在三个层次。其一是**架构层价值**，即通过把业务数据库、对象存储、向量库、图数据库和消息组件组织为统一协同架构，使系统具备承载后续扩展的工程骨架；其二是**数据层价值**，即通过把文档对象、目录结构、知识库范围和关系网络同时纳入统一管理，使知识组织方式从列表式管理进一步提升为网络式管理；其三是**交互层价值**，即通过问答界面、图谱管理页面、统计概览和异常恢复入口，让用户能够感知系统不仅“能存、能查、能答”，还能够“能看、能管、能追溯”。这三个层次共同构成了本文系统原型的阶段性成果。

如果进一步从技术实现角度归纳，本文最重要的两条落地主线分别是：一条面向知识库场景的工程化 RAG 主链路，另一条面向结构化知识组织的图谱增强链路。前者解决“如何稳定回答开放式问题”，后者解决“如何表达关系、统计结构并提供恢复机制”。二者虽然尚未完全融合为终态 GraphRAG，但已经在统一系统中形成了清晰分工和协同接口，这也是本文相较于单点技术验证更具工程价值的地方。

同时需要强调的是，本文所有上述能力均建立在从 0 开始设计与开发的 Mindweave 平台之上，而非建立在既有知识库平台的二次包装之上。无论是知识库主数据组织方式、发布快照驱动的向量索引机制、`conversation_id + nonce` 会话校验、图谱同步补偿策略，还是图谱页面的 2D/3D 展示与重放入口，均是在统一架构下逐步实现的。这种“自主搭建平台骨架，再逐步补强知识图谱与 RAG 链路”的过程，本身也是本文在工程实践层面的重要成果。

对于毕业设计答辩而言，这种分层成果也具有较好的展示逻辑：既可以从整体架构说明系统为什么可运行，又可以从模块实现说明系统如何落地，还可以从图谱页面和问答结果说明系统产生了哪些可见价值。换言之，本文并非停留在概念验证或页面展示，而是形成了一个具备一定复现性、可扩展性和后续研究承接能力的系统化原型，也为后续终稿继续补充实验数据预留了充分空间，并便于后续复现实验。

### 7.2 后续展望

针对当前系统存在的不足，后续可从以下几个方向继续完善。

第一，补齐实体抽取与关系抽取闭环。后续可以引入轻量化命名实体识别模型、大语言模型辅助抽取或规则与模型结合的方法，逐步将 `Entity`、`MENTIONS` 和 `RELATES_TO` 关系真正接入系统。

第二，完成图谱问答完整链路。重点工作包括问题分类、实体链接、Cypher 生成、图谱结果整理与自然语言生成，使系统在关系型问题上具备更强的解释性和推理能力。

第三，完善多模态输入能力。可结合 OCR、文档版面理解与图像语义抽取技术，支持截图、扫描文档、聊天记录等知识对象的统一接入。

第四，补充量化实验与对比评测。后续应围绕图谱覆盖率、问答准确率、响应时间、同步恢复成功率等指标构建更完整的实验体系，提高论文论证力度。

第五，优化前端交互体验。包括图谱筛选、节点详情联动、关系过滤、子图导出、路径高亮和图谱问答入口整合等能力。

从系统持续演进的角度看，后续工作还应关注“研究原型”向“稳定工具”转化时的若干关键问题。其一，需进一步完善知识更新机制，使新增文档、修改文档和删除文档能够在向量库与图谱层之间保持更细粒度的一致性；其二，需建立更明确的答案评价闭环，例如通过人工反馈、问题日志分析和错误案例归档，持续优化检索策略、提示模板和图谱结构；其三，需围绕实际使用场景逐步积累测试数据和基准问题集，使系统评价从阶段性说明转向可重复、可比较的实验验证。只有当这些工程性工作逐步补齐后，系统才能从毕业设计层面的“可演示原型”进一步演进为面向真实知识服务场景的稳定平台。

总体而言，本文所实现的系统原型已具备较强的扩展性和继续演进空间，为后续更完整的多模态知识图谱问答系统研究奠定了工程基础。
