# 知识图谱设计方案与可行性分析

## 一、知识图谱在项目中的定位

### 1.1 核心作用

知识图谱在"基于多模态的知识图谱问答系统"中扮演三个核心角色:

1. 知识组织层: 将碎片化文档结构化为实体-关系网络
2. 增强检索层: 基于实体关系的精准检索,与向量检索互补
3. 推理能力层: 支持多跳推理、路径查询、子图分析

### 1.2 与现有系统的关系

PandaWiki 已有 RAG (检索增强生成) 能力,知识图谱将作为增强层:
- 简单事实查询 → 知识图谱查询 (Neo4j)
- 复杂推理查询 → 混合查询 (Neo4j + Qdrant + LLM)
- 开放式对话 → 向量检索 (Qdrant + LLM)

## 二、系统架构设计

### 2.1 整体架构

前端层: 文档管理、问答交互、图谱可视化
应用层: 文档处理(已有)、实体关系抽取(新增)、图谱问答(新增)
存储层: PostgreSQL(结构化)、Qdrant(向量)、Neo4j(图谱)、MinIO(文件)

### 2.2 数据流设计

文档上传 → 文本提取 → 并行处理:
- 路径1: 向量化 → Qdrant (已有)
- 路径2: 实体关系抽取 → 三元组生成 → Neo4j (新增)

## 三、核心模块设计

### 3.1 实体关系抽取模块

功能: 从文本识别实体、抽取关系、生成三元组

技术方案对比:
- 方案A: Python NLP 服务 (spaCy/BERT) - 推荐
  优点: 成熟工具链,准确率高
  缺点: 需要额外服务,跨语言调用
  
- 方案B: Go NLP 库 (prose)
  优点: 纯 Go 实现,部署简单
  缺点: 功能简单,准确率较低
  
- 方案C: 第三方 API (百度/腾讯/阿里 NLP)
  优点: 开箱即用
  缺点: 需要付费,依赖外部服务

推荐方案: 方案A (Python NLP 服务)


### 3.2 Neo4j 图谱存储模块

功能: 存储实体节点、关系边、支持 Cypher 查询

Schema 设计:
```
实体节点 (Entity):
- id: UUID
- name: 实体名称
- type: 实体类型 (Person/Organization/Concept/Location)
- kb_id: 所属知识库
- source_doc_id: 来源文档
- properties: 扩展属性 (JSON)

关系边 (Relation):
- type: 关系类型 (导师/同事/位于/属于)
- confidence: 置信度 (0-1)
- source: 来源 (auto/manual)
- created_at: 创建时间
```

核心操作:
- CreateNode: 创建实体节点
- CreateRelation: 创建关系边
- QueryByEntity: 根据实体查询
- QueryByPattern: 模式匹配查询
- QueryPath: 路径查询 (多跳推理)

### 3.3 图谱问答模块

功能: 自然语言问题 → Cypher 查询 → 答案生成

处理流程:
1. 问题分析: 识别问题类型 (事实查询/推理查询/开放问答)
2. 实体链接: 提取问题中的实体,链接到图谱
3. 查询生成: 生成 Cypher 查询语句
4. 结果处理: 执行查询,获取结果
5. 答案生成: 将结果转换为自然语言

技术方案:
- 简单问题: 基于模板的 Cypher 生成
- 复杂问题: 使用 LLM (GPT-4) 生成 Cypher
- 混合查询: 图谱定位 + 向量补充细节

### 3.4 图谱可视化模块

功能: 前端展示知识图谱,支持交互操作

技术选型: ECharts Graph (推荐)
- 优点: 易用,文档完善,中文支持好
- 缺点: 定制性相对较弱

核心功能:
- 图谱渲染: 节点和边的可视化
- 交互操作: 缩放、拖拽、点击查看详情
- 子图展示: 以某实体为中心展示关联网络
- 路径高亮: 展示推理路径

### 3.2 Neo4j 图谱存储模块

功能: 存储实体节点、关系边、支持 Cypher 查询

#### 3.2.1 实体类型设计 (Node Labels)

基于 PandaWiki 数据库表结构,设计以下实体类型:

**1. Document (文档)**
来源表: `nodes` (type=1)
```
属性:
- id: string (主键)
- name: string (文档标题)
- content: string (文档内容)
- kb_id: string (所属知识库)
- status: int (状态: 1=正常)
- visibility: int (可见性)
- creator_id: string (创建者)
- editor_id: string (编辑者)
- created_at: timestamp
- updated_at: timestamp
```

**2. Folder (文件夹)**
来源表: `nodes` (type=0)
```
属性:
- id: string
- name: string (文件夹名称)
- kb_id: string
- parent_id: string (父文件夹)
- position: float (排序位置)
- created_at: timestamp
```

**3. Entity (实体)** - 核心
来源: AI 抽取 (从 Document.content 中提取)
```
属性:
- id: string (自动生成)
- name: string (实体名称,如"张三"、"Python")
- type: string (实体类型)
- aliases: string[] (别名列表)
- description: string (实体描述)
- confidence: float (置信度 0-1)
- source_doc_ids: string[] (来源文档 ID 列表)
- created_at: timestamp
- updated_at: timestamp

实体类型枚举:
- Person (人物)
- Organization (组织/公司)
- Technology (技术/工具)
- Concept (概念/术语)
- Product (产品)
- Event (事件)
- Location (地点)
- Other (其他)
```

**4. User (用户)**
来源表: `users`
```
属性:
- id: string
- account: string (账号)
- role: string (角色: admin/user)
- created_at: timestamp
```

**5. KnowledgeBase (知识库)**
来源表: `knowledge_bases`
```
属性:
- id: string
- name: string (知识库名称)
- created_at: timestamp
```

#### 3.2.2 关系类型设计 (Relationships)

**1. CONTAINS (包含关系)**
方向: Folder -> Document / Folder -> Folder
```
属性:
- position: float (排序位置)
- created_at: timestamp
```

**2. MENTIONS (提及关系)** - 核心
方向: Document -> Entity
```
属性:
- count: int (提及次数)
- positions: int[] (在文档中的位置)
- context: string[] (上下文片段)
- confidence: float (置信度)
- created_at: timestamp
```

**3. RELATES_TO (实体关联)** - 核心
方向: Entity -> Entity
```
属性:
- relation_type: string (关系类型)
- description: string (关系描述)
- confidence: float (置信度)
- source_doc_ids: string[] (关系来源文档)
- created_at: timestamp

关系类型枚举:
- DEPENDS_ON (依赖)
- SIMILAR_TO (相似)
- PART_OF (属于)
- USES (使用)
- IMPLEMENTS (实现)
- EXTENDS (扩展)
- RELATED_TO (相关)
```

**4. CREATED_BY (创建关系)**
方向: Document -> User
```
属性:
- created_at: timestamp
```

**5. EDITED_BY (编辑关系)**
方向: Document -> User
```
属性:
- edit_time: timestamp
```

**6. BELONGS_TO (归属关系)**
方向: Document -> KnowledgeBase / Entity -> KnowledgeBase
```
属性:
- created_at: timestamp
```

**7. REFERENCES (引用关系)**
方向: Document -> Document
```
属性:
- reference_type: string (引用类型: link/quote/related)
- created_at: timestamp
```

#### 3.2.3 图谱数据模型示例

```cypher
// 示例 1: 文档提及实体
(:Document {id: "doc1", name: "Python 入门教程"})
  -[:MENTIONS {count: 5, confidence: 0.95}]->
(:Entity {id: "e1", name: "Python", type: "Technology"})

// 示例 2: 实体之间的关系
(:Entity {name: "Django", type: "Technology"})
  -[:RELATES_TO {relation_type: "DEPENDS_ON", confidence: 0.9}]->
(:Entity {name: "Python", type: "Technology"})

// 示例 3: 文档结构
(:Folder {name: "技术文档"})
  -[:CONTAINS {position: 1.0}]->
(:Document {name: "Python 入门"})
  -[:CREATED_BY]->
(:User {account: "admin"})

// 示例 4: 文档引用
(:Document {name: "Django 教程"})
  -[:REFERENCES {reference_type: "link"}]->
(:Document {name: "Python 入门"})
```

#### 3.2.4 Neo4j Schema 定义

```cypher
// 创建约束 (确保 ID 唯一)
CREATE CONSTRAINT document_id IF NOT EXISTS FOR (d:Document) REQUIRE d.id IS UNIQUE;
CREATE CONSTRAINT folder_id IF NOT EXISTS FOR (f:Folder) REQUIRE f.id IS UNIQUE;
CREATE CONSTRAINT entity_id IF NOT EXISTS FOR (e:Entity) REQUIRE e.id IS UNIQUE;
CREATE CONSTRAINT user_id IF NOT EXISTS FOR (u:User) REQUIRE u.id IS UNIQUE;
CREATE CONSTRAINT kb_id IF NOT EXISTS FOR (k:KnowledgeBase) REQUIRE k.id IS UNIQUE;

// 创建索引 (提升查询性能)
CREATE INDEX document_name IF NOT EXISTS FOR (d:Document) ON (d.name);
CREATE INDEX entity_name IF NOT EXISTS FOR (e:Entity) ON (e.name);
CREATE INDEX entity_type IF NOT EXISTS FOR (e:Entity) ON (e.type);
CREATE INDEX document_kb IF NOT EXISTS FOR (d:Document) ON (d.kb_id);
```

#### 3.2.5 核心查询示例

**查询 1: 查找文档中提及的所有实体**
```cypher
MATCH (d:Document {id: $docId})-[m:MENTIONS]->(e:Entity)
RETURN e.name, e.type, m.count, m.confidence
ORDER BY m.count DESC
```

**查询 2: 查找与某实体相关的所有文档**
```cypher
MATCH (d:Document)-[m:MENTIONS]->(e:Entity {name: $entityName})
RETURN d.id, d.name, m.count
ORDER BY m.count DESC
LIMIT 10
```

**查询 3: 查找实体的关联实体 (2 跳)**
```cypher
MATCH (e1:Entity {name: $entityName})-[r:RELATES_TO*1..2]-(e2:Entity)
RETURN DISTINCT e2.name, e2.type, r
LIMIT 20
```

**查询 4: 查找文档的知识网络 (文档 + 实体 + 关联)**
```cypher
MATCH (d:Document {id: $docId})-[:MENTIONS]->(e1:Entity)
OPTIONAL MATCH (e1)-[r:RELATES_TO]-(e2:Entity)
RETURN d, e1, r, e2
```

**查询 5: 查找某知识库的实体统计**
```cypher
MATCH (e:Entity)-[:BELONGS_TO]->(kb:KnowledgeBase {id: $kbId})
RETURN e.type, count(e) as count
ORDER BY count DESC
```

#### 3.2.6 数据迁移策略

**阶段 1: 基础结构迁移 (PostgreSQL -> Neo4j)**
1. 迁移 KnowledgeBase (从 `knowledge_bases` 表)
2. 迁移 User (从 `users` 表)
3. 迁移 Folder 和 Document (从 `nodes` 表,按 type 区分)
4. 根据 parent_id 创建 CONTAINS 关系
5. 根据 creator_id/editor_id 创建 CREATED_BY/EDITED_BY 关系

**阶段 2: 实体抽取 (AI 处理)**
1. 遍历所有 Document 节点
2. 使用 NLP 模型从 content 中抽取实体
3. 创建 Entity 节点
4. 创建 MENTIONS 关系

**阶段 3: 关系抽取 (AI 处理)**
1. 分析实体共现模式
2. 使用关系抽取模型识别实体间关系
3. 创建 RELATES_TO 关系

**阶段 4: 文档引用分析**
1. 解析文档内容中的内部链接
2. 创建 REFERENCES 关系

核心操作: CreateNode, CreateRelation, QueryByEntity, QueryPath

## 五、图谱质量指标

### 5.1 覆盖率指标
- 文档覆盖率: 有实体的文档数 / 总文档数
- 实体密度: 总实体数 / 总文档数
- 关系密度: 总关系数 / 总实体数

### 5.2 质量指标
- 平均置信度: AVG(Entity.confidence)
- 孤立实体率: 无关系的实体数 / 总实体数
- 实体去重率: 合并的重复实体数 / 原始实体数

### 5.3 活跃度指标
- 热门实体: 被提及次数最多的实体 TOP 10
- 核心文档: 包含实体最多的文档 TOP 10
- 关键关系: 连接实体最多的关系类型

## 九、风险评估与应对

### 9.1 技术风险

风险 1: NLP 模型准确率不足
- 影响: 实体抽取质量差，图谱价值低
- 应对: 
  - 使用成熟的中文 NLP 模型 (spaCy/BERT)
  - 提供人工校正功能
  - 设置置信度阈值过滤低质量实体

风险 2: Neo4j 性能问题
- 影响: 大规模图谱查询慢
- 应对:
  - 合理设计索引
  - 使用分页查询
  - 前端限制节点数量 (< 1000)

风险 3: 前后端集成复杂
- 影响: 开发周期延长
- 应对:
  - 先做后台验证技术
  - 前台分阶段实现
  - 使用成熟的可视化库 (Sigma.js)

### 9.2 时间风险

风险: 开发时间不足
- 影响: 功能不完整
- 应对:
  - 严格按优先级实施 (P0 -> P1 -> P2)
  - P0 必须完成，P1 尽量完成，P2 可选
  - 预留 2 周缓冲时间

### 9.3 数据风险

风险: 数据迁移失败
- 影响: 图谱数据不完整
- 应对:
  - 编写完善的迁移脚本
  - 迁移前备份数据
  - 分批迁移，逐步验证
